## 1. 模块与进程

### 1.1 四个模块,两种拓扑

模块划分是**逻辑的**,进程划分是**部署的**。同一份代码按配置装载出两种拓扑(`00` §4)。

| 模块 | 职责 | 状态所有权 | 可多实例 |
|---|---|---|---|
| **gateway** | TCP 接入 · 分片路由 · 握手与限流 | 无状态 | ✅ |
| **world** | 世界模拟 · L3 规则 · 战斗 · 移动 · NPC · 视野 | ★ 进程内权威,扁平池常驻 | ✅ 按线路分片 |
| **session-storage** | 账号 · 存档 · 登录态 · 角色增删 | MySQL 权威 | ⚠️ 需分布式锁 |
| **social** | 家族 · 庄园 · 邮件 · 排行 · KV · 跨线路聊天室 | MySQL 权威 + Redis 派生 | ✅ |

> ★ 模块边界取自 `17` §9 方案 B(**按延迟敏感性切,不按业务名词切**):
> **7 条"会挂起玩家"的协议全部落在 session-storage**;social 的 39 条**一条都不挂起玩家**。

### 1.2 模块间只有一种通信方式

```
Request / Response(72 条)   必带 { instance_id, generation, request_id, deadline_ms }
Notify(34 条)               Ack{accepted} 只代表入队,不代表持久化
                             ★★ 资产类操作禁走此路(见 §8.3)
```

> ★★ **本节是双拓扑的支点。违反它,单容器跑通、生产分布式挂。**
>
> **落地为编译期约束**:
> - 每个模块编译为独立静态库,只对外暴露 `include/<module>/api.h`(纯接口 + POD 消息类型);
> - 模块实现头不进入其它模块的 include 路径;
> - 模块之间**不得**出现对方的具体类型、全局变量、容器引用;
> - 进程内传输是 `ITransport` 的一个实现,**不是"同进程可以直接读"的许可**。
>
> CI 中加一条检查:`grep` 各模块 `src/` 对其它模块 `src/` 路径的 include,命中即失败。

## 2. 线程模型

```
world 进程
 ├─ 主线程         ★ 全部业务逻辑,单线程,无锁      ← 与原版一致,刻意保留
 ├─ I/O 线程池     socket 读写 · 解密 · 分片重组     ← 只做搬运,不碰领域对象
 ├─ 存储线程池     MySQL 调用(阻塞)                ← 结果以消息回投主线程
 └─ 定时线程       节拍源(见 §3.2)
```

**业务逻辑严格单线程**,这不是妥协而是裁定:

- 原版即如此(`01` §3.2:即使启用 epoll-ET 模式,"业务逻辑仍严格单线程,线程只承担 I/O 与解密");
- `15` 实测世界状态是**启动期一次性 `calloc` 的定长数组、运行期零分配**,单线程访问是这个布局的前提;
- 回合制玩法对延迟不敏感,**横向扩展靠增加线路分片,而非线路内并行**(`01` §15.2)。

⚠️ **主线程绝不允许阻塞**。所有 MySQL / Redis / 跨模块调用一律异步:发出请求 → 记续体 →
继续 tick → 结果到达时在主线程恢复。续体形状见 §7.2。

## 3. 主循环与节拍

### 3.1 tick 顺序

原版 `mainloop()` 的顺序是"整个服务端行为的骨架"(`01` §2),新实现保留其**语义顺序**,
但每一项都改为有预算、可观测:

```
tick(dt):
    1. 时钟推进        统一时钟源,单调时钟,不用墙钟做逻辑判断
    2. 网络入站        从 I/O 线程取已完整的消息,派发到会话
    3. NPC 生成
    4. 战斗推进        ★ 受节拍层控制,不再等于 tick 频率
    5. 角色循环        移动 / 状态 / 秒级效果
    6. 定时业务        存档检查 / 家族同步 / 宠物邮件
    7. 出站聚合        视野 Appear/Disappear 聚合 flush(见 §5.3)
    8. 关闭检查
```

### 3.2 ★ 节拍层(必须新增,原版没有)

`15` §5.2 实测:8.0 的 `_BATTLE_TIME` 与 `_CHAR_LOOP_TIME` **均为关**
⇒ **战斗推进速度 = tick 频率**,原版的实际手感取决于当年的硬件与网络。

⇒ 新实现**必须显式建模节拍**,且它是**玩法参数不是性能参数**:

| 节拍 | 含义 | 配置项 |
|---|---|---|
| `tick_hz` | 模拟频率(性能) | 固定,不影响玩法 |
| `battle_turn_interval` | 战斗回合间隔(**玩法**) | 可配 |
| `char_loop_interval` | 角色循环间隔(**玩法**) | 可配 |
| `ca_flush_interval` / `cd_flush_interval` | 视野聚合 flush | 可配 |

⚠️ **这是"手感"层唯一可调的旋钮。** `00` §0 已确认 ④ 层永远无法验证 ——
节拍值只能靠人试出来,所以它必须是**热可调的配置**,不是编译期常量。

⚠️★ ~~**1.5 只建最小切面,但目录与链接边界要一次立对**~~ ⇒ ✅ **已一次立对**:各模块
编译为独立静态库、只对外暴露 `include/<module>/api.h`(`00` §3.1)。
**事后拆比一开始就分贵得多**,而违反它的后果是 `00` §10.4 三类静默错误里最难查的那种
(单容器跑通、生产分布式挂)。⚠️ 该边界**建起来了不等于守得住** —— 新增模块时须沿用同一形状。


★ **`shared/` 是 D2 的物理体现** —— 该目录被客户端仓以 CMake `FetchContent` + 锁定 tag 方式引用
(DR-TS3),**两端编译同一份源码**。因此它只能依赖标准库:不得出现 socket、MySQL、日志、
以及任何 `#include` 服务端头文件的代码。

### 4.1 ★ 这条约束现在是可执行的检查,不是口头纪律

`tools/check_shared_purity.py`(2026-08-31,`ctest` 必跑项)扫描 `shared/` 的每条 `#include`,
命中即失败:

| 禁止 | 后果 |
|---|---|
| `transport/**` | `02` §9:`shared/` 依赖信封/握手/错误面 ⇒「只依赖标准库」破裂 |
| socket / MySQL / Redis / 日志 / ~~asio~~(DR-TS8 已定不引) | 属 L0,客户端侧无法满足 ⇒ D2 当场失效 |
| ★ `<chrono>` / `<ctime>` | L3 读时钟即破坏**可回放性**(`05` §1.5) |
| ★★ `<random>` | 随机源必须经注入的 `IRandom`(`07` §11.3 判据 ④);且 `std::uniform_int_distribution` 的取数方式**不由标准规定**,跨标准库实现序列不同 ⇒ 黄金用例集会整批失败 |
| I/O / 并发原语 | L3 是纯函数(判据 ③) |

⚠️ **为什么用脚本而不是 CMake 的 include 路径隔离**:IDL 生成物的 `#include` 一律从
`generated/cpp` 根算起(如 `"domain/common.sg.h"`)⇒ 只要把该目录加进 include path,
`domain/` 与 `transport/` 就**同时可见**,无法只暴露其一。CMake 也管不住 `#include <sys/socket.h>`。

### 4.2 ⚠️ `shared/` 的编译标准是 C++17,不是 C++20

D1 裁定服务端 C++20,但 **GameStudio 是 C++17**(`00` §1.2)。
⇒ `shared/` 目标显式锁在 C++17,**让双端不兼容在服务端构建时就暴露**,
而不是等到客户端集成那天才发现某个 C++20 特性用不了。

> ★★ **2026-09-02 后记 —— 这条做对了,但它不够。**
>
> 客户端集成那天(`00` §9.0.5)确实**没有**出现任何 C++ 标准层面的不兼容 ⇒ 本节的措施有效。
> ⚠️ **但拦不住的另有其类**,当天实测撞到两样:
>
> | 类 | 实例 | 为什么服务端侧永远看不见 |
> |---|---|---|
> | **构建接口** | `shared/CMakeLists.txt` 依赖顶层的 `sg_idl` / `sg_apply_warnings` ⇒ 客户端只引入 `shared/` 时**配置期就失败** | 服务端顶层永远先定义了那两样 |
> | **标准库巧合** | 客户端 `BootScene.cpp` 用 `va_list` 只包含 `<cstdio>`,Apple libc++ 顺带带进来 ⇒ 编得过,**换标准库就断** | 与 `shared/` 无关,但同一类:靠实现细节而非标准 |
>
> ⇒ ★ **「双端兼容」不只是语言标准一维**,还有构建接口与标准库实现两维。
> 前者已修(`d939247`);后者只有**换一套真正不同的工具链**才能系统性暴露
> ⇒ 见 §13 欠债 7。

### 4.3 ★ `shared/` 必须可被独立消费(2026-09-02 补)

DR-TS3 承诺「客户端以 FetchContent + 锁定 tag 引用 `shared/`」。
⇒ ★ **`shared/CMakeLists.txt` 不得依赖服务端顶层定义的任何目标或函数** ——
否则 `add_subdirectory(shared)` 在客户端侧配置期就失败,DR-TS3 只是纸面成立。

现在的写法是「有就用、没有就就地补」:

| 依赖 | 缺失时 |
|---|---|
| 目标 `sg_idl` | 就地建等价 `INTERFACE` 目标,指向 `../idl/generated/cpp` |
| 函数 `sg_apply_warnings` | 跳过 —— 告警口径由**消费方**在自己那侧给(工具链不同,`-Wconversion` 这类开关不可能逐字通用) |

⚠️ **这条约束没有自动化守卫。** 服务端顶层构建**永远不会**触发它,
因为顶层总是先定义那两样。⇒ 唯一的检验是客户端仓的 `d2-only` 预设,
它现在是 CI 上最该常驻的一条(客户端 README)。

## 5. 网络与会话

### 5.1 `ITransport`

```
ITransport
 ├─ TcpTransport        ✅ 2026-09-05 —— ★ 原生 socket + poll(2),不走 asio(DR-TS8,00 §9.0.14 ①)
 ├─ LoopbackTransport   ✅ 1.5 —— 全部非 socket 用例的载体;同时是下一行的雏形
 ├─ InProcTransport     单容器形态下的模块间传输(阶段 3)
 └─ WsTransport         D4 解冻时新增,不动上层
```

⚠️ 协议**自带长度前缀**。TCP 是字节流、WebSocket 是保留消息边界的,长度前缀同时满足两者 ——
这本来就该做,现在只是把理由写明。

★ **TcpTransport 只做对三件事,其余是样板**(tcp_transport.cpp 卷首):① 出站背压 —— `send()` 写不完的尾巴排队、下一轮 `POLLOUT` 续写,
配 `kMaxOutboundBytes` = 4 MB 熔断(对端连上却不读时断连,不等待);② 短读与粘包不是本层的事,`OnBytes` 交出的就是这一轮读到的字节;
③ 回调期间容器不得失效(宿主会在 `OnBytes` 里反过来 `Send`)。★ `net/api.h` 里**没有一个平台类型** —— `windows.h` 的宏不许顺着 PUBLIC 头传染给 world 与 tests。

⚠️ **不复刻原版网络层**:`01` §3.1 的 `netloop_faster` 是**每个连接一次 `select` 系统调用**
(1000 连接 = 一轮最多 1000 次 `select` + 1000 次 `read`),`15` 实测
**51 处容量界循环中 35 处上限是 `fdnum`,19 处在 `net.c`** ⇒ **计算量主项是网络层轮询,不是战斗**。
这是纯粹的历史包袱,**无任何语义需要保留**。

### 5.2 连接与会话生命周期

原版 `LoginType` 是连接级状态机(`01` §3.3),新实现保留状态划分但把它从连接上剥离:

```
Connection(传输级)      : 建立 → 握手 → 活跃 → 关闭
Session(账号级)         : 匿名 → 认证中 → 已认证 → 选角中 → 在线 → 登出中
CharacterInstance(世界级): 载入中 → 在世 → 保存中 → 卸载
```

三者**生命周期不同**,原版把它们压在一个 `LoginType` 上,导致掉线路径与停服路径各自
长出一串状态。分开后,掉线只影响 Connection,Session 可保留重连窗口。

⚠️ **索引不得线性扫描**。原版 `getfdFromCdkey` / `getfdFromCharaIndex` /
`getCharindexFromFdid` / `getFdidFromCharaIndex` **全是线性扫描**(`01` §3.3)。
新实现用哈希索引,且句柄稳定(见 §6.2)。

### 5.3 出站聚合与广播

- **保留** CA/CD 聚合思想(周边角色 Appear/Disappear 攒批 flush)—— 这是原版唯一的带宽优化机制;
- ★ **频道类广播改订阅制** —— 原版除地图局部广播外全是"全扫 `fdnum`"(`15` §7.3);
- ★ **重设每连接缓冲** —— 原版每连接固定 **324–452 KB** 双缓冲,是 `sizeof(Char)`(12.3 KB)的
  **26–37 倍**,是每连接成本主项(`15` §4.3)。新实现按需增长 + 上限熔断。

## 6. 协议层

### 6.1 IDL 是唯一真源

一份 schema 生成两端编解码。**不实现旧 lssproto**(R2),`10` 的 151 + 123 条清单是
**语义参考,不是兼容目标**。

⚠️ **必须显式赋值每个协议号与窗口类型**。原版是"枚举顺序即协议号"的隐式约定,而
`10` §0.2 实测**枚举成员集受 `#ifdef` 影响、两端宏集不同** ⇒ 私服分叉后必然破裂
(5 个编号两端指向完全不同的功能,客户端头文件自身还有 2 处同号重复)。
**这是旧实现两端漂移的根因。**

### 6.2 不沿用的三个历史构造

| 原版构造 | 处置 | 依据 |
|---|---|---|
| 协议编号偏移(上行 +13 / 下行 +23)与分发魔数 `1458` | ❌ 不沿用 —— 新 IDL 下这两个常量不存在 | `00` §9.2 的语义反转 |
| saacproto 的 **base-62 整数编码** + 名字 `strcmp` 分派 | ❌ 不沿用 | `10` §D |
| 字段级 `PersonalKey` + 整包 TEA(`DENGLUKEY1` 两端硬编码) | ❌ 不沿用,改标准 TLS | `02` §3.2 |

### 6.3 服务端驱动 UI:保留思想,改变传输

原版几乎所有 UI(NPC 对话、商店、银行、家族、任务)由服务端经 `WN` 协议驱动,
客户端窗口只是渲染器(`02` §6.1)。

**这条思想保留** —— 它减少客户端逻辑、天然防改,且与"服务端权威"一致。
**但传输从"字符串拼装"改为结构化消息**:原版 `WN` 负载是自定义分段串,
`10` §5.4 已还原其原始规格(首 token = 消息行数、其后每 token 一个选项、1-based 回传)。
新实现把这套语义表达为 IDL 中的结构化窗口描述。

## 7. 领域模型与数据布局

### 7.1 对外和类型,对内扁平池

```
对外(shared/model)   CHAR_TYPE 分派的和类型 —— 47 种实体,强类型,不可混淆
对内(world 运行时)   定长池 + int 下标句柄 —— 启动期一次性分配,运行期零分配
```

**两者必须同时成立**,这是 `00` §1.2 点明的附带前提:
`15` §9.1 的三根支柱(运行期零分配 / 活对象数常量且几乎无指针图 / 单 tick 只触及 5.4% 槽位)
依赖扁平布局;而 `11` 的 65 条 slot 别名要求对外必须是独立强类型字段。
⇒ **句柄是 `int` 下标,不是裸指针;实体访问经类型化视图,不直接暴露池。**

### 7.2 三条不可违反的模型约束

| # | 约束 | 违反后果 |
|---|---|---|
| **M1** | **65 条别名展开为 65 个独立字段**,不得合并任意两个 | ★ 静默错误 —— 不报错、不崩溃、数据烂掉(`CHAR_CHARM` 魅力在宠物身上是 `CHAR_MODAI` AI 模式) |
| **M2** | **不照搬定长槽位数组** —— 死字段 80 个中 37.5% 来自批量预留槽位(`MATERIAL02..25` / `LOWRIDEPETS3..8`),改为变长集合 | 存档与内存双重浪费 |
| **M3** | **持久化边界沿用字段级划分**(285 个有存档键 / 384 个纯运行时) | 把运行时字段一起持久化 ⇒ **存档膨胀 135%** |

### 7.3 `GoldLedger` 单入口

石币在原版**不是一个字段,是 5 个载体 + 4 个独立上限**
(`GOLD` / `BANKGOLD` / `PERSONAGOLD` / `AUCGOLD` / `FMBANKGOLD`),
且 **96 个写点里 60 个(62.5%)绕过**唯一带上限与余额检查的 API
⇒ **原版没有"金钱变更"这个领域操作,只有"往 int 字段写值"**(`12`)。

```
GoldLedger::apply(subject, delta, reason, ctx)
    ① 钳位      ② 溢出处置      ③ 写审计       ← 三步不可拆
```

⚠️ **合并 5 载体前必须先决定 4 个上限怎么合并。** 且注意:8.0 随身上限 =
1,000,000 + 转生×1,800,000,8.5 改成阶梯且兜底 100 万 → 1 亿(**100 倍**)
⇒ **原版经济的净回收是靠上限压出来的,不是靠设计;照抄 8.5 上限会把经济压力整个抹掉。**

## 8. 存储与一致性

### 8.1 MySQL 访问

| 项 | 定 |
|---|---|
| 版本 / 引擎 | MySQL **8.4.8** / InnoDB / `REPEATABLE READ` |
| 字符集 | ★ `utf8mb4` / `utf8mb4_0900_ai_ci`,**库级强制** |
| 客户端库 | **Connector/C++ 8.4**,JDBC 风格,3306 |
| 认证 | ★ `caching_sha2_password` + TLS(8.4 已默认停用 `mysql_native_password`) |
| 角色档 | ★ **JSON 列 + 生成列索引**,不引入文档库 |

⚠️ **内容资产入库前必须完成编码归一** —— 原始数据五态混编、**64 个文件行内就混编码**
(`09` 坑 2)。决策 ② 保证新库从第一天干净,
但**任何一条乱码串进库,之后就再也分不清是数据本身还是转换错误**。

### 8.2 工作单元(unit of work)

★ **两侧都要做,不是只有数据库那一侧。**

`17` 给的是 saac 侧的事务面(12 个"必须原子"操作,有保护的 **0** 个);
`12` 补上 gmsv 进程内的另一半 —— `trade.c:975 TRADE_HandleTrade` 是
**10 步顺序结算 + 零回滚**,任一步失败就把已扣的道具/宠物/石币留在半途。
**⇒ 加数据库事务解决不了后者。**

```
world 进程内 UoW:  收集变更 → 全部校验通过 → 一次性提交到领域对象
                   任一校验失败 ⇒ 整体丢弃,不留半途状态
storage 侧   UoW:  InnoDB 事务
跨模块       UoW:  Saga + 补偿(见 §8.3)
```

### 8.3 一致性对策表

| 缺口(实测) | 对策 |
|---|---|
| 12 个"必须原子"操作零保护 | 单库内 InnoDB 事务(9 条);跨模块 Saga |
| **角色删除横跨 3 个职责域且不等第 1 条结果**(密码错 ⇒ 角色还在但决斗点与名片簿已删) | **Saga + 补偿**:删存档成功后才删派生数据 |
| 公共仓库 **fire-and-forget 后立刻销毁本地道具对象** ⇒ 道具永久蒸发 | ★★ **资产移动一律"预留 → 提交"两阶段,禁走 Notify** |
| 点数**读-改-写两条独立 SQL** | **原子增量或 CAS** |
| `charSave` **先解锁后写盘**(写盘失败 ⇒ 锁已放、新档未写、进度永久丢失) | **写盘成功后才释放锁** |
| **72 条**需显式请求关联(不是 49 条) | 全部带 `request_id`,不靠连接顺序对齐 |
| **`SERVSTATE_init()` 把 fdid 归零** ⇒ 重启后迟到应答可能命中新连接 | 续体带 **(instance_id, generation, request_id)** 三元组 |

### 8.4 锁

`ILock` 的**默认且唯一实现是 Redis**(生产与测试都用,不做进程内变体)。

理由是实测:原版账号锁是**纯进程内存 256 桶哈希链**,且 **42 条家族协议完全无锁**,
今天不出事靠"saac 单线程隐式串行"。**多实例一上,该隐式保证立刻消失。**

⚠️ 顺带不复刻的一个 bug:原版星系移民锁的守卫字面量 4 处里错 1 处
(`DeleteMemLock` 写成 `"移民"`)⇒ **移民锁会被当普通锁删掉**(`17` §F)。
新实现把锁语义显式建模,不用字符串比对做守卫。

## 11. 启动与关闭

### 11.1 启动序列

原版按 `setup.cf` 依次加载数十个数据文件,**任一失败即拒绝启动**(`01` §2)。
**这个"快速失败"的性质保留** —— 内容数据不全就起来,只会在玩家碰到时才炸。

```
1. 读配置 + schema 校验          任一项不合法 ⇒ 拒绝启动
2. 连接 MySQL / Redis            ⇒ 拒绝启动
3. 分配定长池                     ★ 一次性,此后运行期零分配
4. 装载 L4 内容资产               ⇒ 任一失败拒绝启动
5. 装载模块(按部署配置)
6. 绑定端口 / 注册分片
7. 进入 tick
```

> ✅ **1.5 已接的步骤(2026-09-05)**:1 · 5 · 6 · 7。2 要 storage,3 要 L2 实体族,4 要内容管线 —— 都属阶段 2。
> ★ 第 6 步失败的形态是 `listen_failed` 事件(带 errno 文本)+ 退出码 1,与第 1 步的 `config_rejected` 同一性质:
> 任一步失败即拒绝启动,且原因要在日志里说得出(`00` §9.0.14 ②)。

### 11.2 关闭

原版有 `ShutdownProc` 停服流程与 `WHILECLOSEALLSOCKETSSAVE` / `WHILESAVEWAIT` 状态。
新实现:

```
收到停服信号 → 拒绝新连接 → 广播倒计时 → 逐会话保存(带并发上限)
              → 等待在途跨模块请求收敛(带 deadline)→ 落盘确认 → 退出
```

> 1.5 只做了能做的一段(2026-09-05):SIGINT / SIGTERM ⇒ `shutdown_signal` ⇒ `RequestShutdown` ⇒ 同一 tick 的第 8 步关闭全部连接
> ⇒ `Stop` 传输层 ⇒ 退出码 0。广播倒计时 / 逐会话保存 / 等在途请求收敛,要等 storage 与跨模块请求存在。
> ⚠️ 信号处理函数里只置标志,日志与关连接都在主线程的 tick 里做。

⚠️ **保存必须"写成功再释放锁"**(§8.3),这正是原版 `charSave` 出错的地方。
