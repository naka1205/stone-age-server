### 1.1 DR-TS1 的裁定理由与边界

**形态**:

```
schema/*.proto          .proto 语法(不自己设计语言)
     ↓  protoc --descriptor_set_out   ★ 只在构建期,且只用它做解析
descriptor set
     ↓  自写 codegen 后端
idl/generated/*.h       ★ 纯 POD struct + 手写编解码,零运行时依赖
```

**三条硬约束**三个候选方案都满足 ⇒ **分歧点不在约束,在依赖纯净度与自建成本。**

★ **决定性依据 —— 用不到 Protobuf 的核心价值,却要付它的全部成本**:

| Protobuf 的核心卖点 | 本项目 |
|---|---|
| 向后兼容的 wire format | ❌ 用不到 —— §2.1 已裁定「版本不匹配在握手阶段直接拒绝,不做版本分支」 |
| 跨语言 | ❌ 用不到 —— D1 全线 C++20 |
| 反射 / `Any` / 动态消息 | ❌ 无使用场景 |

而成本是实打实的三条:

1. ★★ **`shared/` 的依赖约束会被破坏**。`01` §4 明写「`shared/` 只能依赖标准库」,
   而 `02` §9 又要求 `shared/rules` 输出 IDL 事件类型 ⇒ 用 protobuf message 作事件类型,
   `shared/` 就依赖了 libprotobuf。**这两条裁定会直接冲突,必须改一条。**
2. **protobuf message 是堆分配**,与 `15` §9.1「运行期零分配」有张力
   (仅影响消息对象、不影响 `Char` 池,但方向相反);
3. **客户端多一个重量级依赖** —— 实测 GameStudio 现有依赖只有 **SDL3 系列 + zlib**,
   依赖面很干净;客户端 `01` §6.1 的原则是「引擎只依赖 SDL3/zlib/rapidxml,加网络会破坏其边界」。

⇒ 选定方案**同时保住**:`shared/` 只依赖标准库(`01` §4 不改)· 运行期零分配(`15` §9.1 不改)·
客户端依赖面不变 · schema 语法不用自己设计。

**代价**:codegen 后端约 1–2 周。⚠️ **这是本方案唯一的成本,须显式认下。**

⚠️ **边界(不得越界)**:

| # | 约束 |
|---|---|
| 1 | ★ **protoc 只用于构建期解析**(产出 descriptor set)。**运行时不链接 libprotobuf** |
| 2 | ★ 生成产物**必须是 POD**(可 `memcpy`、无虚函数、无堆成员);变长字段用显式的定长上限或调用方提供的缓冲 |
| 3 | ★ **`msg_id` 不是 protobuf 的概念** —— 用 `.proto` 的自定义 option 显式标注,codegen 校验唯一性(对接 §8 的 CI 检查 1/2) |
| 4 | ★ `.proto` 里**不得使用** `Any` / `oneof` 以外的高级特性;`oneof` 生成为 **tag + union**,不生成继承 |
| 5 | schema 分两组:`schema/domain/`(`shared/` 可依赖)与 `schema/transport/`(只有 `src/net` 依赖),见 `02` §9 |

### 1.2 ★ DR-TS5 — 角色名长度上限(新增,✅ 已裁定)

**来源**:不是从文档推导出来的,是**写 `domain/battle_events.proto` 时撞上的** ——
`CombatantState` 需要给 `name` / `title` / `pet_name` 三个字段一个定长上限(DR-TS1 边界 ②)。

**证据两条,互相矛盾**:

| 出处 | 值 | 性质 |
|---|---:|---|
| `char_base.h:1345` `STRING128 string[CHAR_DATACHARNUM]` | **127** + NUL | 物理槽宽,**是存储事实** |
| `char_base.c:2228` `if( strlen(name) > 16 )` | **16** | ⚠️ **其告警 `print` 被注释掉了 ⇒ 不强制**,只是一处失效的提示 |

⇒ ★ **原版没有真正生效的名字长度上限**,只有一个槽宽。
**现取 127**(按槽宽,不截断任何原版可表达的名字),但这是**存储事实、不是玩法口径**。

⚠️ **它有可度量的后果**:三个名字字段占 `CombatantState` **428 B 中的 384 B**
⇒ 全场 20 人的 `BattleSnapshot` = **8,576 B**。
若定为 31,快照降到约 **2.6 KB(3.3×)**。

⚠️ **这条不挡 1.4 demo**(127 可用),但**上线前必须裁定** ——
名字长度是玩家可感知的玩法口径(能不能起长名字),按 §0 规则 3 不设"暂时这样"。
⇒ 需人显式选定,**不由实现者按体积偏好定**。

✅ **裁定:31 字节**(2026-09-07,用户拍板)。三个字段 `name` / `title` / `pet_name`
统一定 `(sa.max_len) = 31`。理由:原版 `>16` 告警 `print` 被注释掉 ⇒ 从不生效,
127 只是槽宽而非玩法上限;31B ≈ 10 个汉字 / 15 个 ASCII,对石器时代角色名够用,
且把 20 人 `BattleSnapshot` **从 8,576 B 降到 2,816 B(3.05×)**
(⚠️ 上文预估「约 2.6 KB / 3.3×」是裁定前的估算,**2,816 B 是 2026-09-07 实测值**,
已连带更新 `02` §10.1 体积表并补一条等值 `static_assert` 钉住它)。
落地:`idl/schema/domain/battle_events.proto` 三处 `max_len` 127→31 + 重跑
`saidl_gen.py` 生成 `FixedStr<31>`;`ci_verify.py` 六项全绿、`idl --check` 一致。
⇒ **§14 待拍板降为 0 条,关键路径无 ⏳**(全表仍有 7 条 ⏳ 待数据,均不挡关键路径)。

### 1.5 ★ DR-TS8 — 服务端网络栈(新增,已裁定)

**来源**:与 DR-TS5 同类,**写代码时撞上的** —— 1.5 收尾项 `TcpTransport` 落地前,`01` §12 与 `00` §8 的技术栈表写着
「asio + C++20 协程」,而那一行从未被任何一次实现检验过。

✅ **裁定:原生 socket + `poll(2)`,单线程 reactor;asio 不引入**(2026-09-04,用户拍板)。

| # | 理由(按分量) |
|---|---|
| ① | ★ `ITransport::Poll()` 的契约(主线程 tick 第 2 步调用、不得阻塞)**本来就是 reactor**。asio 协程的价值在这个接口下发挥不出来 —— 要么改接口让 `io_context` 独占一个线程(推翻 `01` §2 的线程模型),要么退化成 `io_context.poll()`,那只是把 poll 包了一层 |
| ② | 它会是 `src/` 的**第一个运行时第三方依赖**(doctest 只进 `tests/`)⇒ FetchContent + 三平台 CI 是一笔独立的引入成本 |
| ③ | ★ 与 `platform/api.h` 日志那处偏离(不引 spdlog)**同一条先例**:接口先立死、库延后引 —— `ITransport` 已把替换成本压到局部,换 asio 不动上层一行 |

**认下的代价**:`poll(2)` 是 O(连接数),上规模时换 epoll / kqueue / IOCP(`01` §13 欠债 13)。
⚠️ 这不是回到原版:原版是**每连接一次 `select`**(1000 连接 = 1000 次系统调用,`01` §5.1),poll 一次调用传整个数组已不同量级。
⇒ `00` §8 与 `01` §12 技术栈表同步改;落地细节见 `00` §9.0.14 ①。

### 1.6 ★★ DR-TS9 — 客户端 `sa_net` 的成帧 / 信封层归属(新增,✅ 已裁定)

**来源**:与 DR-TS6 同类,**排期时撞上的** —— 1.5 收尾后追问「1.4 客户端侧的第一行网络代码写在哪、抄不抄服务端」,
发现客户端 `01` §12.1 只写了 `sa_net` 要「`ITransport`(TCP)· 长度前缀成帧 · IDL 编解码接入 · 握手会话」,
没有回答成帧与信封编解码这两样**双端语义相同**的东西从哪来。服务端 `src/net` 已有一份(`framing.cpp` 115 行 + `net/api.h` 的 `FrameReader` / 信封),
被 18 条用例钉死;而 D5 只说「`sa_net` 首次放游戏仓」,没说它与服务端那份是什么关系。

| 案 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **甲 自写** | 客户端 `src/net` 自己实现 `FrameReader` / 信封编解码 / 客户端侧握手 | 目录形状与 D5 一致;服务端零改动 | ★ **同一语义两份实现** —— 与 DR-BT5 反对「双份实现必然漂移」的理由正面冲突。成帧层现在不大,但信封 / 错误面 / 握手会随 0.2 的号段增长 |

### 2.9 DR-DT9 的公式与边界(属性推导,批次 M.3)

**移植来源**:`CHAR_complianceParameter`(展开视图 `char/char.c:3525`)是**编排器**,真公式在它调的
`CHAR_initcharWorkInt`(`:3419-3487`)。其产物 attack/defense/quick/max_hp 是 `CHAR_WORKDATAINT`
**派生字段(不存档)**,而原始四维 vital/str/tough/dex 是存储字段 —— 印证「三围是推导量,不是存量」。

**公式**(⚠️ 每个 `CHAR_setWorkInt` 第三参是 `int`,整表达式算完 `static_cast<int>` 截断一次):

```
attack  = (int)( str*0.01 + tough*0.001 + vital*0.001 + dex*0.0005 )
defense = (int)( tough*0.01 + str*0.001 + vital*0.001 + dex*0.0005 )
quick   = (int)( dex*0.01 )
max_hp  = (int)( (vital*4 + str + tough + dex) * 0.01 )   ★ 原版经 float 中间变量(char.c:3397)
max_mp  = 直接读 CHAR_MAXMP 字段,不推导(char.c:3488)
```

### 2.10 DR-DT10 的边界与四维生成公式(批次 M.4a)

移植来源 `ENEMY_createEnemy`(展开视图 `char/enemy.c`),四维生成分**四步,顺序即语义**:

| 步 | 行号 | 做什么 |
|---|---|---|
| ① | `:1045-1048` | 四维基数各 `+= RAND(0,4) − 2`(取值 {−2..2},闭区间) |
| ② | `:1052-1056` | ★ **成长率打包** —— 用的是**此刻**的基数 |
| ③ | `:1058-1064` | `for i<10`:`RAND(0,3)` 给对应维 `++` |
| ④ | `:1067-1070` | `PARAM_CAL(base) = ((level−1) × LVUPPOINT + INITNUM) × base` |

★★ **成长率取「+10 之前」、四维取「+10 之后」** —— 照抄时最易做错的一处;
把 ② 挪到 ③ 之后,成长率会系统性偏大(期望 +2.5/维)。
⚠️ `:1040` 与 `:1042` 是 `#if 1` / `#else` 的两个 `PARAM_CAL`,**只有 `:1040` 生效**
(unifdef 不解析 `#if 1`,展开视图里两行都在)。

**DR-DT10 的偏离面(已量化,2026-09-08 实测 csa8.0 数据包)**:

- 打包的语义是**四个独立的 8 bit 槽**(消费侧一律 `(p >> shift) & 0xFF`),而原版用 `+` 拼接。
- 只有**低三位(str/tough/dex)为负**时才会借位 —— `vital` 是最高位,无处可借。
- 1,053 行模板中**低三位含 ≤1 基数的 39 行(3.7%)是上界**,且需该维实际被摇成负
  (基数 0 时约 40%、基数 1 时约 20%)。
- 实测对照 `[vital=150, str=−2, tgh=50, dex=−2]`(行 45「光之圣石」摇到 −2):
  **原版 `[149, 254, 49, 254]`** vs **本实现 `[150, 254, 50, 254]`** ——
  借位污染了 `vital` 与 `tough` **两维各 1**。
- ★ **字段内回绕保留**:基数 `300 ⇒ 44` · `400 ⇒ 144` · `−2 ⇒ 254`,与原版逐位一致
  (10 组边界交叉实测,只有跨字段借位那两组分歧)。

⚠️ **两处照抄不修,别顺手"修正"**:
① **负四维**:`PARAM_CAL(−2) = −20`,原版就是这样,且 `deriveBaseStats` 对负输入照算 ⇒ 不在此兜底;
② **成长率的 ≤60 / ≤50 夹取不加** —— `03` §6.1 的 M6 要求逐调用点保留各自上限,而那两条
   属**别的路径**(≤60 进化/孵化 · ≤50 死亡扣属,`battle.c:5868` PETID 718),
   **创建路径源码里一处夹取都没有**;0..255 的字段容量由 `std::uint8_t` 类型本身兑现。

**反向验证四处**(每处注入 → 报红点名 → 还原 → 复跑回绿):
① 成长率打包挪到 ③ 之后 ⇒ `30 == 20` 红;
② 改回原版 `+` 打包 ⇒ `149 == 150` **与** `49 == 50` 双红(与上表实测值逐位吻合);
③ `replicate_atoi_truncation` 失效 ⇒ `3000 == 2700` 红;
④ ±2 的四次 `rand` 换序 ⇒ `148 == 150` 红(可回放序列变了)。


### 2.11 DR-DT11 —— 评级档位 `enemyRank`,与 M.4b 一并核出的三处事实(批次 M.4b)

移植来源 `ENEMY_getRank`(展开视图 `char/enemy.c:802-840`)。公式极短,但它带出的三条事实

### 2.12 DR-BT22 —— 捕获的两个数据源分工与敌人实体的生命周期(批次 M.4b)

原版 `PET_createPetFromCharaIndex(charaindex, enemyindex)` 从**一个完整的 `Char`**
一处拷全部字段。我们把敌人拆成了**两半** —— L2 实体 `Model::Enemy` + 战场投影
`Rules::Combatant` ⇒ 拷的时候必须各取权威的那一半:

| 字段 | 取自 | 为什么不能取另一个 |
|---|---|---|
| `hp` / `mp` / `max_mp` | **战场 `Combatant`** | 战斗中的血量写在投影上;L2 实体的 `hp` 是**入场时**的满血值,取它会把"抓一只残血怪"变成"抓一只满血怪" |

★★ **敌人实体的生命周期照源码,不是我们加的清理**:
`_BATTLE_Exit`(`battle.c:1114-1115`)对 `CHAR_TYPEENEMY` 直接 `CHAR_endCharOneArray`
⇒ **敌人离场即销毁实体**,与"玩家离场只是退出战斗"截然不同。
⇒ 落地为两处释放:捕获成功后(目标离场)· 战斗结束时(剩余敌人)。
⚠️ 漏掉的后果与 `01` §13 欠债 20 那条一模一样:**池只增不减、没有一处报错**,
且敌人池每场战斗都分配 ⇒ 泄漏得比宠物快得多。

**三处照抄不修**:

① ⚠️★★ **`luck` 恒 0,而这是同槽异义的必然结果,不是"幸运没实现"**:
   `CHAR_VARIABLEAI == CHAR_LUCK`(`include/char_base.h:637`)——
   `pet.c:347` 以「幸运」的名义读,`enemy.c:1076` 以「AI 变量」的名义写了 **0**。
   ⇒ `Model::Enemy` **不建 `luck` 字段**(原版里敌人没有这个属性),
   捕获处写 `pet->luck = src_enemy->variable_ai` 而不是 `= 0` —— ★ 让这条同槽异义
   **在代码里看得见**;写 0 会让下一个人以为是我们省事。
   ★ 这是 `03` §9 的 **M1**「合并任意两个别名都是静默错误」目前最干净的样本:
   两个名字的值恰好都是 0 ⇒ **合并了连测试都抓不到**。

② `capture_difficulty` **不兜底 30**:`battle_event.c:3845` 的 30 是局部初值、随即被
   `CHAR_getWorkInt` 覆盖 ⇒ 30 是"读不到时的兜底",不是默认值。
   ★ 实测 `E_T_GET` 真实取值是 **−30..30 的小整数**(最常见 11 = 276 行 · 0 = 265 · −1 = 142),
   载入器对空列保持 `-1`(`06` §3.5)⇒ 照传不修。
   ⇒ `Combatant.h` 里「1.5 无敌人数值表 ⇒ 调用方按 30 兜底」那条到此兑现,兜底值退场。

③ ★★ **HP 夹取(`min(HP, WORKMAXHP)`,`char.c:3555`)不在"入场投影"这一步做** ——
   它在 `CHAR_complianceParameter` 里,而那个函数在原版是**每回合准备阶段**逐角色重算三围时调的
   (`05` §2.3 第 4 件事 = `BATTLE_TurnParam`,**未移植**)。
   ⚠️ 这条**替换掉了** M.2/M.3 期间记的旧理由(「四维无源 ⇒ max_hp 恒 0 ⇒ 夹取 = 叫出即死」)——

⚠️★★ **一条只有接上真实模板才会显形的性质**:`Df_HpPer = 10 − HP²/MaxHp`

### 2.13 DR-DT12 —— 敌人表 `enemy1.txt`:等级摇号、归一位置与四处"名字在骗人"(批次 M.5)

本条裁定的是 M.4b 明确留下的两个入参(`level` / `capturable`)的来源表,
以及移植它时撞出的四处**名实不符** —— 后者比公式本身更值钱,因为它们都是
「照着名字转述就会记错」的形态,而本项目已在这一类上栽过五次。

#### ① ★★ `enemy1.txt` 不是 `enemy.txt` —— 差一列,整表错位

`setup.cf` 的 `enemyfile` 指向 **`enemy1.txt`(34 列 = 3 char + 31 int,实测 2154 行)**。
同目录并存的 `enemy.txt`(33 列 / 1494 行)是**宏关闭时代的旧数据**。

判据:`ENEMY_STARTINTNUM` 在 `_BATTLENPC_WARP_PLAYER` 开启时是 **4**
(展开视图 `char/enemy.c:458`),而 `include/version.h:103` 该宏**已定义**
⇒ 多一列 `ENEMY_ACT_CONDITION`。`stoneage-plan/docs/05` §3.1 称这一对新旧文件是
「宏状态的天然标尺」。

⚠️★ **拿错文件的后果不是"少一列"而是"从第 3 列起全表错位"**:
`enemy.txt` 的 c3 是 `ENEMY_ID`,`enemy1.txt` 的 c3 是 `ENEMY_ACT_CONDITION`
⇒ 所有 int 列各错一位,而**每一列都还是个合法整数** ⇒ 不会有任何解析错误。
★ 本条落地时先按 `enemy.txt` 量过一遍分布,数字全都"看起来合理"(`min > max` 占 60%),
换成正确的 `enemy1.txt` 后**那 60% 变成 0%** —— ⇒ 结论完全相反。

#### ② 裁定:等级 = `baselevel > 0 ? baselevel : RAND(LV_MIN, LV_MAX)`,**两支都是原版**

源码 `:1030-1035`。⇒ M.4b 的"等级是入参"**不是权宜**,它就是前一支。
★ 而**分流靠一个局部变量的初值**,这一点值得记准:`battle.c:2178` 声明
`baselevel = 0`,**只有 NPC 触发那一支才赋值**(`:2225` 取 `CHAR_getInt(npcindex, CHAR_LV)`),
两支最后统一传入 `:2250` ⇒ 野外遇敌(`:2228` 的 `npcindex == -1`)一路保持 0 ⇒ 走摇号。
⚠️ 所以"谁决定等级"在源码里**不是一个显式的参数选择**,是初值 + 一处条件赋值
⇒ 只读 `ENEMY_createEnemy` 看不出这件事,必须回到调用方。

⇒ **照抄,不改成两个入口**。⚠️ 把它拆成 `spawnEnemy` + `spawnEnemyAtLevel` 会把原版的
一个 `if/else` 变成调用方的选择,而调用方(将来的刷怪)本来就是按这个条件分流的。

#### ③ ★★ 载入期两条归一:实测**一次都不触发**,但仍然移植 —— 判据不是"照抄"

源码 `:479-486`(载入期,写回表):

```c
if( lv_min == 0 ) lv_min = lv_max;              // ① 0 ⇒ 固定为 max
ENEMY_setInt(i, ENEMY_LV_MIN, min(lv_min, lv_max));   // ② 写反了自动纠正
ENEMY_setInt(i, ENEMY_LV_MAX, max(lv_min, lv_max));
```

实测 `enemy1.txt` 2154 行:`lv_min == 0` **0 行** · `lv_min > lv_max` **0 行**
⇒ 两条都是**在 8.0 投产数据上永不执行**的防御性代码。

★★ **裁定移植,而判据是第三条**:`Rules::Random::rand` 的接口契约写明
「`lo > hi` 时的行为由实现定义,调用方须自行保证 `lo <= hi`」

### 2.14 DR-BT23 —— 随机源在退化区间上的消耗语义,以及它为什么三个批次没被发现(批次 R.1)

> **本条的裁定只有一行(「照常消耗」),而值得读的是后面四节 ——
> 一个横跨三个批次、影响 25 个调用点的偏差,在 3,300+ 条断言下全绿。**

#### ① 事实:原版那个"笨拙"的宏形式恰好定义了退化区间

```c
#define RAND(x,y)  ((x-1)+1 + (int)((double)(y-(x-1))*rand()/(RAND_MAX+1.0)))
```

| 输入 | `y-(x-1)` | 取整结果 | 返回 | 是否消耗 `rand()` |
|---|---|---|---|---|
| `RAND(5,9)` | 5 | `[0,5)` | 5..9 | ✅ |
| **`RAND(5,5)`** | **1** | `[0,1)` ⇒ **0** | **5** | ✅ |
| **`RAND(0,-1)`** | **0** | `0.0` ⇒ **0** | **0** | ✅ |

★★ **两个退化情形都是有定义的,不是 UB** —— 我最初判为「原版自己踩 UB」,复核宏展开后**推翻了这个判断**。
⚠️ 而 `rand()` 是那个乘法的**操作数**:C 不允许因系数为 0 而消除有副作用的调用
⇒ **系数是 0 也要求值** ⇒ 原版在退化区间上照样消耗一次。

#### ② 我方的分叉:同一接口两个实现,而只有一个是对的

| 实现 | 用途 | `rand(n,n)` | 一致性 |
|---|---|---|---|
| `ScriptedRandom`(tests) | 全部用例 | **先取数**再钳制 ⇒ 消耗 | ✅ 与原版一致 |
| `SeededRandom`(shared) | **生产 + 回放** | `if (hi <= lo) return lo;` ⇒ **不消耗** | ❌ |

⇒ ★★ **偏差只存在于生产实现,而验证只走测试实现** ⇒ 结构性盲区。
⚠️ `randMod` 上两边**都**不对齐(`n <= 0` 各自早退),只是当前无 `randMod(0)` 调用点。

#### ③ 实测规模:不是边缘情况

| 调用点 | 命中退化的条件 | 实测 |
|---|---|---|
| `rand(attack_num_min, attack_num_max)`(攻击次数) | 上下限相等 | ⚠️ 用例里 3 处 fixture **全部相等**(2/2 · 0/0 · 30/30);真实配置里攻击次数固定是常态 |
| `rand(lv_min, lv_max)`(M.5 敌人等级) | 两列相等 | ⚠️★ **1142/2154 = 53.0%**(`enemy1.txt`) |
| `rand(0, r_max)`(本批遇敌组编组抽签) | 权重和为 0 ⇒ `r_max = −1` | `group1.txt` **4 行**,其中 **3 行被 `encount.txt` 引用 ⇒ 可达** |
| `rand(0, attack×kD16)` / `rand(0, quick×ratio)` | 乘积截断为 0 | 低等级单位 |

⇒ 25 个调用点里**至少 6 个**会命中。

#### ④ ★★★ 为什么它能全绿 —— 本条最该被读的一节

改对之后重跑:**`ctest` 15/15,3,300+ 断言一条都没红。**
⚠️ 而原因**不是**「断言不敏感」(那是 M.5 ⑤ 那一族),是更根本的一层:

> **用例集从未触及那个实现。** 期望值一直是按「消耗」算出来的(`ScriptedRandom` 的语义),
> 生产实现偷偷少消耗一次 ⇒ ★ **「黄金用例集 = 生产行为的保证」这个前提,在这一点上是假的。**

★ 而 `RulesProgressionTest` 当时(批次 M.4a)就写下了这句注释:

> ★ 消费次数是**可回放性的一部分**,不只是调试信息:多摇或少摇一次,
>   同种子下后续所有取值全错位,而没有任何一处报错。

⇒ ★★ **认识早就有了,缺的是把它作用到生产实现上的那条断言。**
⚠️ 这与 M.5 ⑦(三条 DR 只有小节、主表无行)同族:**纪律写下来了,而没有任何东西会失败**。

#### ⑤ 连带影响:M.5 两条归一的理由要改口径(★ 逻辑不动,而三处代码注释必须改)

M.5 把载入期归一的判据写成「`Rules::Random::rand` 的契约把 `lo<=hi` 交给调用方
⇒ 不移植就是给自己开 UB 入口」。⚠️ **那个理由现在失效了**(退化区间已有定义)。
⇒ ★ 但**归一本身仍然必须移植**,理由换成更硬的一条:**原版在载入期就做了**

⚠️★★ **本条初稿写「但代码不动」,那是错的**:逻辑不动,而那个失效理由**写在三处注释里**

#### ⑥ 处置与判据

#### ④ ★★★ 两处「等价写法」,以及我为它们编造的理由

抽签那一行里有两处细节,我在注释与用例里都把它们当成**行为判据**:

```c
for (i = 0; i < found - 1; i++) {           /* ← 上界是 found-1,不是 found */
    aaa += wr[i];
    if (wr[i] != 0 && r < aaa) break;       /* ← 多了半个 wr[i] != 0 */
}
```

⚠️ 反向验证:注入「上界改 `found`」与「删掉 `wr[i] != 0`」——**各 0 条转红**。
⇒ 穷举验证(1..4 槽 × 权重 {−1,0,1,2,3} × `r` 遍历 `[0, Σ−1]`,共 **2,580 组**):
**两处各自改掉、以及同时改掉,结果差异均为 0 组。**

| 细节 | 为什么等价 |
|---|---|
| 上界 `found - 1` | `r <= Σ−1 < acc(最后一个)` ⇒ 最后一个候选**必然**命中 ⇒ 让它进循环与兜底给它,结果相同 |
| `wr[i] != 0` | 权重 0 的槽不让 `acc` 增长 ⇒ 「选中它」等价于 `r < acc_prev`,而那个条件在前一轮就已 `break`;`i == 0` 那种情形要求 `r < 0`,而 `r >= 0` 恒成立 ⇒ **冗余** |

⚠️★★ **而我的注释原文是**:「`w != 0` 那半个条件要紧:**权重 0 的槽不该被选中**,少了它会选中它」
—— **那句话是错的**,用例也据此写了一条**没有区分力**的断言。

⇒ ★★★ **这是同一族教训的第三次**:
· §9.0.35 ⑤ ——「数据的形状」掩盖错误(手填 `hp=1` 让捕获的二次式性质从未暴露);
· §9.0.36 ⑥ ——「断言的形状」没有区分力(`calls()` 数的是调用次数不是取数次数);
· **本条 —— 我给照抄的代码编造了一个「它很要紧」的理由,而反向验证揭穿了它。**

★ 三次的共同结构:**我倾向于把"我不理解为什么这么写"补完成"它一定有理由"**,
而那个补出来的理由**不经检验**。⇒ 处置不是删掉那两行(它们是源码原文,照抄没错),
而是**把注释改成"实测等价,照抄但不声称要紧"**,并让用例明说它守的是**性质**而不是那个条件。
⚠️ **别再给冗余分支补断言** —— 冗余的分支没有能区分它的输入。

### 3.1 逐条裁定理由


#### DR-BT1 — 照抄(空手连击各段全额)

**量化**:`LUCK` 上限 25 ⇒ `luckwork = 25`,触发分布为
`≤35` → `RAND(5,10)`(3.5%)· `≤55` → 3 段(2.0%)· `≤95` → 2 段(4.0%)· 否则 1 段(90.5%)
⇒ **期望段数 = 1.31**。空手无武器攻击力加成,1.31 倍不足以反超武器。

⇒ `05` §9-1 "空手在高幸运下强于武器"**在数值上不成立**,除非武器攻击力加成 < 31%。

★ **决定性依据**:拳套走 `gDamageDiv = attack_max`(总伤不变、分摊到多段),空手保持 1.0。
**拳套那行是显式添加的补丁** —— 若开发者认为多段都该分摊,不会只为拳套写一行。
⇒ 空手保持 1.0 是**差别对待**,不是忘了写。

⇒ 保留。它给「幸运」一个独特用途,符合「玩法自洽」的定位。
⚠️ 留配置开关,上线后实测失衡可关 —— 但**默认按原版**。

#### DR-BT2 — 修正(骑宠分摊)

原式:`playerdamage = damage · petDef / (myDef + petDef) + 1`

`petDef` 在**分子** ⇒ 宠物防御越高,主人吃得越多。这**反向惩罚了「培养骑宠」**:
玩家把骑宠练得越强,自己越脆。骑宠是核心养成路径,没有任何设计意图能解释这个反向激励。

⇒ 改为 `playerdamage = damage · myDef / (myDef + petDef)`
(**防御高者多扛** ⇒ 练宠有回报),并改**无损分摊**:`petdamage = damage − playerdamage`,
总和恒等于 `damage`;若某侧分到 0 而 `damage ≥ 1`,保底 1 并从另一侧扣除。

⚠️ **文档口径存疑,实现期须核源码**:`05` §3.6 写 `petdamage = damage − playerdamage + 1`。
若 `playerdamage` 已含 `+1`,总和是 `damage + 1` 而非 `05` §9-2 所称的 `+2`。
**多 1 还是多 2 不影响本裁定**(两者都归零),但需在移植时核对。

★ 连带:客户端 **DR-UX8**(若照抄则 UI 不做误导性提示)**随本条作废** —— 修正后无反直觉可提示。

#### DR-BT3 — 照抄(战斗指令不耗 MP)

名义成本(逃跑 20 / 捕获 20 / 换宠 10 / 宠技 10 / 普攻 5 / 防御 2)全部**不生效**,
`SSRC80` 与 8.5 **完全相同的 `#if 1` 短路**。

三条理由,任一单独成立:

1. ★ **两代一致 ⇒ 是稳定的产物形态,不是某版的临时调试。** 8.0 玩家实际体验就是"指令免费";
2. ★ **`csa8.0` 的咒术 MP 数值(`ITEM_MAGICUSEMP`)是在"指令免费"前提下配平的。**
   恢复指令消耗 = 全套咒术成本立刻失衡,而重新配平需要 **120 个技能的逐条数值**
   (`05` 欠债 1,5–8 天,**尚未做**)⇒ 修正的真实代价远大于表面;
3. 与已裁定的 **DR-BT9**(`@` 纯回 MP 不迁移)自洽:指令既然免费,就不需要白给回 MP 的指令。

⇒ **MP 的定位固定为「施法资源」,不是通用行动力。** 这个定位清晰且自洽。

⚠️★ **名义 MP 成本不得写进代码**。它们在原版是死数据,写进去会让后人误以为生效。
若将来要开启,按**新设计**重新配平,不复活这批数字。

#### DR-BT4 — 修正(补齐 31..43 的抵抗)

涉及 13 种:31 三属抗 · 32 水附体 · 33 附身 · 34 恐惧 · 35–43 冰爆术 2–10。

★ **决定性依据 —— 三张表长度各不相同**:
