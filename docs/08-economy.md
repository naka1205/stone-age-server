## 0. 三句话

> ★ **① 石币不是一个字段,是 5 个并存的载体、4 个不同上限。「玩家有多少钱」在 8.0 里没有单一真值。**
>
> ★ **② 8.0 没有「金钱变更」这个领域操作,只有「往一个 int 字段写值」** ——
> 96 个写点里 **60 个(62.5%)绕过**唯一带上限与余额检查的 API。
>
> ★ **③ 8.0 的石币经济是净回收型的,但净回收是靠上限压出来的,不是靠设计压出来的。**
> 上限一调高(8.5 把随身兜底从 100 万改成 1 亿,**100 倍**),这套结构立刻变成净增发。

### 0.1 净流向的三条结构性判据

## 2. 石币的五个载体

| 载体 | 语义 | 上限常量 | 8.0 值 |
|---|---|---|---:|
| `GOLD` | 随身 | `CHAR_getMaxHaveGold()` | ★ **公式,见 §2.1** |
| `BANKGOLD` | 家族银行·**个人**帐户 | `CHAR_MAXBANKGOLDHAVE` | 10,000,000 |
| `PERSONAGOLD` | 赌场个人银行(「宝箱」) | `CHAR_MAXPERSONAGOLD` | 50,000,000 |
| `FMBANKGOLD` | 家族银行·**家族公款** | `CHAR_MAXFMBANKGOLDHAVE` | 100,000,000 |
| `AUCGOLD` | 拍卖所得待领 | — | ★ **8.0 有 0 个写点 ⇒ 死字段** |

**写点分布实测**:`GOLD` 86 处、`BANKGOLD` 7、`PERSONAGOLD` 3、`FMBANKGOLD` 2、**`AUCGOLD` 0**。

⚠️ ★ **合并成一个 `balance` 前必须先决定 4 个上限怎么合并** —— 直接相加得 1.6 亿,
远超 8.0 任何单一上限。

★ **`PERSONAGOLD`(赌场宝箱)是 8.0 里唯一与「点数」形态接近的东西**:
独立余额、独立上限、独立存取窗口 —— **但它用的是石币,不是点数**(§7)。

### 2.1 ★★ 随身上限:两代公式完全不同

```c
/* 8.0 —— 线性 */
MaxGold = 1000000 + trans * 1800000;

/* 8.5 —— 阶梯 */
switch(trans){ case 0:1e6; case 1:2e6; case 2:5e6; case 3:1e7; case 4:5e7; default:1e8; }
```

| | 0 转 | 1 转 | 2 转 | 3 转 | 4 转 | **5 转** |
|---|---:|---:|---:|---:|---:|---:|
| **8.0(线性)** | 100 万 | 280 万 | 460 万 | 640 万 | 820 万 | **1,000 万** |
| 8.5(阶梯) | 100 万 | 200 万 | 500 万 | 1,000 万 | 5,000 万 | 10,000 万 |

⚠️ ★ **兜底常量也差 100 倍**:`CHAR_MAXGOLDHAVE` 8.0 = 100 万、8.5 = 1 亿。
⇒ **照抄 8.5 会把 8.0 的经济压力整个抹掉。**

★ **一条印证**:`csa8.0/data/itemset6.txt` 有三件石币袋道具
(十万 / 百万 / **千万**石币),而 **8.0 五转上限恰好 = 10,000,000**
⇒ **这三件道具是照着 8.0 的线性公式设计的,不是随手填的数。**
⚠️ 非五转玩家使用「千万石币」,**超出部分静默销毁**。

## 3. ★★ `GoldLedger`:唯一入口,三步不可拆

### 3.1 原版的形状

| API | 上限截断 | 溢出转宝箱 | 余额不足即拒 | 写审计 |
|---|:-:|:-:|:-:|:-:|
| `CHAR_AddGold` | ✅ | ✅ 转 `PERSONAGOLD` | — | ✅ |
| `CHAR_DelGold` | ✅ | — | ✅ 返回 0 | ❌ |

**写点惯用法分布(8.0,96 处)**:

```
CHAR_setInt(裸写)      58   ← 60.4%  ┐
->data[](结构体裸写)    2   ←  2.1%  ├ 合�� 60 / 96 = 62.5% 绕过 API
CHAR_DelGold           24   ← 25.0%  ┘
CHAR_AddGold           12   ← 12.5%
```

⇒ ★★ **审计、上限、溢出、日志四件事各写各的,靠 60 个调用点自觉。**

★ **溢出语义是「转存」不是「销毁」**:超出随身上限的部分进宝箱,并写一条审计。
⚠️ **但只有走 API 的 12 个源享受这个待遇**;18 个绕过点一律是直接钳位(销毁)。

### 3.2 新形状

```
GoldLedger::apply(subject, carrier, delta, reason, ctx) -> Result
    ① 钳位        按该载体的上限
    ② 溢出处置    转存 / 拒绝 / 销毁 —— ★ 由 reason 决定,不由调用点自选
    ③ 写审计      ★ 带 corr_id + 变更前后余额
```

★ **三步不可拆**,且**任何石币变更只能经这一个入口**。

⚠️ **`reason` 不是日志字符串,是枚举** —— 它同时决定溢出处置策略。
这样"任务给钱转宝箱、交易超上限拒绝、GM 设定不检查"这三种语义
就成了**显式的三个枚举值**,而不是三段各自为政的代码。

### 3.3 为什么必须是唯一入口

`12` §5.2 的 18 个绕过点(8.0 生效 16 个),**共同缺少三件事**:
溢出转宝箱、审计、统一的上限判据。

★ **新实现的第一条不变式**:
**任何石币变更只能经唯一入口,且入口必须同时完成「钳位 → 溢出处置 → 写审计」三步。**

### 5.2 ★★ 一处"读代码会得出错误经济结论"的典型

```c
CHAR_DropMoney(charaindex, CHAR_getInt(charaindex, CHAR_GOLD) / 2);
CHAR_setInt(charaindex, CHAR_GOLD, 0);          /* ★ 掉一半,却清全部 */
```

意图显然是"死亡掉一半",实现是"掉一半在地上、剩下一半凭空销毁"。

★ **但它在两代里都不可达**:唯一取这个函数指针的地方**把指针取出后从不调用**,
只把 HP 设为 1 并记一条作弊日志。

⇒ ★★ **8.0 玩家死亡不掉石币、也不销毁石币。**
⚠️ **若照搬这段逻辑,会凭空多出一个巨大的石币汇。**

### 5.3 另两处清零

| 位置 | 行为 |
|---|---|
| 答题 NPC | ★ **余额不足时清零而不是拒绝**:`if (stone - cost < 0) 设为 0;` |
| 房屋管理员 | ★ 结算流程里**无条件清零** |

### 5.4 ★★ 反作弊纠正 = 没收全部石币,且不可追溯

```c
if (money > MaxGold) {
    CHAR_setInt(charaindex, CHAR_GOLD, 0);
    print("\n ERR: ... dropMoney%d > CHAR_MAXGOLDHAVE !!", ...);
}
```

⇒ 只要玩家石币**曾经超过上限**(§4.2 的第三条路径就能做到)且触发一次丢钱,
**全部石币归零**,且 ★ **只 `print` 不写石币日志** ⇒ **事后不可追溯**;
而 `print` 的目标是每次启动清空的进程日志 ⇒ **重启即丢**。

### 5.5 不经字段的两个汇

扫石币字段扫不到,但是真实的经济漏损:

| 机制 | 配置 | csa8.0 |
|---|---|---:|
| **地面石币定时删除** | `Golddeletetime`(秒) | **300** |
| **地图清场** | 按层清理石币对象 | — |

★ 地面石币在 8.0 里**只由丢弃产生** ⇒ **拾取是转移不是增发**,
**真正的净漏损点是这两个删除器**(`StoneAge8.0` = 1800 s、8.5 = 30 s,差 60 倍)。

## 6. 交易结算:两侧都要工作单元

`12` §5.3 / `04-storage-schema.md` §5.1:

```c
if (DelItem(me, ...) == -1) return FALSE;      /* ① */
... 共 6 步「移除」...
if (AddItem(me, MeItem) == FALSE) return FALSE;/* ⑦ */
... 共 4 步「加入」...
```

★ **10 步顺序结算 + 零回滚**:任一步失败即返回,**已经移除的道具/宠物/石币不归还**。
调用者也不补偿。★ **B80 里四个相关符号全部存在 ⇒ 8.0 投产就是这个实现。**

**两处石币侧的具体缺陷**:

| 位置 | 缺陷 |
|---|---|
| 扣款 | ★ 余额越界时**先把钳位值写回再返回失败** —— **失败路径也改了状态** |
| 加款 | ★ 钳到上限,**不像 `CHAR_AddGold` 那样转存宝箱** ⇒ **交易超上限的石币静默销毁** |

⇒ ★★ **这与存储侧的事务缺失是两个独立问题,加数据库事务解决不了它。**
**`world` 进程内也需要工作单元边界。**

### 6.1 三处超上限即静默销毁

偷窃 / 交易 / 任务 `AddGold2` —— 三处都是钳位后直接写回,
**既不转宝箱也不留在原处** ⇒ **石币从世界上消失且无日志**。

## 8. 审计事件模型

### 8.1 8.0 的日志面

```
SSRC80 枚举   28 条   (8.5 是 27 条,且漏列一条)
被宏关掉       4 条
★ 生效        24 条   ← 与 B80 里 24 个 Log* 外部函数一致
```

★ **`csa8.0/gmsv/log/` 的 23 个产物文件是一份独立于源码的门控 oracle**:

⚠️ 附带发现:`log.cf` 里有一条**死配置** —— 键名在日志配置表里根本不存在,整行被静默忽略。

### 8.2 新实现必须保留的事件

| 事件 | 关键字段 | 为什么必须留 |
|---|---|---|
| **石币变动** | 角色 / 账号 / 数量 / 坐标 / **前后余额** | 唯一能追石币的流水 |
| **个人银行存取** | + 事由 / 随身余额 / 宝箱余额 | ★ 溢出转存也走它 |
| **家族银行存取** | 家族 / 角色 / 金额 / 余额 | 家族公款 |
| **交易** | ★ 现状是**拼字符串,不可解析** ⇒ 必须结构化 | |
| **道具变动** | 角色 / 道具 / 唯一码 / 数量 / 坐标 | 与石币等价的资产 |
| **宠物变动 / 转移 / 喂养** | 宠物唯一码 / 等级 / 属性 | 高价值资产 |
| **摆摊成交** | 买卖双方 / 价格 / 标的 | 唯一的 C2C 成交流水 |
| **赌博** | 玩家 / 下注 / 结果 | 风控入口 |
| **庄园奖金 / 声望商店** | 家族 / 气势 / 金额 / 去向 | ★ 唯一的**凭空增发**流水 |
| **GM 操作** | GM / 目标 / 指令 | ★ 三个 GM 增发口全靠它 |
| 杀怪 / 死亡 / 转生 / 登录 | — | 关联分析用 |

### 8.3 ★ 现状的三个结构性缺口

```
① 无 correlation id —— 一次交易在三个日志文件里是三条互不关联的行,事后无法重建
② 交易日志是 sprintf 拼串,不是结构化字段
③ ★★ 5 个「直接清零」写点与 18 个绕过 API 的增发口,一条日志都不写;
   反作弊没收只 print 到每次启动清空的日志 ⇒ 重启即丢
```

⇒ **新实现的审计要求**:
**一次业务操作 = 一个事务 = 一条带 `corr_id` 的结构化事件;
资产变更事件必须携带变更前后余额。**

★ 8.0 的银行日志**已经带前后余额了**,其字段设计可直接沿用。

表结构见 `04-storage-schema.md` §9。
