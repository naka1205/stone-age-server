## 1. ★★ 经验曲线:两条并行路径,不是替换关系

`08` §2.1 结案:

| 路径 | 谁提供 | 入口 |
|---|---|---|
| **「升到 L 级要多少经验」** | ★ **数据表 `exp.txt`** | `CHAR_GetLevelExp()` |
| **「等级上限是多少」** | ★ 三条并存路径,见 §3 | `CHAR_GetLevel()` / `getMaxLevel()` |
| 旧曲线(仅遗留调用) | 硬编码 `LevelUpTbl[]` | `CHAR_GetOldLevelExp()` |

三条独立证据:

1. 两代源码的门控(`_NEWOPEN_MAXEXP` / `_USER_EXP_CF`)**同时为开**;
2. ★ **B80 函数级 oracle**:`getNeedLevelUpTbls` / `CHAR_GetLevelExp` / `LoadEXP` /
   `getEXPfile` 全部命中,且 **`NeedLevelUpTbls` 在 B80 的外部数据符号表里**;
3. `csa8.0/setup.cf:162` `USEREXP=data/exp.txt`,文件存在(2,368 B / 201 数据行)。

### 1.1 ★★ 两条曲线差一个数量级

`exp.txt` 装入的值与 `LevelUpTbl[]` 在 **141 个下标里 138 个不同**:

| 等级 | 硬编码 `LevelUpTbl[]` | ★ 实际生效的 `exp.txt` | 倍数 |
|---:|---:|---:|---:|
| 10 | 1,000 | 344 | 2.9× |
| 20 | 16,000 | 2,968 | 5.4× |
| 40 | 256,000 | 24,656 | 10.4× |
| **60** | **1,296,000** | **84,264** | **15.4×** |
| 100 | 20,000,000 | 1,256,663 | 15.9× |
| **140** | **1,224,160,000** | **70,858,959** | **17.3×** |

⇒ ★ **裁错这一条,整个升级节奏会差一个数量级。**

★ 顺带一条:`exp.txt` 的值与 `char_data.c:1231` **被注释掉的那张 `NeedLevelUpTbls[]`**
逐下标完全一致(161/161)⇒ **`exp.txt` 是那张表 externalize 出来的**,
不是 `LevelUpTbl` 的外置副本。

### 1.2 ★★ `exp.txt` 的三个格式陷阱

装载器**只取第 2 个 token**:

```c
easyGetTokenFromString(line, 2, exp, sizeof(exp));
NeedLevelUpTbls[MaxLevel] = atoi(exp);
```

| # | 陷阱 | 后果 |
|---|---|---|
| 1 | ★ **第 1 列根本不被读** —— 生效的是**行序** | 导出/重建时按第 1 列对齐会错 |
| 2 | ★★ **第 1 列写的值比它实际配置的等级小 1** —— 第 k 个数据行的第 1 列是 `k−1`,却被写进 `NeedLevelUpTbls[k]` | **照第 1 列重建 `exp.txt`,整条曲线平移一级** |
| 3 | ★ 末行 `200 -1` 这个"没有下一级"的哨兵,**两代都读不到就 break 了** | **哨兵在投产里从未生效**,等级上限完全由 §3 决定 |

⚠️ **8.0 装载器有一处越界写**:`int NeedLevelUpTbls[160]` 配 `if (MaxLevel > 160) break;`
⇒ **允许写下标 160(合法 0..159),越界 1 个 int**。8.5 已修(`[200]` 配 `>= 200`)。
★ **照抄 `SSRC80` 的循环条件会复刻这个 bug。**

## 2. 等级上限:三条并存路径,必须分开建模

`08` §2.4:

| 路径 | 来源 | 值 |
|---|---|---:|
| **A** | `MAXLEVEL` 配置项 | **160**(`csa8.0/setup.cf:173`) |
| **B** | `exp.txt` 的行计数(夹取到 160) | 160 |
| **C** | ★ `arraysizeof(LevelUpTbl) − 1`,**两代都写死在源码里** | **140** |

★ **B80 走的是路径 A**(`08` §2.4 的 C5):

```
MAXLEVEL 在 B80 的配置表里         ✅(序号 132;SSRC80 的配置表里没有这个键)
MaxLevel 在 B80 的外部数据符号里   ❌ ⇒ 不是 SSRC80 那个文件级全局
NeedLevelUpTbls 在外部数据符号里   ✅
```

⚠️ ★ **路径 C 的 140 与路径 A 的 160 并存,分别服务不同调用点。**
⇒ **新实现必须把这两条路径分开建模,不能合并成一个「等级上限」。**

### 2.1 一条被 BSS 零值改变语义的配置

`YBLEVEL` 在**三份 `setup.cf` 全都没赋值** ⇒ BSS 零 ⇒ `getYBLevel()` 返回 0
⇒ `level > getYBLevel()` **恒真** ⇒ **转生数检查对所有等级生效**。

★ 这是 `01` §10.2 的"默认值统一模型"(未赋值即 0 / 空串)在玩法上的一个实例:
**一个从未被填的配置,把一条本该分级的规则变成了全局规则。**

## 3. 属性点与宠物成长率

### 3.1 ★ `CHAR_ALLOCPOINT` 的真实语义

```c
vital = (LevelUpPoint >> 24) & 0xFF;
str   = (LevelUpPoint >> 16) & 0xFF;
tgh   = (LevelUpPoint >>  8) & 0xFF;
dex   = (LevelUpPoint >>  0) & 0xFF;
```

★ **不是「玩家可分配的属性点」,是宠物的四维成长率**(GM/Lua 暴露名「对像_成长%」)。

⚠️ **三个并存上限必须逐调用点保留**:

| 场景 | 上限 |
|---|---:|
| 字段容量 | 255 |
| 宠物创建时 | **60** |
| 宠物死亡扣属性时 | **50** |

⇒ 拆成 4 个独立字段时**不能统一成一个上限**(`03-domain-model.md` §6.1)。

### 3.2 ★★ 战斗结算有养成侧副作用

`08` §9.2 给 W1 的移交:`Pet_Check_Die` 会**在战斗内改写 `CHAR_ALLOCPOINT`**
(特定宠物死亡扣四维 + AI 模式扣 5%)。

⇒ ★ **这是 `05-battle.md` §1.2 第 ② 步"把写回剥出去"必须覆盖的一条** ——
战斗结算不只写 HP,还写养成字段。

### 3.3 ★ 一个明确可裁定的精度决策

`enemybase1.txt` **第 9 列 = `E_T_LVUPPOINT`**(宠物四维成长系数),原版用 `atoi` 读:

```
csa8.0 数据包 1,053 行:
  4.50 → 538 行(51.1%),atoi 后 4,损失 −11.1%
  5.50 →  31 行( 2.9%),atoi 后 5,损失  −9.1%
  ★ 小数部分 ≠ 0 合计 569 行 = 54.0%

消费公式 PARAM_CAL = ((level−1) × LVUPPOINT + INITNUM) × 属性系数
★★ 系数被乘以 (level−1) ⇒ 截断不是一次性的 0.5,是每升一级累积
```

★ **11 张主表全扫,只有这一列有小数** ⇒ **这是唯一的一个,不存在悬念**。
⇒ 见 §11 决策 1,以及 `04-storage-schema.md` §7.4。

## 4. 宠物融合

### 4.1 ★ 不是一张表,是三张表串联

```
两只宠的 E_T_FUSIONCODE  →  查 PetTable[29][29]      → base2,取值 0..10
两只宠的属性(地水火风)  →  查 PropertyTable[4][4]   → base1,取值 0..15
                            查 FusionTable[11][16]    → 结果宠 ID
```

**维度自洽性已实测**:`PetTable` 取值集 ⊂ [0,11)、`PropertyTable` 取值集 ⊂ [0,16),**不存在越界**。

⚠️ 但 `PetTable` 的取值集里 **没有 7** ⇒ **`FusionTable` 第 7 行经这条链永远取不到**。

### 4.2 ★ 融合码的覆盖面

`E_T_FUSIONCODE` = `enemybase1.txt` **第 56 列**。实测 1,053 行:

```
-1(不可融合)  617 行
空列(解析器跳过,保持初始 -1)  55 行
⇒ 合计 672 / 1,053 = 63.8% 的宠物模板不参与融合
取值域 [-1, 28],最常见的正值是 28(99 行)
```

### 4.3 ★ 一处 off-by-one(两代逐字相同,不是 8.5 引入)

```c
if (k1 <= 1) table1 = Property1[0];
else         table1 = Property1[ rand() % (k1 - 1) ];   /* ★ 应为 rand() % k1 */
```

`k1` = 属性值 > 0 的个数。取值域是 `0..k1−2` ⇒
★ **最后一个正属性永远选不中**;`k1 == 2` 时 `rand()%1` 恒为 0 ⇒ **完全没有随机性**。

⇒ **双属性宠的第 2 个属性不参与融合判定。** 见 §11 决策 2。

### 4.4 ★ 一份现成的可读副本

`08` §4.8 结案:`csa8.0/gmsv/data/oldfusion.txt` **就是 `FusionTable[11][16]` 的逐元素文本副本**
(11 行 × 16 列,**逐元素比对 176/176 完全相同**),
**两棵源码树零引用、B80 无此字面量** ⇒ **零装载器,不是私服扩展,是导出快照**。

⇒ ★ **迁移时不必处理它,但可以直接当 `FusionTable` 的可读版本用** —— 省掉一半导出工作。

⚠️ 附带一条方法论:**「文件时间戳 2008.3.16」不是"私服自制"的充分判据**。

### 4.5 为什么"逐组合 A+B→C 表"要推到实现期

★ 它不是 176 行的表,而是 **(29×29 融合码对) × (4×4 属性对)** 的投影,
且第 2 跳里带 `rand()` ⇒ ★ **同一对宠可能出不同结果**。
⇒ 产出应是**概率分布表**而非确定映射(`08` §8 待补 2,1.5 天)。
