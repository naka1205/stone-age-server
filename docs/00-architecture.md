### 1.1 D2 的裁定理由与可撤销点

`07` §11.3 五条实测,无一条是软的:

| 判据 | 实测 |
|---|---|
| ① 叶子函数已无副作用 | **20/23** 个 ≤150 行叶子函数零写零 I/O |
| ② 副作用集中 | 122 次写里 **105 次(86%)** 在 2 个函数 |

### 1.2 D1 的裁定理由

D2 采纳后 D1 是被决定的,不是被选择的:GameStudio 是 **C++17**,
C++ 是 `00` §8.3 矩阵里**唯一**能让 L3 一份实现、两端编译的选项。
Rust 可编 WASM 但无法与 C++ 客户端直接共享源码(需 FFI 或双份实现),那正是 D2 要消灭的东西。

**服务端不混用语言**(用户决策)。收益:L2 领域模型与 IDL 生成代码全线复用、单一构建与测试工具链、
"服务"与"库"的边界成为零成本选择(这正是 §4 两种部署形态得以成立的前提)。

⚠️ **与语言无关的附带前提,选了 C++ 也不自动满足**:`15` §9.1 三根支柱
(运行期零分配 / 活对象数常量且几乎无指针图 / 单 tick 只触及 5.4% 槽位)
成立的条件是**保留"扁平数组"的数据布局**。
若把 `Char` 改成"每角色一个堆对象 + `map` 索引",三根支柱全部失效,
只是失效形式从 GC 停顿变成 cache miss 与分配抖动。
⇒ **L2 对外是和类型,底下仍是定长池 + int 下标句柄。两者不冲突,但必须同时成立。**

### 1.3 ★★ 四步改造的真实规模(2026-08-31 实测,排期依据)

> **D2 存续与否看「能不能做」(§1.1),排期看「有多少要做」(本节)。**
> `07` §11.4 的四步量级是在 **26 个函数**上数出来的,**直接拿去排期会严重低估**。

| 步 | W1(普攻链路) | 实测(全闭包 + 全分支) | 放大 |
|---|---|---|---:|
| ① `g*` → 显式参数结构体 | 10 个全局 × 约 40 处引用 | **109 处** / 10 个函数 | **2.7×** |
| ② 写世界状态 → 返回事件 | 1 个函数 / 20 处写 | ★★ **1,047 处** / **167 个函数** | ★★ **52.4×** |
| ③ 串拼装 + 发包 → 事件列表 | 72 处串缓冲 + 44 处 I/O(全在一个函数) | **429 处串缓冲** / 63 函数 + **120 处 I/O** / 39 函数 | **6.0× / 2.7×** |
| ④ `RAND()` → 注入序列 | 166 处 / 2 入口 | 131 处 / 64 函数,**入口仍是 2 个** | **0.8×**(不变) |

★ **第 ② 步是唯一量级失真的一笔**:W1 因只沿普攻链路,把它估成「1 个函数 20 处写」,
实测是 **167 个函数 1,047 处写** —— 因为**每个技能实现函数都自己写状态**。

⚠️ 但**改造的性质未变**:仍是机械替换、不动公式。变的是**份数**,不是**难度**
—— 判据 ①b 已证这 1,047 处写 **100% 经访问器**。

⇒ **`07` §0.5 的四步改造估时须按本表重算。** 第 ④ 步量级不变(0.8× 是因为 W1 的 166
本就是全 `battle/` 目录统计,而 131 是闭包内 ⇒ 闭包覆盖了 79% 的随机点)。

#### 1.3.1 ★★ 重算结果(2026-08-31 晚,`tools/rescope_battle_port.py`)

> **上表的 1,047 是"写点总数",不是"移植工作量"。** 回源码逐点分类后,
> 两条实测把第②步的净规模降下来了 —— ⚠️ **减的是「份数」,不是「难度」。**

**★ 发现 1 —— 指令登记不是世界状态写(327 / 1,047 = 31.2%)**

原版没有 `TurnCommands` 这个类型,它把本回合指令**暂存在角色的 WORK 槽**里,
由 `BATTLE_Battling` 稍后读回来分发:

```c
CHAR_setWorkInt(charaindex, CHAR_WORKBATTLECOM1, com1);    // 指令码
CHAR_setWorkInt(charaindex, CHAR_WORKBATTLECOM2, toNo);    // 目标位次
CHAR_setWorkInt(charaindex, CHAR_WORKBATTLEMODE, BATTLE_CHARMODE_C_OK);
```

⇒ 这是**传参**,不是状态变更。新契约里它就是 `rules::TurnCommands` /
`domain::BattleCommand`(IDL 已落地),是 `ResolveTurn` 的**输入**。
⇒ ★ **第②步净规模 = 720 处,不是 1,047 处。**

⚠️ 口径**故意取窄**:只算 4 个指令槽 + 5 个集气延迟槽;`CHAR_WORKBATTLEINDEX`
(战场归属)、`CHAR_WORKBATTLEFLG`(战斗标志)虽同前缀但是真状态,**不列入**。
宁可高估工作量,不可反过来。

**★ 发现 2 —— 62/64 个职业技能函数不是 64 份实现**

| 类 | 个数 | 形态 | 移植后 |
|---|---:|---|---|
| 同构薄包装 | **53** | `if(toNo>19) toNo=0; profession_common_fun(…, BATTLE_COM_S_X); return TRUE;` 逐字同构,只有指令码常量不同 | **一张 62 行的映射表** |
| 技能指令空实现 | **9** | `{ return TRUE; }` —— 被动技能,效果在攻击序列里(`PROFESSION_weapon_focus` 空,而 `PROFESSION_SKILL_WEAPON_FOCUS_LVEVEL_UP` 有 66 行) | **零**;⚠️ **勿当成「8.0 缺失、需补齐」** |
| 真实现 | **2** | `PROFESSION_escape`(30 行)· `PROFESSION_track`(29 行) | 逐个移植 |

⇒ C 批次 64 个函数的净移植量 = **2 个函数 + 一张表**。唯一实体
`profession_common_fun` 只有 28 行,且它做的正是发现 1 里那件事 —— **指令登记**。

**★ 批次表(可独立交付的切分)**

| 批次 | 函数 | 行数 | ① `g*` | ② 真状态写 | ③ 串缓冲 | ④ 随机点 |

## 2. 分层与硬约束

```
┌──────────────────────────────────────────────────────────────┐
│  L4  内容资产   地图/NPC/道具/数值表/脚本  ← 与代码解耦,可热更  │
├──────────────────────────────────────────────────────────────┤
│  L3  玩法规则   战斗结算 · 属性成长 · 掉落 · 任务             │
│      ★ 纯函数 + 注入式随机源,与客户端共享同一份源码            │
├──────────────────────────────────────────────────────────────┤
│  L2  领域模型   CHAR_TYPE 分派的和类型 + GoldLedger            │
├──────────────────────────────────────────────────────────────┤
│  L1  会话与协议 IDL 生成的编解码 · 连接状态机 · 线路/分片      │
├──────────────────────────────────────────────────────────────┤
│  L0  基础设施   网络 I/O · 存储 · 日志/指标 · 配置 · 节拍调度  │
└──────────────────────────────────────────────────────────────┘
```

各层的硬约束,全部来自实测,违反后果均为**静默错误**(不报错、不崩溃、数据烂掉):

| 层 | 约束 | 出处 |
|---|---|---|
| **L4** | 内容资产入库前必须完成**编码归一** —— 原始数据五态混编,**64 个文件行内就混编码** | `09` 坑 2 |
| **L3** | 纯函数 + 注入式随机源;**166 个随机点只经 2 个入口**,一律换成确定性序列 | `07` §0.5 ④ |
| **L2** | ★ **`CHAR_TYPE` 分派的和类型,不是 693 列宽表**;**65 条别名压在 38 个物理 slot 上**,合并任意两个都是静默错误(`CHAR_CHARM` 魅力在宠物身上叫 `CHAR_MODAI` AI 模式) | `11` §7 C1–C8 |
| **L2** | ★ **`GoldLedger` 单入口**:钳位 → 溢出处置 → 写审计,三步不可拆。石币是 **5 个载体 4 个上限**,原版 96 个写点里 **62.5% 绕过唯一带校验的 API** | `12` §2 / `00` §8.4.3 |
| **L2** | 死字段 80 个(11.5%),其中 37.5% 来自批量预留槽位 ⇒ **不照搬定长槽位数组,改为变长集合** | `11` |
| **L1** | ★ **必须显式赋值每个协议号与窗口类型**,不得沿用"枚举顺序即协议号" —— 那是旧实现两端漂移的根因 | `10` §0.2 结论 C |
| **L1** | 协议自带**长度前缀**(同时满足 TCP 与将来的 WebSocket 消息边界) | 本文 §4.3 |
| **L0** | ★ **必须新增节拍层** —— 8.0 无节流(`_BATTLE_TIME`/`_CHAR_LOOP_TIME` 均关),战斗速度 = tick 频率 | `15` §5.2 |
| **L0** | 重设每连接缓冲 —— 原版每连接 **324–452 KB** 双缓冲,是 `sizeof(Char)`(12.3 KB)的 **26–37 倍**,是每连接成本主项 | `15` §4.3 |
| **L0** | 频道类广播**改订阅制** —— 原版除地图局部广播外全是"全扫 `fdnum`" | `15` §7.3 |

### 2.1 L2 的真实形状(必须写进模型设计)

```
物理 slot 693 个(270 data + 15 string + 24 flg + 374 workint + 10 workchar)
  ├─ slot 复用别名 65 条 / 38 个物理 slot   ← 最严重的 CHAR_NPCWORKINT1 有 9 种含义
  ├─ 死字段 80 个(11.5%),其中 41 个仍占持久化空间
  └─ 持久化边界已在字段级画好:285 个有存档键 / 384 个纯运行时
```

★ **"一张宽 `Char` 表"是 8.0 的实现方式,不是它的领域模型。**
真实的领域模型是 **47 种 `CHAR_TYPE` 共享一个内存池、靠 `CHAR_TYPE` 分派** ——
65 条别名就是这个事实的疤痕。
⚠️ **把运行时字段一起持久化会让存档膨胀 135%**,持久化边界直接沿用原版的字段级划分即可。

## 3. 服务边界

取 `17` §9 **方案 B(两服务,按延迟敏感性切)**,而非按业务名词切。
判据是 `17` §3.2 实测:**7 条"会挂起玩家"的协议全部落在会话与存档一侧**,
社交侧 **39 条一条都不挂起玩家** ⇒ 社交侧可做成完全异步、可重试、最终一致。

| 服务 | 职责域 | 8.0 协议数 | 一致性要求 |
|---|---|---:|---|
| **gateway** | 连接接入 · 路由 · 鉴权握手 | — | 无状态 |
| **game**(分片) | 世界模拟 · L3 规则 · 战斗 · 移动 · NPC | — | 进程内权威 |
| **session-storage** | D1 账号 + D2 存档 + D6 + D7 | 29 | ★ 强一致 · 原子 |
| **social** | D3 家族 + D4 KV/排行 + D5 | 39 | 最终一致 |

⚠️ `17` §9.1 的已知归属难点:**D4 归属两难** —— `DBDeleteEntry*` 参与删角(延迟敏感),
其余 11 条是排行(不敏感)。**裁定:按 `17` §5.5 把 `DBDeleteEntry*` 划归 session-storage。**

**拆解顺序:家族优先**,四条独立证据同向(`17` §9.4):
① 家族占 gmsv↔saac 交互量 **57.5%(8.0)**;
② `channelMember[1000][5][50]` 是最大单项全局(1 MB);
③ AC 读缓冲熔断的传导路径(达 78% 直接拒绝新登录);
④ **42 条家族协议无一挂起玩家、仅 3 条带续体** = 规模最大 + 风险最低。

### 3.1 服务间接口(两种拓扑共用的唯一形状)

```
Request / Response(72 条):
    rpc <Op>(Req) returns (Resp)
    Req  必带:{ instance_id, generation, request_id, deadline_ms }
    Resp 必带:{ request_id, status, error_code }
    ⚠️ 不再用「按连接顺序对齐」——原版靠单 TCP 长连接 + 单线程 saac 隐式对齐,
       拆分后该前提消失。实际需显式关联的是 72 条,不是 49 条(17 §7.4)

Notify(34 条,fire-and-forget):
    rpc <Op>(Event) returns (Ack{accepted})
    ⚠️ 「accepted」只代表入队,不代表持久化
    ★★ 资产类操作**不得**走这条路(见 §6)
```

> ★★ **本节是 §4 两种部署形态的支点,违反它生产必挂:**
> **进程内形态下,服务之间只能通过上述接口通信,不得有共享内存捷径。**
> 本地传输只是 `ITransport` 的一个实现,不是"可以直接读对方内部状态"的许可。
> ⇒ **做成编译期约束**:各模块互相不可见,只暴露接口头,链接期换实现。
> 一旦有人在单容器形态下写了"反正同进程,直接读 social 的 map",
> 生产分布式形态就会以最难查的方式崩掉。

## 4. 部署形态

### 4.1 生产:分布式

```
  ┌─────────┐   ┌─────────┐        gateway 可多实例,无状态
  │ gateway │ … │ gateway │        TCP 接入 + 路由
  └────┬────┘   └────┬────┘
       │             │
  ┌────▼────┐   ┌────▼────┐        game 按线路分片
  │ game #1 │ … │ game #N │        每实例 ~305MB,扁平池不变
  └────┬────┘   └────┬────┘
       └──────┬──────┘
    ┌─────────▼────────┐  ┌──────────┐
    │ session-storage  │  │  social  │  ★ 家族最先具备独立扩容
    └─────────┬────────┘  └────┬─────┘
              └────────┬───────┘
         ┌─────────────▼─────┐  ┌──────────────┐
         │  MySQL 8.4.8      │  │ Redis 8.6.2  │
         │  状态真相          │  │ 锁 / 路由 / 排行 │
         └───────────────────┘  └──────────────┘
```

### 4.2 测试:单容器

```
  ┌──────────────────────────────────────────┐
  │ 一个二进制 · 配置决定装载哪些模块          │  ← 与生产同一份代码
  │ gateway + game×1 + session-storage        │  ← ITransport = 进程内实现
  │           + social                        │  ← ILock  = Redis 实现(不换!)
  └───────────────────┬──────────────────────┘
                      │
        外部容器: MySQL 8.4.8 + Redis 8.6.2
```

**单二进制 + 配置装载**,不用 supervisor 跑多进程 ——
单容器形态的目的是"一条命令起一套完整环境",多进程会把它变成一个小型编排问题。

⚠️ **测试环境不得省掉 Redis。** 省掉会造成最坏的一种情况:
**测试环境跑通、生产挂** —— 而本项目没有任何行为验证手段来接住它(§0)。

### 4.3 分片策略:按线路

**这不是新发明,是原版形态。** `17` §C 实测 8.0 的 saac 是**四通信面枢纽**:
除 saacproto 外还有 **LS 上锁服务器**(6 条 `SA*` 协议,**跨 saac 全局账号锁**)
与 **OAC 跨星球**(4 条 `OAC*` 协议)。
⇒ **8.0 原版就是多分区多实例架构,账号鉴权本来就是独立进程。**
`17` 原话:"R2 要拆的账号服务有先例;做多分区/多星球时 LS 与 OAC 是现成参考设计"。

**分片单位 = 线路(game 实例)**,每实例持有全部静态世界数据 + 自己那批玩家。
与 `15` §9.1 三根支柱**完全相容** —— 每实例内部仍是扁平数组、运行期零分配、单 tick 触及 5.4%。
实测每实例 **305 MB**(100 玩家档);按 700 / 1,000 玩家档,**每 fd 内存随规模下降**
(3.65 → 2.45 MB),因为主体是不随玩家增长的世界数据。
⇒ **分布式没有动摇容量结论,只是把它复制了 N 份。**

★ 连带影响:`00` §10.2 中"saac 侧 3 个 8.0 独有子系统"里的**跨线路聊天室(506 行)**
正是原版为该拓扑准备的跨分片通信面 ⇒ **它不是玩法长尾,是拓扑的一部分**(见 §7)。

### 4.4 服务发现

**暂不引入**(consul / etcd 之类):静态配置 + DNS 即可。
实例数量在可预见期内是个位数,引入服务发现是拿真实的运维复杂度去换一个还不存在的问题。

## 5. 存储与外部依赖

| 项 | 定 |
|---|---|
| 关系库 | **MySQL 8.4.8 · InnoDB · `REPEATABLE READ`** |
| 字符集 | ★ **`utf8mb4` / `utf8mb4_0900_ai_ci`,库级强制** |
| 角色档 | ★ **JSON 列 + 生成列索引**,不引入文档库 |
| 客户端库 | **Connector/C++ 8.4,JDBC 风格 API(3306 经典协议)**,不用 X DevAPI |
| 认证 | ★ **`caching_sha2_password` + TLS** |
| 缓存与锁 | **Redis 8.6.2** —— 分布式锁 · 跨分片路由 · 排行 ZSET |

**MySQL 与证据相容,甚至更贴近原版**:`17` 实测 8.0 的 saac 走 **ODBC**
(壳导入表有 `ODBC32.DLL` + `SQLAllocConnect`),`csadb.mdb` 仅 74 KB ——
原版本来就是"关系库 + 一张表"。`17` §9.2 中方案 C 的"需要分布式事务 = 0(单库事务)"
在 InnoDB 上直接成立,**12 条"必须原子"里的 9 条**由此自动解决。

⚠️ **8.4 的一处硬差异**:**默认不再启用 `mysql_native_password`**(降为需显式加载的组件)
⇒ 旧版 C/C++ 客户端库连不上。**Connector/C++ 必须取 8.4 线**,
且需配 TLS 或 RSA 公钥交换才能完成 `caching_sha2_password` 首次认证。
**这一点极易在联调第一天被误诊成网络问题。**

⚠️ **字符集不是例行公事**:`09` 实测原始内容数据**五态混编、64 个文件行内就混编码**
(EUC-JP 被当 Big5 再繁转简的双重乱码链)。
决策 ② 保证新库从第一天就干净,但 **L4 导入管线必须在入库前完成编码归一** ——
让任何一条乱码串进库,后面就再也分不清是数据本身还是转换错误。

**Redis 是生产必需,不是可选项。** 理由是实测而非惯例:8.0 的账号锁是**纯进程内存 256 桶哈希链**,
且 **42 条家族协议完全无锁**,今天不出事靠的是"saac 单线程隐式串行"。
**多实例一上,该隐式保证立刻消失**,而它保护的正是 `17` §5 那 12 条零事务保护的必须原子操作。

**待在服务器上核实(本文不替代实测)**:① X Plugin(33060)是否启用;② MySQL 是否已配 TLS。

## 6. 一致性账单

`17` 实测的缺口,在单进程下部分被隐式串行掩盖,**分布式后全部暴露**。这是本架构最贵的一部分:

| 缺口 | 实测 | 必须做 |
|---|---|---|
| 12 个"必须原子"操作,有保护的 **0** 个 | `17` §5 | 单库内走 InnoDB 事务(9 条);跨服务走 Saga |
| **角色删除横跨 3 个职责域,且不等第 1 条结果**(密码错 ⇒ 角色还在但决斗点与名片簿已删) | `17` §5.5 | **Saga + 补偿**,删存档成功后才删派生数据 |
| 公共仓库 **fire-and-forget 后立刻销毁本地道具对象** ⇒ 道具永久蒸发 | `17` §5.4 | ★★ **资产移动一律"预留 → 提交"两阶段,禁走 Notify** |
| 点数**读-改-写两条独立 SQL**,全用绝对值写 | `17` §5.6 | **原子增量或 CAS** |
| `charSave` **先解锁后写盘**(写盘失败 ⇒ 锁已放、新档未写、进度永久丢失) | `17` §5 | 写盘成功后才释放锁 |
| **72 条**需显式请求关联(不是 49 条) | `17` §7.4 | 全部带 `request_id`,不靠连接顺序对齐 |
| ★ **`SERVSTATE_init()` 把 fdid 归零** ⇒ 重启后迟到应答可能命中新连接 | `17` §E | 续体带 **(实例 ID, 世代号, 请求 ID)** 三元组 |
| 星系移民锁守卫字面量写错(4 处里错 1 处)⇒ **移民锁会被当普通锁删掉** | `17` §F | 新实现不复刻;锁语义显式建模 |

⚠️ **`trade.c:975 TRADE_HandleTrade` 是 10 步顺序结算 + 零回滚**,任一步失败就把已扣的

(`12` §W6)。⇒ **gmsv 进程内也需要工作单元(unit of work)边界。两侧都要做。**

⚠️ 倒数第二条在多实例下危害成倍放大,且它是从原版实测挖出的**真实故障模式**,不是理论风险。

### 9.0.3 ★★ 0.1 的产物形态 —— 一遍到位,不做中间态(2026-08-31 裁定)

### 9.0.6 ★★ 跨编译器验证 —— 在 mac 上关掉 MSVC 的两类风险(2026-09-02)

> **§9.0.5 把「跨工具链」整个记成一笔未知。拆开看,它其实是三类,只有一类真的需要 Windows。**

| 风险类 | 内容 | 需要 MSVC? |
|---|---|---|
| **A 标准库差异** | 隐式包含、传递依赖、ADL(如客户端 `BootScene` 的 `va_list` 只包 `<cstdio>`) | ❌ 换 libstdc++ 即可暴露 |
| **B 编译器方言** | LLP64 · `wchar_t` 宽度 · `min`/`max` 宏 · 两阶段名称查找 | ✅ **只有它需要** |
| **C 浮点逐位一致** | 黄金用例集的全部价值所系;FMA 合并策略三家编译器各不相同**且无告警** | ❌ 换任何编译器都能暴露 |

⇒ 用 **GCC 15.2 / libstdc++** 在 mac 上跑四个组合,A 与 C 两类当场出清:

| 组合 | 结果 |
|---|---|
| 服务端 × Apple clang 21 | ✅ 0 告警 · `ctest` 5/5 |
| ★ 服务端 × GCC 15 / libstdc++ | ✅ 0 告警 · `ctest` 5/5(修完下述缺口后) |
| 客户端 `d2-only` × Apple clang 21 | ✅ 0 告警 · 黄金用例集 1/1 |
| ★ 客户端 `d2-only` × GCC 15 / libstdc++ | ✅ 0 告警 · 黄金用例集 1/1 |

**★ 两笔当场兑现的价值:**

① **A 类实证:GCC 报出 36 处 `-Wshadow`,Apple clang 一处都不报。**
全部来自 IDL 生成物 —— `repeated` 字段的编解码会包一层 lambda,而 lambda 的形参
也叫 `w` / `r`,**遮蔽了外层同名形参**。
⚠️ 修在 **codegen**(`sgidl/cpp.py` 的 `write_elem` / `read_elem` 增流名参数,
lambda 内改用 `we` / `re`),不是修生成物 —— 否则下次 `sgidl_gen.py` 一跑就回来了。

② ★★ **C 类固化:`shared/` 显式关闭 FMA 合并**(`-ffp-contract=off` / MSVC `/fp:precise`)。
GCC 默认 `fast`(跨语句合并)· clang 默认 `on`(仅语句内)· MSVC 默认 `/fp:precise`
⇒ **同一份 `float` 公式可以算出逐位不同的结果,且三家都不会给任何告警。**
实测 2,148 断言在 GCC 下确实全绿,**但那是当前公式恰好没踩到合并点,不是这条性质成立**。
⚠️ 这与 §10.4 的三类静默错误同源;而 `00` §0 已认下 L3 黄金用例集是第 ③ 层
「不可自证」的**唯一**补偿手段 ⇒ 它的逐位一致性不能靠运气。

★ **对排期的后果**:MSVC 从「D2 唯一未出清的风险」降级为「只剩 B 类方言未验」,
⇒ **不必为它切换开发平台**;剩下那一类交给 CI 的 `windows-latest`(前置是欠债 8 的推送)。

> ✅ **后续(2026-09-02 当日)**:用户已把开发环境搬到 Windows ⇒ B 类当场用
> §9.0.7 的一次性验证收口,**没等 CI**。⚠️ 但 CI 的 `windows-latest` 仍要挂 ——
> 一次性验证回答的是「今天这份代码在 MSVC 下成不成立」,**CI 回答的是「明天改了还成不成立」**,
> 两者不可互替。⇒ 该项转入客户端 `01` §13 欠债 8 的后续。

#### ★★ 两个在编写脚本时当场发现并修掉的缺口

> **它们的共同点:两端都是 clang 时永远不会暴露** —— 与 `d939247` 那个
> 「`shared/` 依赖服务端顶层」的缺口是同一族。

**① `cmake/SgWarnings.cmake` 的 MSVC 分支缺 `/utf-8`。**

本仓源码是 UTF-8,而中文**不止在注释里**:

```
TEST_CASE("相克矩阵:与 battle_event.c:922-949 逐项一致")      ← doctest 用例名
assert(false && "相克矩阵与 05-battle.md §3.4 原表不符")        ← 断言消息
```

⚠️ MSVC 默认按**系统 ANSI 代码页**读源文件(简体中文 Windows = 936/GBK)⇒
轻则 `C4819` 刷屏 + 用例名与断言消息乱码,重则某个 UTF-8 字节序列在 GBK 下
被读成尾随反斜杠一类,**直接编译错误**。
★ 客户端 `SgClientWarnings.cmake` **早就有这一行**,服务端漏了。

**② 更要紧的一处:`shared/` 自己没有 `/utf-8`。**

客户端只 `add_subdirectory(shared)` 时**不会**调用任何 `sg_apply_warnings`
⇒ 只补在两仓的告警函数里,`sg_shared` 这个目标本身仍然没有它。
⇒ 已补在 `shared/CMakeLists.txt`,理由与 `-ffp-contract=off` 同类:
**`/utf-8` 决定源文件怎么被解码,是语义不是风格** ——
凡是「消费方不做就会坏」的东西,都得 `shared/` 自己保证(DR-TS3 的承诺)。

#### ★ 第 6 项为什么必须做

`sg_enable_assertions()` 的 MSVC 分支从未执行过。若它在 MSVC 下不生效,
后果与 2026-08-31 服务端踩过的那次**一模一样**:测试照常链接、退出码 0、
打印 OK,**但一条都没验证** —— 而这次我们会把那个绿色读成「D2 在 MSVC 上通过了」。

⇒ 脚本故意把相克矩阵改错一格,**期望测试失败**;不失败才是问题。
⚠️ 这也决定了报告的**归因顺序**:先看 `C4819`(有 ⇒ `/utf-8` 没生效,其余结论全部不可信),
再看第 6 项(失效 ⇒ 所有「通过」都不算数),然后才是逐条方言问题。

⚠️ **修在源码或 CMake,不要为了让它绿而放宽告警口径** —— `/W4 /permissive-` 是
这次唯一一次能用 MSVC 审这份代码的机会。
