## 0. 一条必须先说清的边界

> ★ **`10` 的 151 + 123 条清单是语义参考,不是兼容目标。**

R2 已定不实现旧 lssproto。新协议**不与任何旧客户端互通**,因此:

| 旧构造 | 处置 | 理由 |
|---|---|---|
| 协议编号偏移(上行 **+13** / 下行 **+23**) | ❌ 不沿用 | `10` §2.1 实测;新 IDL 下这个常量不存在 |
| 分发魔数 `1458` | ❌ 不沿用 | `10` §4.2;私有握手的替代品是 TLS |
| 校验和 = **整数字段值之和 + 字符串字段长度之和** | ❌ 不复刻 | `10` §2.3 实测:交换两个整数字段的值不改变校验和,**防篡改强度为零** |
| 字段级 6bit 编码 + `PersonalKey`(= cdkey + `_RUNNING_KEY`) | ❌ 不复刻 | `02` §3.2;密钥由玩家自己知道 |
| 整包 TEA(`DENGLUKEY1` 两端硬编码同值) | ❌ 不复刻 | 同上;改标准 TLS |
| saacproto 的 **base-62 整数** + 协议名 `strcmp` 分派 | ❌ 不沿用 | `10` §3.1 |
| `MAXLSRPCARGS` 单消息 ≤ 13 字段(saacproto ≤ 7) | ❌ 不沿用 | 结构化消息无此限制 |

⇒ **本文的映射表只回答「这条协议承载的业务要不要做、做成什么形状」,不回答「怎么兼容」。**

## 1. 三条硬约束

### 1.1 ★★ 显式赋值每一个协议号与窗口类型号

> **这是旧实现两端漂移的根因,不是风格问题。**

`10` §0.2 结论 B/C 的实测:

| 事实 | 数字 |
|---|---:|
| 服务端与客户端**同号异义**的编号 | **5 个**(127 / 135 / 136 / 137 / 138) |
| 客户端头文件**自身同号重复**(后定义覆盖前者) | **2 处**(137 / 138) |
| 窗口类型枚举**两端成员值不同** | **3 个**(`_10_MEMONTUM` / `_FM_MEMONTUM` / `_MANOR_SCHEDULE`,服务端比客户端大 1) |

成因是**枚举成员受 `#ifdef` 影响,而两端宏集不同** —— 被关掉的成员不占号。
⇒ 私服一分叉,「枚举顺序即协议号」这个隐式约定必然破裂。

**落地规则**:

```
1. 每个 message 的编号在 IDL 里写死数字,不依赖声明顺序;
2. 每个窗口类型、每个枚举成员同样写死数字;
3. 编号一经发布不得复用,废弃只标 deprecated 并保留占位;
4. IDL 里不得出现任何条件编译 / 特性开关。
   ★ 特性差异走运行时配置(D7),不走 schema 分支。
```

⚠️ **第 4 条是第 1–3 条的前提**:只要 schema 里有一个 `#ifdef`,两端宏集一分叉,
1–3 条全部失效。

### 1.2 长度前缀

协议自带长度前缀。理由不是"约定俗成",而是 `00` §4.3:
**TCP 是字节流、WebSocket 保留消息边界,长度前缀同时满足两者** ——
D4 解冻时换 `WsTransport` 不动上层。

⚠️ 旧实现按 `'\n'` 切行(`01` §4.1 的 `GetOneLine`),这与"负载里可能有换行"直接冲突,
原实现靠转义硬撑。**新实现不按分隔符切帧。**

### 1.3 ★ 每条请求带 `request_id`,不靠连接顺序对齐

`17` §7.4 的实测更正:需要显式关联的是 **72 条**,不是 49 条 ——
49 条带续体字段 + 40 条有应答但无续体(重叠 17)。
后 40 条今天靠"单 TCP 长连接 + 单线程 saac ⇒ 应答必然按请求顺序返回"隐式对齐,
**拆分后这个前提消失**。

⇒ 服务间接口一律带 `request_id`(§7),**客户端侧同理**:
凡是"发出去要等结果"的请求都带关联 ID,不靠"下一个到达的包就是回复"。

## 2. 分层与帧

```
┌────────────────────────────────────────────┐
│  应用层   IDL 生成的 message,业务直接消费   │
├────────────────────────────────────────────┤
│  信封层   Envelope { msg_id, corr_id, body }│
├────────────────────────────────────────────┤
│  帧层     [u32 length][payload]             │
├────────────────────────────────────────────┤
│  传输层   ITransport:TCP(现)/ WS(D4)  │
│           TLS 在此层,不在协议层            │
└────────────────────────────────────────────┘
```

### 2.1 信封

```
Envelope {
    uint32  msg_id       // ★ 显式赋值,见 §3 号段
    uint64  corr_id      // 请求-响应关联;Notify 为 0
    bytes   body         // 对应 msg_id 的 message 编码
}
```

⚠️ **不在信封里放版本号做分支**。协议版本不匹配时在握手阶段直接拒绝,
不做"按版本走不同解析路径"—— 那是旧实现 `bNewServer` 双协议分支的老路。

### 2.2 编解码选型

| 项 | 定 | 备注 |
|---|---|---|
| 序列化 | **Protobuf** 或自定义 DSL(`00` §8) | 判据是"能否显式赋值编号 + 能否生成 C++20 两端" |
| 生成产物位置 | `idl/generated/`,两端共用同一份 schema 生成 | `01` §4 目录结构 |
| 客户端引用方式 | submodule / `FetchContent`,**不手写编解码** | `01`(客户端)§6.2 |

★ **schema 是唯一真源** —— 两端都不允许手写 `encode/decode`。
这一条是 §1.1 三处双端漂移的**结构性对策**:让漂移在编译期就不可能发生。

## 3. 号段划分

按业务面切,给每段留足空位。数字本身可调,**分段这件事不可省**:

| 号段 | 用途 | 说明 |
|---|---|---|
| `0x0001 – 0x00FF` | 握手 / 会话 / 心跳 | 登录、选角、登出、Echo |
| `0x0100 – 0x01FF` | 世界与移动 | 移动、地图块、视野 Appear/Disappear |
| `0x0200 – 0x02FF` | 战斗 | 指令、事件流、进出场 |
| `0x0300 – 0x03FF` | 角色与成长 | 属性、技能、转生、状态 |
| `0x0400 – 0x04FF` | 道具与装备 | 背包、装备、掉落、交易 |
| `0x0500 – 0x05FF` | 宠物 | 出战、技能、邮件 |
| `0x0600 – 0x06FF` | NPC 与窗口 | ★ 窗口驱动 UI(§5) |
| `0x0700 – 0x07FF` | 社交与聊天 | 频道、名片、组队 |
| `0x0800 – 0x08FF` | 家族与庄园 | |
| `0x0F00 – 0x0FFF` | GM 与运维 | ★ 独立鉴权面(见 `09` §6) |

⚠️ **不设"上行段/下行段"**。旧实现的上下行编号空间会重叠
(`EV_SEND` 下行 27、`B_RECV` 上行 27,`10` §2.1),靠"两个方向各自独立解析路径"避免冲突
—— 这在结构化协议里是纯粹的复杂度,**方向由 message 类型本身表达**。

### 4.3 ★ `EN`(遇敌)不是网络入口

`lssproto_EN_recv` 被服务端内部当"开战入口"直接调用 **9 处**(移动遇敌 4 处 + `net.c` +
战斗事件 + GM 命令 + `callfromcli.c` 2 处)。

⇒ ★★ **玩家无法主动请求遇敌,遇敌完全由服务端在移动时判定。**
**新协议不得给客户端一个"我要遇敌"的上行消息。** 这不是简化,是原版语义。

## 5. ★★ 窗口协议:保留思想,改变载体

### 5.1 为什么保留

`01`(服务端)§6.3 已裁定保留"服务端驱动 UI"。规模依据:
`10` §5.5 实测 **350 个真实 `WN_send` 调用点**,其中
`MESSAGE` 一种类型占 **191 / 350 = 54.6%**,前 3 种占 **66.6%**。

⇒ **绝大多数 NPC 交互就是"发一段文字 + 一组选项"**。
把它做成结构化的窗口描述,一次投入就覆盖三分之二的交互面。

### 5.2 原始负载语法(已知,不必归纳)

★ `10` §5.4 的重大发现:**`WN` 的负载语法在原始 `lssproto.html` 规格里有完整定义,
且以注释形式保留在 `SSRC80/lssproto_serv.c:2363`**(8.5 已删除)。

| 字段 | 原始规格 |
|---|---|
| `windowtype` | 决定窗口形状;与 `buttontype` 组合确定窗口 |
| `buttontype` | **按位或**组合。位号两端 100% 一致:`OK=1<<0` `CANCEL=1<<1` `YES=1<<2` `NO=1<<3` `PREV=1<<4` `NEXT=1<<5` |
| `seqno` | ★ **这个窗口的编号,由服务端指定**;客户端回执原样带回 ⇒ 服务端据此知道"是哪个 NPC 的哪一步" |
| `objindex` | 触发窗口的 NPC 的 index;**系统触发时为 `-1`**;客户端原样返回 |
| `data`(选择型) | ★ `"\n"` 分隔;**首 token = 消息行数 N**;接着 N 个 token 是消息;**其后每个 token 是一个选项,1-based 编号**,选中后回传该编号 |
| `data`(商店型) | 逐项含:能否买旗标 / 是否沿用前次数据 / 店名 / 消息 / 店消息 / 个数消息 / 等级不足消息 / 确认消息 / 道具满消息 / 道具等级 / 价格 / 图号 / … |

### 5.3 新形状

```
WindowOpen {
    uint32          window_id     // ★ 取代 seqno,服务端指定,回执原样带回
    WindowKind      kind          // ★ 显式枚举值,不用声明顺序
    ButtonMask      buttons       // 位掩码,位号沿用(两端本来就一致)
    int32           source_entity // ★ 取代 objindex;系统触发用独立的 SYSTEM 值,不用 -1
    WindowBody      body          // oneof:见下
}

WindowBody = oneof {
    Message      { repeated string lines }
    LineInput    { repeated string lines; uint32 max_len }
    Select       { repeated string lines; repeated Choice choices }  // ★ Choice 带显式 id
    ItemShop     { ShopHeader header; repeated ShopEntry entries }
    PetSkillShop { ... }
    ...
}

WindowReply {
    uint32  window_id             // 原样带回
    int32   source_entity
    oneof   { uint32 choice_id | string text | uint32 index }
}
```

**四条改变**(每条都对应一处实测缺陷):

| # | 旧 | 新 | 依据 |
|---|---|---|---|
| 1 | 选项编号 = **在 `data` 里的位置**(1-based) | ★ 每个选项带**显式 `choice_id`** | `09` §3.7:条件分支与文案是**位置耦合**的,重排分支就错位 |
| 2 | 消息行数写在负载第一个 token | 用 `repeated string` | 首 token 是行数这件事本身就是分隔符复用 |
| 3 | 系统触发用 `objindex = -1` | 显式枚举值 | `-1` 与"无效实体"混淆 |
| 4 | 窗口类型是隐式枚举序号 | ★ 显式赋值 | `10` §5.2:两端差 1 |

### 5.4 窗口类型清单的口径

⚠️ `10` §5.5 已更正原"43 种窗口"的口径:

```
两端并集         52 种
有服务端调用点   29 种      ← ★ 这才是要实现的
两端齐备         28 种
其余 24 种       「注册了但没投产」
```

⇒ **首批只实现有调用点的 29 种**,其余登记不做。逐条映射见 `../../stone-age-client/docs/03-ui-window-catalog.md`。

⚠️ 另有 **48 处 `windowtype` 是运行期变量**(NPC 通用窗口分发),不可静态归类 ——
`10` §13 待补 2 已登记,实现期须做常量传播确定取值域。

### 5.5 ★ 回执侧的两条强校验必须保留

`10` §5.7 实测,`lssproto_WN_recv` 里有两条**与窗口无关**的校验:

| 校验 | 原实现 | 新实现 |
|---|---|---|
| **交易态锁** | `CHAR_WORKTRADEMODE != CHAR_TRADE_FREE` 直接 return | ✅ 保留 —— 交易中不得响应任何窗口 |
| **坐标一致性** | 客户端上报的 `x,y` 与服务端记录不符则 return(注释写 `avoid the warp at will`) | ✅ 保留语义,但**服务端不该依赖客户端上报坐标** —— 改为校验"玩家是否仍在该 NPC 的交互范围内" |

★ 第二条的改法比照抄更强:原实现只是比对客户端自报的坐标,
新实现用服务端权威坐标做范围判定,**客户端根本不需要上报坐标**。

### 5.6 窗口状态常量

`10` §5.7:`char.h` 里有 **144 个 `CHAR_WINDOWTYPE_*`**,而全库只有 **32 个**被 `seqno` 实际判定。
⇒ 其余 112 个要么只由 NPC 侧自己消费,要么已废弃。

**处置**:窗口会话状态不做成全局常量族,改为**每个 NPC 交互一个显式的会话状态机**
(见 `07-npc-quest.md` §5)。`window_id` 只需在一次会话内唯一,不需要全局编号空间。

## 6. 战斗:从字符串串到事件流

### 6.1 旧形状

`07` §8:一个回合的下发 = `szAllBattleString`(≤ 4096 B)= Σ 每个行动者的段 + 状态变更段。
**33 个子命令**,形如 `BH|a3|r5|f2|d1E|p0|FF|`,字段**带标签**而非位置参数
(客户端 `get_num()` 逐字符扫十六进制,遇非 `[0-9A-F]` 即停 ⇒ **标签字母本身就是分隔符**)。

### 6.2 新形状

```
BattleEvents {
    uint64             battle_id
    uint32             turn
    repeated BattleEvent events   // ★ 顺序即演出顺序
}

BattleEvent = oneof {
    TurnBegin   { ActionMask ready_mask; uint32 turn }        // ← 旧 BA
    Snapshot    { repeated CombatantState states }            // ← 旧 BC
    SelfInfo    { uint32 slot; MenuMask menu; int32 mp }      // ← 旧 BP
    Hit         { uint32 attacker; repeated HitTarget targets }// ← 旧 BH / BB / B+ / BJ
    Damage      { uint32 target; int32 hp_delta; int32 pet_hp_delta; DamageFlags flags }
    StatusChange{ uint32 target; StatusKind kind; bool applied }// ← 旧 BM
    ...
}
```

**四条改变**:

| # | 旧 | 新 | 依据 |
|---|---|---|---|
| 1 | 变长目标列表靠 `FF\|` 终止符 | `repeated HitTarget` | `07` §8.2:`FF` 是终止符不是校验和 |
| 2 | 状态变更拼进固定 1024 B 缓冲,`strncat` 第三参用错 ⇒ 等价无上界 `strcat` | 结构化列表 | `07` §10.4:**余量仅 56 字节**,新增状态种类即溢出且无第二道防线 |
| 3 | 位标志两端名字不同但位号相同(`BCF_NO_DAMAGE` ⇄ `ATT_NOMISS`,语义相反的命名同一位) | 单一枚举,双端同源生成 | `07` §8.3 |
| 4 | 三个子命令服务端发、客户端**不解析**(门控落差),`switch` 无 `default` ⇒ **静默跳过** | schema 唯一 ⇒ 不可能落差 | `07` §8.4:`Ba`/`Bb`/`Bf` |

★ **第 4 条是本节最重要的一条**:8.0 存在"服务端算了、客户端没演出"的技能。
新实现的 schema 单一真源从结构上消灭这个 bug 类。

### 6.3 上行指令

`07` §5.2 实测:客户端上行只有 **12 个字母**,却要驱动 **148 个内部指令码** ——
具体技能由**参数里的数组下标**决定,不在指令字母里。

⇒ ★ **新协议必须显式技能 ID**,不能沿用"一个字母一条指令 + 下标选技能"。

```
BattleCommand {
    uint64  battle_id
    uint32  turn          // ★ 带回合号,防止迟到指令作用到新回合
    oneof {
        Attack   { uint32 target }
        Guard    {}
        Escape   {}
        Capture  { uint32 target }
        PetIn    { uint32 pet_slot }   PetOut {}
        UseItem  { uint32 item_slot; uint32 target }
        PetSkill { uint32 skill_id; uint32 target }    // ★ 显式 skill_id
        ProfSkill{ uint32 skill_id; uint32 target }
        Spell    { uint32 spell_id;  uint32 target }
        Wait     {}
    }
}
```

⚠️ **`@`(纯回 MP,`MP += 30` 上限 100)这条旧指令不迁移** —— 它是无战斗动作的白给,
且 `07` §3.5 已证 `BATTLE_MpDown` 被 `#if 1` 短路成空函数 ⇒ 战斗指令本就不耗 MP。
两者一起决策,见 `05-battle.md` §8.3。

### 6.3.1 ★★ 入场序列(2026-09-06 落地,1.4 服务端侧)

> **一处此前没写下来的契约:客户端凭什么组得出 `BattleCommand`?**
> §6.3 的 `BattleCommand` 要 `battle_id` 与 `turn` —— **而握手回执里这两样都没有。**
> ⇒ 入场时必须先把它们下发,否则上行链路在客户端那头根本走不到第一步。

**入场即下发两条,顺序固定:**

```
（客户端握手通过后）
  ← BattleSelfInfo  (0x0203)   battle_id · slot · cannot_act
  ← BattleTurnBegin (0x0202)   battle_id · turn · ready_mask
  ← BattleEvents    (0x0205)   每个节拍一批
  ← BattleTurnBegin (0x0202)   回合推进
  → BattleCommand   (0x0210)   battle_id / turn 取自上面两条
```

★ **顺序是契约的一部分**:`BattleSelfInfo` 必须排在第一条 `BattleEvents` 之前 ——
反过来客户端会先收到一堆**不知道打给谁看**的事件。已由用例钉住(`00` §9.0.16 ④)。

⚠️★ **两个字段的取值口径不同,别一起处理**:

| 字段 | 口径 |
|---|---|
| `cannot_act` | ✅ **照 `rules::CheckCanAct` 填** —— DR-BT5 把「能否行动」定为那一个真源,客户端**可以**据它置灰(DR-CP7) |
| `menu_flags` | ⚠️ **恒为 0**(阶段 2 的 UI 契约,此处不猜)⇒ 客户端 1.4 **不应**消费它,否则会得到"什么都没开" |

⚠️ `ready_mask` 同样恒为 0:1.5/1.4 **没有指令收集期**(指令一到就存下),
而 §6.4 那条「按节拍聚合就绪位」要等收集期存在才有意义 ⇒ 属阶段 2。

★ 下发点在 `World::JoinBattle` 而**不是**在 demo 装配代码里:
任何入场路径(阶段 2 的选角、观战加入)都需要这两条,它不是脚手架专用的。

### 6.4 报文量的一处必须改

`07` §5.2:**每条玩家指令都触发一次 `BA` 串下发**(全场 endBit 位图 + 回合号),
而不是等一回合结束 ⇒ 指令阶段报文量 = 玩家数²。

⇒ **新实现按节拍聚合**:指令阶段的"谁已就绪"变更攒批下发,
与 `01` §3.2 的 `ca_flush_interval` 同源。

## 7. 服务间接口

沿用 `00` §3.1 的形状,此处只补编号与错误面。

```
Request / Response(72 条)
    Req  必带 { instance_id, generation, request_id, deadline_ms }
    Resp 必带 { request_id, status, error_code }

Notify(34 条)
    rpc <Op>(Event) returns (Ack{accepted})
    ⚠️ accepted 只代表入队,不代表持久化
    ★★ 资产类操作禁走此路
```

### 7.1 为什么是三元组而不是一个自增整数

`17` §7.2 的实测故障模式:`SERVSTATE_init()` 把 `servstate.fdid` **归零**
⇒ gmsv 每次启动都从 0 重新发放续体号。
saac 侧 `is_game_server_login(ti)` 只检查槽位登录状态、**没有世代号**
⇒ 重启后旧实例的迟到应答可能命中新实例的同号连接,**投递给不相干的玩家**。

⇒ `instance_id`(哪个实例)+ `generation`(第几次启动)+ `request_id`(哪个请求),缺一不可。

### 7.2 错误面

```
Status = { OK, INVALID_ARGUMENT, NOT_FOUND, CONFLICT, PERMISSION_DENIED,
           RESOURCE_EXHAUSTED, FAILED_PRECONDITION, ABORTED, DEADLINE_EXCEEDED,
           UNAVAILABLE, INTERNAL }
```

⚠️ **`error_code` 是业务码,与 `status` 正交**。
原实现的失败处置多半是"发一句聊天提示就完事"(`17` §5.4 的仓库存盘失败只发
`"道具仓库资料存档失败!"`,不回滚不重试)——
**新实现的每个错误码必须绑定一个明确的调用方动作**:重试 / 补偿 / 放弃并告知玩家。

### 8.1 ★ 第四道关:生成物本身能不能用

> 前三条检查的是 **schema**;它们全绿,生成物仍可能编译不过或形状不对。

`idl/tests/`(2026-08-31 新增,入口 `sh idl/tests/run.sh`):

| 检查 | 挡住什么 |
|---|---|
| POD 断言(`is_trivially_copyable` / `is_standard_layout`) | DR-TS1 边界 ② 被破坏 |
| 枚举窄化(`sizeof(BattleStatus) == 1`) | `(sg.width)` 失效 |
| `msg_id` 编译期映射 | `ids.h` 与 schema 漂移 |
| 编解码往返 / 截断输入 / 写缓冲不足 | 越界读写 |
| ★ **体积回归断言** | 见下 |

★★ **为什么体积要写成断言而不是靠 code review**:

⇒ **这类回归静默且昂贵**,与 §1.1 的编号漂移同属"半年后才暴露"的一类。

## 9. 与 `shared/` 的关系

```
shared/rules  →  输出 BattleEvent 序列(IDL 类型)
shared/model  →  L2 领域类型
idl/generated →  两者都可依赖
```

⚠️ **`shared/rules` 可以依赖 IDL 生成的**事件类型**,但不得依赖任何**传输**类型**
(Envelope、连接、会话)。否则 `01` §4 的"`shared/` 只依赖标准库"就破了。

⇒ 实践做法:IDL 分两组 schema ——
`schema/domain/`(事件与领域值对象,`shared/` 可依赖)与
`schema/transport/`(信封、握手、错误面)。

### 9.1 ★★ 该边界 2026-09-06 起**按子树**,不再按 `shared/` 整体(DR-TS9)

> 上面那句「`shared/` 不得引用 `transport/`,只有 `src/net` 依赖」在 DR-TS9 裁定后**过窄了** ——
> 它会挡住一个我们明确想要的东西:**双端共编的成帧 / 信封层**。

```
shared/rules/   ❌ transport/ 仍然禁止      ← 不放宽。L3 是纯函数,
                                              信封是传输概念,进来就破了 05 §1.5 的契约
shared/model/   ❌ 同上
shared/wire/    ✅ transport/ 可**且只可**它引  ← 它的职责就是信封
src/net/        ✅ 宿主侧,本来就可以
```

**为什么放宽**:成帧与信封编解码是**双端语义完全相同**的东西,客户端 1.4 也要一份。
三案(自写第二份 / 双端共享 / 客户端直编服务端源文件)见 `11` §1.6,**用户 2026-09-06 拍板共享一份**。
⇒ 与 D2 · DR-TS3 · 黄金用例集「复用不复制」· DR-BT5 反对双份实现同一条理由:
**凡双端同一语义的东西只留一份,让漂移在编译期就不可能发生。**

⚠️★ **放宽的实现方式本身是这条裁定的一部分,不是配套细节**:
`tools/check_shared_purity.py` 的 `SUBTREE_ALLOWED` 只按**路径前缀**开口。
若有人把它写成「整个 `shared/` 都允许 `transport/`」,L3 的纯度会一起被放掉,
**而那不会有任何东西报错** —— 与 `00` §10.4 三类静默错误同族。
⇒ 已有一条反向验证钉着它:往 `shared/rules/battle.h` 塞一行 `transport/` include,
本脚本必须报红并点名(实测退出码 1,还原后 0)。

★ **两处守卫,管的不是同一件事**:

| 处 | 管什么 |
|---|---|
| `check_shared_purity.py` 的 `SUBTREE_ALLOWED` | 能不能 `#include` |
| `shared/CMakeLists.txt` 拆出独立目标 `sa_wire` | 能不能**链接** —— `sa_shared` 的闭包里永远没有信封 |

⇒ 目标切分让这条差别落在**构建图**上:谁想让 `rules` 用上 Envelope,得先改 `shared/CMakeLists.txt`。
⚠️ 但构建图管不住 include(IDL 生成物的 `#include` 从 `generated/cpp` 根算起,
`sa_idl` 一个目标同时暴露两组头)⇒ **两处都要,缺一处就是半个边界**。
