## 1. 三份地图数据与合并策略

### 1.1 现状:同一张地图有三份数据

| 文件 | 数量 | 每格字节 | 内容 | 字节序 |
|---|---:|---:|---|---|
| 客户端 `<编号>.dat` | 1,280 | 6 | ★ **三层 planar**:地面 / 覆盖物 / 位域 | 小端 |
| 客户端 `<编号>.MAP` | 1,026 | 2 | 地面 tile 层 | 小端 |
| **服务端 `LS2MAP`** | **1,235** | 4 | 逻辑层:tile + obj | ★ **大端** |

⚠️ **`.dat` 的布局是 planar(分层连续)而非 interleaved** ——
按 interleaved 解会全表不匹配。服务端同样是 planar,两者一致。

★ 第三层实测是**位域不是事件层**:60.88% 是 `0xC000`、37.22% 是 `0x0000`,
低 14 位非零的格仅占 0.28% ⇒ **实质是 2 个标志位**。

### 1.2 ★ 三源关系已量化

`03` §7.3,1,157 张可比地图:

| 关系 | 实测 |
|---|---|
| 客户端地面层 == 服务端 tile | **757 张完全一致(65.4%)** |
| 客户端覆盖物层 == 服务端 obj | 746 张(64.5%) |
| ★ **差异格的性质**(283,585 格) | ★★ **98.51% 是「服务端有、客户端无」** —— 服务端多出的**不可见碰撞** |
| | 1.36% 是「客户端有、服务端无」(纯视觉装饰) |
| | 0.13% 是两侧都有但图元号不同 |
| 覆盖差 | **49 张仅服务端有**(无渲染数据);155 张缺 `.MAP` |
| 尺寸不一致 | **10 例** |

### 1.3 ★ 合并策略(有量化依据,不是偏好)

```
几何与图元号  取客户端   (渲染保真)
碰撞/通行性   取服务端   (玩法保真)
```

**依据**:98.5% 的差异是服务端多出的碰撞信息,**正是玩法正确性所依赖的部分**。

⚠️ **两项须逐张人工裁定**:
① **10 例尺寸冲突**;② **49 张"仅服务端有"** —— 是废弃地图,还是渲染资产缺失?

⇒ ★ **客户端不再自行维护碰撞**;通行性以服务端逻辑层为唯一真源,客户端只做预测与表现
(`../../stone-age-client/docs/05-world-movement.md`)。

## 2. `LS2MAP` 的实测结论

```
+0    char[6]   magic = "LS2MAP"
+6    U2 BE     id            ← ★ 大端,且 422 个文件的文件名 != 此 id
+8    char[32]  showstring    ← 地图名,格式「名称|数字」
+40   U2 BE     xsiz
+42   U2 BE     ysiz
+44   U2 BE     tile[xsiz*ysiz]
      U2 BE     obj [xsiz*ysiz]
文件大小 >= 44 + 4*xsiz*ysiz      ← ★ 判据是 >= 而非 ==
```

**全量验证**:

| 项 | 结果 |
|---|---|
| 带魔数的文件 | 1,235 |
| **解析成功** | ★ **1,235 / 1,235(100%)** |
| 唯一 map id | 1,214 ⇒ ★ **21 个 id 重复**,加载时按目录序后者覆盖 |
| ★ **文件名 ≠ 头部 id** | **422** ⇒ ★★ **不能用文件名识别地图** |
| 图元号合法性 | ★ **0 张含非法图元号**;tile 层用 5,993 种、obj 层 2,184 种,全部在图元属性表内 |
| 尺寸分布 Top3 | 50×50(230 张)、30×30(162)、60×60(115) |

**两个须处理的数据缺陷**:

| # | 缺陷 | 处理 |
|---|---|---|
| 1 | **10 个文件尾部有多余数据**(最多多 54,000 B) | 头部尺寸经客户端交叉验证正确 ⇒ ★ **判据用 `>=`** |
| 2 | **21 个重复 id** | 原实现按目录序后者覆盖 ⇒ ★ **提取时须显式选定并记录** |

★ **`showstring` 是可用的地图命名来源**:全量统计显示绝大多数是真实地图名
(`幻影之界第三层|0` `民房|0` `龙蜥洞窟|0` …),格式为「名称|数字」。
⚠️ 曾有一处误判(某单个样本的内容是广告),那只是**一个样本**,不是普遍情况。

## 3. 运行时结构

### 3.1 内存形状

```
Map {
    id; xsiz; ysiz; name;
    tile[]      地表图元号
    obj []      物件图元号
    olink[]     ★ 每格上的动态对象链表(角色 / 道具 / 石币)
    startpoint; map_type
}
```

★ **`olink` 是视野广播的代价来源**(§5.2):每次广播都要逐格遍历这条链。

### 3.2 图元属性表(17 项)

由图元属性文件提供,**每个图元号一行**(20,157 行):

```
WALKABLE  HAVEHEIGHT  DEFENCE  INTODAMAGE  OUTOFDAMAGE
SETED_BATTLEMAP  BATTLEMAP1/2/3
INTODARKNESS  INTOCONFUSION
OUTOFPOISON  OUTOFPARALYSIS  OUTOFSILENCE  OUTOFSTONE  OUTOFDARKNESS  OUTOFCONFUSION
```

⚠️ ★ **解析器的列偏移是 4,不是 2** —— 第 1 列是图元号,**第 2、3 列被跳过且源码从不读取**。
`offset` 硬编码为 4 说明历史上这两列有用途。⇒ **可原样搬迁,但不要按"第 2 列就是第 1 个属性"解析。**

### 3.3 ★ 新形状:属性入图元表,不入格子

原版每格只存图元号,属性从图元表查 —— **这个设计保留**:
20,157 个图元 × 17 项属性 ≈ 一张小表,而 1,075 万格 × 17 项属性是不可接受的。

⚠️ 但**碰撞层要单独存**(§1.3):服务端的不可见碰撞不是从图元属性推出来的,
是 obj 层多出来的格子。

## 4. 移动与碰撞

### 4.1 权威归属

| 判定 | 权威方 |
|---|---|
| 通行性 | ★ **服务端**(逻辑层 obj + 图元属性) |
| 位置 | ★ **服务端**;客户端只做预测,收到纠正即回滚 |
| 遇敌 | ★ **服务端在移动时判定**;★★ **玩家无法主动请求遇敌**(`02-protocol.md` §4.3) |

### 4.2 ★ 角色循环的两段结构必须保留

`15` §5.3:

```
段一:玩家 —— 每 tick 全扫
段二:非玩家 —— ★ 游标滑动窗口(每 tick 只看 petnum/2 个槽位),
      且 ★ 每 tick 最多让 EnemyMoveNum 个实体移动就提前退出
```

| 特征 | 玩家段 | 非玩家段 |
|---|---|---|
| 每 tick 触及槽位 | 全扫 | `petnum/2` |
| 覆盖全量所需 tick | 1 | ★ **12 tick** |
| 提前退出 | 无 | ★ `movecnt >= EnemyMoveNum` |

⇒ ★★ **NPC/敌人的 AI 是摊还执行的**:12 个 tick 才轮完一遍,且每 tick 最多 10 个实体移动。
★ **这是原实现自带的负载整形机制** ——
**新实现若改成"每 tick 全扫所有 NPC"会把计算量放大 12 倍。**

### 4.3 ★ `EnemyMoveNum`:一个不在配置文件里的运营旋钮

| 项 | 值 |
|---|---|
| 语义 | 每 tick 允许移动的非玩家角色数上限 |
| 8.5 默认 | 20 |
| ★ **8.0 默认** | **10** |
| 在线改写入口 | ★ **经系统信息 NPC 在线改** |
| ★ **不在配置文件** | 不是配置项,不在 295 参数字典里 |

⇒ ★ **只迁移配置文件会丢掉这个旋钮**,而它直接决定"地图上的怪物动得多快" ——
**玩家可感知**。**建议纳入正式配置项,并保留在线可改的能力。**

### 4.4 地图属性的整节配置

`01`(plan)§9.3:配置文件里有整节地图属性 ——
禁救援地图 / 玩家重叠 PK / **禁逃地图** / 非法登出处理 / 禁组队地图 / 地图治疗 / 禁声望地图。

⚠️ ★ **战斗逃跑时会先扫 32 个禁逃地图**(`07` §5.2)⇒ 这是玩法配置,不是部署配置。

⚠️ 另有一条**硬编码数据路径**:禁出地图表走硬编码路径,不经配置键(`08` §4.6 的第四类)。

## 5. ★★ 视野与广播

### 5.1 两份血统的视野常量不同

| 常量 | 8.5 | ★ 8.0 | 扫格数 8.5 | ★ 8.0 |
|---|---:|---:|---:|---:|
| 角色视野 | **20** | **23** | 441 | ★ **529**(+20.0%) |
| 地图块视野 | 24 | **27** | 625 | ★ **729**(+16.6%) |

★ **扫格公式必须用 `(2*(c/2)+1)²`,不是 `(c+1)²`** ——
循环是 `for(i = x−c/2; i <= x+c/2; i++)`,而 C 的 `c/2` 是**整数除法**。
两者只在 `c` 为偶数时相等;**8.0 的 `c = 23` 是奇数**,用 `(c+1)²` 会**高估 8.9%**(576 vs 529)。

⚠️ ★ **置信度**:二进制符号表**不含 `#define`** ⇒ **此项无二进制侧证据**。
两份源码不一致,按 8.0 血统源码取 23,但**哪一个是投产二进制的值不可判定**
(`00` §10.2 六项之一)。
★ **`16` §11 待补 5 的建议:取 8.0 血统的 23,以与数据基线一致。**

### 5.2 扇出的代价结构

```c
for (i = x−SEE/2; i <= x+SEE/2; i++)
  for (j = y−SEE/2; j <= y+SEE/2; j++)
    for (object = 该格对象链首; object; object = 下一个)
        /* 逐个判类型,是玩家则发包 */
```

⇒ ★ **每次广播 = 529 次格子查表 + 每格遍历该格的对象链。**
★ **只有外两层是常量界(23×23),内层是链表长度。**

| 原语 | 8.0 扫格数 | 调用点数 | 用途 |
|---|---:|---:|---|
| **角色事件广播** | **529** | **66**(★ 8.0 实际 ≤ 62) | 移动、外观、特效、道具、石币 |
| 地图块下发 | **729** | 2 | 进图 / 传送 |

调用点分布前 4:角色主流程 14、战斗 12、行走 9、道具栏 6。

⇒ ⚠️ ★ **一次移动触发一次 529 格扫描 —— 这是真实的热点。**

### 5.3 新实现的三条改法

| # | 改法 | 依据 |
|---|---|---|
| 1 | ★ **保留 CA/CD 聚合思想** —— 周边角色 Appear/Disappear 攒批 flush | 这是原版**唯一的**带宽优化机制 |
| 2 | ★ **格子索引改为按区域维护订阅集合**,不每次全扫视野 | §5.2 的 529 格是可以省掉的 |
| 3 | ★ **频道类广播改订阅制**(`09-social.md` §5) | 除地图局部广播外全是全扫连接表 |

⚠️ **第 2 条要小心**:视野是**连续变化**的(移动一格就有进有出),
订阅集合的维护成本可能高于扫格。★ **判据是"每 tick 有多少实体在动"** ——
而 §4.2 已经把它压到 `EnemyMoveNum`(10)+ 在线玩家数。
⇒ **先按"扫格 + 聚合"实现,把订阅优化留到有实测数据之后。**

### 5.4 每连接缓冲必须重设

`15` §4.3:原版每连接固定 **324–452 KB** 双缓冲,
是 `sizeof(Char)`(12.3 KB)的 **26–37 倍** ⇒ **是每连接成本主项**。

⇒ **新实现按需增长 + 上限熔断。**

### 5.5 ⚠️ 计算量的主项不是玩法

`15` §5.5:51 处容量界循环中 **35 处(68.6%)上限是连接数,其中 19 处在网络层文件**
⇒ ★★ **计算量的主项是网络层轮询,不是游戏世界。**

★ 且**全树零 O(n²)**(容量 × 容量的嵌套循环 0 处)。

⇒ **换任何现代 I/O 模型都是数量级改进**,这一项不构成对技术选型的约束。
