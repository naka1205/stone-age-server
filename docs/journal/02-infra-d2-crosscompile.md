### 9.0.5 ★★ D2 的两端编译已实证 —— 比计划早了一个阶段(2026-09-02)

> **§1.1 关闭的可撤销点只是 D2 的一半。另一半刚刚才被验证,而手段比预想的便宜得多。**

§1.1 的阶段 0.0 回答的是「战斗代码**能不能**纯函数化」——
那是对**原版源码**的静态度量。而 D2 的字面主张是「L3 规则层**双端共享同一份源码**」,
它的另一半是:**一份源码,两端真的编译得起来吗?**

⚠️ 这一问在 2026-09-02 之前**从未被任何一次编译验证过**。
`shared/` 锁 C++17(§9 阶段 1 的注)只是让**服务端的编译器**在 C++17 模式下编它,
不构成"另一端也能编"的证据。

⇒ 客户端仓工程骨架落地当天完成了验证(客户端 `01` §12.2):

| 项 | 结果 |
|---|---|
| `shared/` 被客户端仓独立 `add_subdirectory` 引入 | ✅(⚠️ 先修了一个阻塞,见下) |
| 客户端工程上下文 · C++17 · 客户端告警口径 | ✅ 零告警 |
| ★★ **服务端黄金用例集用客户端工具链编译运行** | ✅ **15 用例 / 2,148 断言全绿** |
| L3 链接进可执行、在引擎主循环里被调用 | ✅ `BootScene` + `--autotest` |

★★ **一个只可能在客户端侧暴露的缺口,当场兑现**:
`shared/CMakeLists.txt` 依赖两样**只在服务端顶层存在**的东西
(目标 `sg_idl`、函数 `sg_apply_warnings`)⇒ 客户端按 DR-TS3 只引入 `shared/` 时
**在配置期就失败**,D2 的物理前提根本走不到编译那一步。
⚠️ 该缺口在服务端侧**无论如何都不会暴露** —— 顶层永远先定义了那两样东西。
已修(`d939247`,两处改成「有就用、没有就就地补」,服务端行为不变)。

⚠️⚠️ **边界必须写清,不得当成"D2 全绿"**:

| 已验证 | **未**验证 |
|---|---|
| 独立可消费性 · 另一工程上下文 · C++17 · 另一套告警口径 · 用例逐位一致 | emcc(wasm,D4 解冻后)· Android NDK |
| ★ **另一套编译器与标准库**(GCC 15 / libstdc++,2026-09-02 补,见 §9.0.6) | |
| ★★ **MSVC / Windows** —— ✅ **2026-09-02 收口**(§9.0.7.1) | |
| L3 运行期可调用、同种子确定性可复现 | |

✅ ~~⇒ ★ **下一个真正有增量的检验是 MSVC**……在跑通它之前,不得把「D2 两端编译成立」
当作已结案~~ —— **已兑现**:§9.0.7 的一次性验证 **11 项全绿**(报告
`tools/win_validate_report.txt`),B 类方言出清。
⇒ ★★ **D2「一份规则两端编译」在桌面三套工具链(Apple clang / GCC / MSVC)上结案。**

⚠️ 结案的边界仍要说清:**emcc 与 Android NDK 未验**,但它们分别绑在 D4 解冻与移动端出包上,
不在当前路径 —— 与 MSVC 当初「挡着关键路径」的性质不同。

### 9.0.6 ★★ 跨编译器验证 —— 在 mac 上关掉 MSVC 的两类风险(2026-09-02)

> **§9.0.5 把「跨工具链」整个记成一笔未知。拆开看,它其实是三类,只有一类真的需要 Windows。**

| 风险类 | 内容 | 需要 MSVC? |
|---|---|---|
| **A 标准库差异** | 隐式包含、传递依赖、ADL(如客户端 `BootScene` 的 `va_list` 只包 `<cstdio>`) | ❌ 换 libstdc++ 即可暴露 |
| **B 编译器方言** | LLP64 · `wchar_t` 宽度 · `min`/`max` 宏 · 两阶段名称查找 | ✅ **只有它需要** |
| **C 浮点逐位一致** | 黄金用例集的全部价值所系;FMA 合并策略三家编译器各不相同**且无告警** | ❌ 换任何编译器都能暴露 |

⇒ 用 **GCC 15.2 / libstdc++** 在 mac 上跑四个组合,A 与 C 两类当场出清:

| 组合 | 结果 |
|---|---|
| 服务端 × Apple clang 21 | ✅ 0 告警 · `ctest` 5/5 |
| ★ 服务端 × GCC 15 / libstdc++ | ✅ 0 告警 · `ctest` 5/5(修完下述缺口后) |
| 客户端 `d2-only` × Apple clang 21 | ✅ 0 告警 · 黄金用例集 1/1 |
| ★ 客户端 `d2-only` × GCC 15 / libstdc++ | ✅ 0 告警 · 黄金用例集 1/1 |

**★ 两笔当场兑现的价值:**

① **A 类实证:GCC 报出 36 处 `-Wshadow`,Apple clang 一处都不报。**
全部来自 IDL 生成物 —— `repeated` 字段的编解码会包一层 lambda,而 lambda 的形参
也叫 `w` / `r`,**遮蔽了外层同名形参**。
⚠️ 修在 **codegen**(`sgidl/cpp.py` 的 `write_elem` / `read_elem` 增流名参数,
lambda 内改用 `we` / `re`),不是修生成物 —— 否则下次 `sgidl_gen.py` 一跑就回来了。

② ★★ **C 类固化:`shared/` 显式关闭 FMA 合并**(`-ffp-contract=off` / MSVC `/fp:precise`)。
GCC 默认 `fast`(跨语句合并)· clang 默认 `on`(仅语句内)· MSVC 默认 `/fp:precise`
⇒ **同一份 `float` 公式可以算出逐位不同的结果,且三家都不会给任何告警。**
实测 2,148 断言在 GCC 下确实全绿,**但那是当前公式恰好没踩到合并点,不是这条性质成立**。
⚠️ 这与 §10.4 的三类静默错误同源;而 `00` §0 已认下 L3 黄金用例集是第 ③ 层
「不可自证」的**唯一**补偿手段 ⇒ 它的逐位一致性不能靠运气。

★ **对排期的后果**:MSVC 从「D2 唯一未出清的风险」降级为「只剩 B 类方言未验」,
⇒ **不必为它切换开发平台**;剩下那一类交给 CI 的 `windows-latest`(前置是欠债 8 的推送)。

> ✅ **后续(2026-09-02 当日)**:用户已把开发环境搬到 Windows ⇒ B 类当场用
> §9.0.7 的一次性验证收口,**没等 CI**。⚠️ 但 CI 的 `windows-latest` 仍要挂 ——
> 一次性验证回答的是「今天这份代码在 MSVC 下成不成立」,**CI 回答的是「明天改了还成不成立」**,
> 两者不可互替。⇒ 该项转入客户端 `01` §13 欠债 8 的后续。

### 9.0.7 ★★ Windows 一次性验证(2026-09-02 用户裁定)

> ⚠️ **上一节的「不必切换平台」是针对「只为验 MSVC」而言的。用户已把整套开发环境
> 搬到 Windows,那是一个独立决定,本节不复议它,只回答:**
> **既然人在 Windows,应该一次性验完哪些东西,然后就能切回 macOS。**

**★ 口径:一次进,一次出。** 目标不是「在 Windows 上继续开发」,
而是**把所有「只有 Windows 能回答的问题」在一趟里答完**,之后开发环境切回 macOS ——
理由与 §9.0.6 相同:B 类方言是**收敛性问题**,答完就不必再答。

#### 清单(`tools/win_validate.ps1` 已把 1–6 全部脚本化)

| # | 检验 | 为什么只有 Windows 能答 |
|---|---|---|
| 1 | 服务端 × MSVC:配置 + 构建 + `ctest` 5/5 | B 类方言的主体 |
| 2 | ★★ **客户端 `d2-only` × MSVC** | **D2 的完整形态** —— 另一编译器 × 另一工程上下文同时成立 |
| 3 | 浮点逐位一致(`/fp:precise`) | ★ 不需额外动作:黄金用例集的期望值是**手算基准**,全绿即等价于与 macOS 逐位一致 |
| 4 | LLP64 / `wchar_t` 数据模型探针 | macOS 是 LP64(`long` 8 字节),Windows 是 LLP64(4 字节) |
| 5 | Python 检查脚本在 Windows 上运行 | 路径分隔符与编码 |
| 6 | ★ **断言防线反向验证** | `sg_enable_assertions()` 的 MSVC 分支(`/UNDEBUG`)**从未执行过**(见下) |
| 7 | ⏸ `sg_engine` / `sg_gameplay` 在 Windows 构建 | **独立未知数,与 D2 无关** —— 阶段 2/3 出包时才需要,不列入本次收口 |

#### ★★ 两个在编写脚本时当场发现并修掉的缺口

> **它们的共同点:两端都是 clang 时永远不会暴露** —— 与 `d939247` 那个
> 「`shared/` 依赖服务端顶层」的缺口是同一族。

**① `cmake/SgWarnings.cmake` 的 MSVC 分支缺 `/utf-8`。**

本仓源码是 UTF-8,而中文**不止在注释里**:

```
TEST_CASE("相克矩阵:与 battle_event.c:922-949 逐项一致")      ← doctest 用例名
assert(false && "相克矩阵与 05-battle.md §3.4 原表不符")        ← 断言消息
```

⚠️ MSVC 默认按**系统 ANSI 代码页**读源文件(简体中文 Windows = 936/GBK)⇒
轻则 `C4819` 刷屏 + 用例名与断言消息乱码,重则某个 UTF-8 字节序列在 GBK 下
被读成尾随反斜杠一类,**直接编译错误**。
★ 客户端 `SgClientWarnings.cmake` **早就有这一行**,服务端漏了。

**② 更要紧的一处:`shared/` 自己没有 `/utf-8`。**

客户端只 `add_subdirectory(shared)` 时**不会**调用任何 `sg_apply_warnings`
⇒ 只补在两仓的告警函数里,`sg_shared` 这个目标本身仍然没有它。
⇒ 已补在 `shared/CMakeLists.txt`,理由与 `-ffp-contract=off` 同类:
**`/utf-8` 决定源文件怎么被解码,是语义不是风格** ——
凡是「消费方不做就会坏」的东西,都得 `shared/` 自己保证(DR-TS3 的承诺)。

#### ★ 第 6 项为什么必须做

`sg_enable_assertions()` 的 MSVC 分支从未执行过。若它在 MSVC 下不生效,
后果与 2026-08-31 服务端踩过的那次**一模一样**:测试照常链接、退出码 0、
打印 OK,**但一条都没验证** —— 而这次我们会把那个绿色读成「D2 在 MSVC 上通过了」。

⇒ 脚本故意把相克矩阵改错一格,**期望测试失败**;不失败才是问题。
⚠️ 这也决定了报告的**归因顺序**:先看 `C4819`(有 ⇒ `/utf-8` 没生效,其余结论全部不可信),
再看第 6 项(失效 ⇒ 所有「通过」都不算数),然后才是逐条方言问题。

⚠️ **修在源码或 CMake,不要为了让它绿而放宽告警口径** —— `/W4 /permissive-` 是
这次唯一一次能用 MSVC 审这份代码的机会。

### 9.0.7.1 ★★ 执行结果(2026-09-02)—— 11 项全绿,但价值在它抓到的 5 个缺口

**环境**(与文档原假设不同,已连带修脚本):

| 检验 | 结果 |

#### ★★ 五个缺口(首跑暴露,已逐个修掉)

| # | 缺口 | 为什么只有这一趟会暴露 |
|---|---|---|
| **1** | ★ 脚本把生成器**写死** `Visual Studio 17 2022`,而本机只有 VS 18 ⇒ **配置期即失败,六项一条都拿不到** | 写脚本时无处可试。⇒ 改为「装了哪个用哪个」,并与 `cmake --help` 的生成器列表求交集(两侧都会漂) |
| **2** | ★★ **第 6 节瞄错了目标** —— 初版打 `sg_rules_battle_test`,但守相克矩阵的 `assert` 在 `tests/contract_smoke.cpp:72`;而黄金用例集用的是 **doctest 的 `CHECK`,与 `NDEBUG` 无关** ⇒ 不论 `/UNDEBUG` 是否生效,改错矩阵它都会红 | ⚠️ **那样得到的「失败」证明不了断言有效,反而会把假阳性读成「断言在 MSVC 下有效」** —— 这正是本节要防的错误,只不过发生在**上一层**。⇒ 改打 `contract_smoke`,并按「失败+见 `Assertion`」「通过+见 printf」分辨四种结果 |
| **3** | 注入模式找 `1.5f`,而 `kElementMatrix` 是 **`double`** ⇒ 源码里根本没有 `1.5f`,**本节从未真正执行过**(首跑记为「跳过注入」) | 与 #2 叠加:一个瞄错靶、一个没开枪 |
| **4** | ★ **两个 Python 检查脚本在简中 Windows 上不可用** —— 控制台 cp936,而输出含 `✅`/`★` ⇒ `print` 抛 `UnicodeEncodeError`:**通过时崩在成功那一行(退出码 1,CI 报「D2 的守卫失败」而它其实通过了)**;失败时崩在打印违规清单那一行(看到 traceback 而不是「D2 被破了」) | ⇒ 两种情况**都读不出真相**。已在脚本内 `reconfigure` 到 UTF-8 —— 与 `shared/` 自己给 `/utf-8` 同理:凡「消费方不做就会坏」的,自己保证 |
| **5** | ★ 脚本用 `-match 中文关键字` 判两件事,而 PowerShell 5.1 用 **cp936** 解码子进程输出(我们的子进程输出是 UTF-8)⇒ 匹配永不命中。**其中一条正是「相克矩阵重排错误被打印」= 断言被编译掉这一最危险结果的探测分支** | ⇒ 统一 `chcp 65001` + `[Console]::OutputEncoding = UTF8`。与 `/utf-8`、`-ffp-contract=off` 同类:**决定「字节怎么被解释」的都是语义,不是风格** |

★ 另修两处报告可信度问题:① **清洁构建**(不清则第二次跑「告警 0 条」是假证据 —— 增量什么都没重编);
② `@(...)` 包住计数(PowerShell 单项筛选返回标量,`.Count` 取不到 ⇒ **失败恰好一条时汇总印成「失败 」空白**,
一份藏起失败条数的报告不配当凭据)。

#### ⏭ 一项本趟**未验**,须显式记下

**`idl_verify`(schema 与生成物同步)未运行 —— 本机无 `protoc`。**

★ 这不是缺陷:`protoc` 是**构建期工具**(DR-TS1 边界 ①:运行时不链接 libprotobuf;
DR-TS2:生成物入库)⇒ **只消费生成物的人根本不需要装它**,「本机没有」是正常状态,
且它**与 B 类方言正交**,不在本趟收口范围。

处置(两条,已落地):
- `sgidl_gen.py` 缺 `protoc` 时给**一句能照着做的诊断**并支持 `PROTOC=<路径>`,不再抛 `WinError 2` traceback;
- `tests/CMakeLists.txt` 按「Python3 缺失」的既有先例:**不注册该测试 + `message(WARNING)`**,
  而不是留一条常红 —— 常红会训练人忽略红色,而本仓最怕的恰是把绿/红读错(§10.4)。
- ⚠️ **但 CI 上必须有 `protoc`**,否则这道关会**静默消失**,那比常红更坏。

### 9.0.17 ★★ CI 首次覆盖 GCC/MSVC —— 一条注释承诺了三年、代码从未兑现的语义(2026-09-06)

> **§9.0.16 的提交信息里写着「只在 Apple clang 跑过,GCC / MSVC 交 CI」。
> 那是一句**承诺**,而它的兑现前提是推送 —— 不推,`e56e61a` 就永远停在
> 「一套工具链验过」的状态。本节是推送之后的第一手结果。**

#### ① 红的形状本身就是诊断:单平台特异

| 平台 | 结果 |
|---|---|
| Linux · GCC | ❌ **清洁构建失败** |
| macOS · Apple clang | ✅ 六项全过 |
| Windows · MSVC | ✅ 六项全过 |

★ 与 §9.0.10 那次(三平台**同一步同一原因**)恰好相反:那次的同步同因说明与编译器无关
(根因是跨仓可见性);**这次的单平台特异说明它就是编译器差异** ——
⇒ 归因方向一开始就定了,不必先怀疑代码逻辑。

```
tests/world_tick_test.cpp:372:14: error:
    'b.sa::domain::BattleTurnBegin::turn' may be used uninitialized
    [-Werror=maybe-uninitialized]
```

`-Wmaybe-uninitialized` 是 **GCC 特有**且**依赖 `-O2` 的数据流分析**
(`RelWithDebInfo` 才有)⇒ clang 与 MSVC 一个字都不说。
⚠️ **不是它们对,是它们的分析没走到这一步。**

#### ② ★★ 根因:注释里的承诺,与生成物的形状相反

`sa_idl_runtime.h` 的 `Reader` 卷首从第一天就写着:

> 任一次越界读都会置错误位并**返回零值**;后续读取全部短路。
> ⇒ 解码失败是「整条消息作废」,不存在「部分成功」的中间态。

而 codegen 生成的 `decode` 是这样:

```cpp
inline void decode(sa::idl::Reader& r, BattleTurnBegin& m) {
  m.battle_id = r.u64();
  if (!r.ok()) return;      // ← ★ 早退。turn 与 ready_mask 从此保持**未初始化**
  m.turn = r.u32();
  if (!r.ok()) return;
  m.ready_mask = r.u32();
}
```

⇒ ★★ **「作废」的实际含义是「首字段是真值 / 尾字段是垃圾」,而不是承诺的全零。**
Reader 精心设计的「短路返回 0」被早退整个绕过了。

★ **一处印证根因的细节值得记**:GCC 只报 `turn`,**不报 `battle_id`** ——
因为首字段在第一次早退**之前**赋值,必然被写;从第二个字段起才存在"不写"的路径。
⇒ 诊断的形状与根因严丝合缝,不是误报。

#### ③ ★ 同族静默失效的第七种形态

| 形态 | 缺的是 |
|---|---|
| A(§9.0.12) | 报告印的是硬编码文本,不是观测 |
| B(§9.0.13) | 观测是真的,没断言它 == 期望值 |
| C(§9.0.14 ③) | 动作做了,没有东西观测结果 |
| D(客户端欠债 15) | 观测对象在到达检查前被清空 |
| E(§9.0.16 ①) | 消费侧齐备、生产侧从未接上 |
| F(§9.0.16 ⑤) | 动作被看见了没 —— "现在"的分辨率由构建系统说了算 |
| ★ **G(本次)** | **契约写在注释里,没有任何东西检查代码是否兑现它** |

⚠️ G 的隐蔽处:那句注释**读起来像是在描述代码**,而它实际上是在描述**意图**。
两者分叉之后,注释不会变红,而代码也不会。
⇒ 它靠一个**外部编译器的可选诊断**偶然抓到 —— 那是运气,不是防线。

#### ④ 修法:去掉早退,而不是给 79 个 struct 加默认初始化器

两条路都能让 GCC 闭嘴,但只有一条修的是根因:

| | 做法 | 评价 |
|---|---|---|
| NSDMI | 给每个字段加 `= 0` / `{}` | ⚠️ ① **每次声明都要零初始化整个 `FixedVec<BattleEvent, 256>`(≈10 KB)**;② `is_trivial` 变 false,削弱 DR-TS1 边界 ② 的「纯 POD」;③ 它是在**每个消费点**补一层,根因(早退违背短路设计)还在 |
| ★ **去掉早退** | `decode` 无条件写满整个 struct | ✅ 失败时每次读短路返回 0 ⇒ 全部标量字段无条件被赋值。**零内存成本 · POD 性质不变 · 修的是根因** |

⇒ 采用后者。⚠️ 认下的代价:失败路径上会多走完剩余字段的短路读(每字段一个分支);
`repeated` 反而更便宜 —— count 短路读回 0 ⇒ 循环零次。

★ **`is_trivially_copyable` / `is_standard_layout` 两条既有 `static_assert` 不受影响**
(`idl/tests/smoke.cpp` §①),这是选型前先验证的,不是事后发现没坏。

#### ⑤ ★★ runtime 自己有两处同族漏洞,其中一处后果比原始缺陷更重

去掉生成代码的早退只解决了三方配合里的一方。`read_str` / `read_vec` **各自的失败路径
原先一个字段都不写**:

| 函数 | 失败时 | 后果 |
|---|---|---|
| `read_str` | `len` 与 `data` 都不写 | `c_str()` 返回一个**没有终止符**的指针 ⇒ **越界读**,比读到错的数值更坏 |
| ★★ `read_vec` | `count` 不写 | `end() = data + count` ⇒ **一次 range-for 就按垃圾长度遍历** |

⇒ 处置:两者在函数**开头**先置零(`len = 0; data[0] = '\0';` / `count = 0;`),
代价合计不到 5 个字节的写。
★ `read_vec` 置零同时让它保留的那条早退变得安全 —— 失败时写了一半的元素
**不可达**(count 仍是 0),不必为了"写满"去读完剩下的 256 个元素。

#### ⑥ ★★ 用例的手法才是这批真正买到的东西

⚠️ `smoke.cpp` **原本就有两段截断测试**,而它们**挡不住这个缺陷**:

```cpp
domain::WindowOpen tmp{};   // ← 已经全零
decode(rt, tmp);
assert(!rt.ok());           // ⇒ 即使 decode 一个字段都不写,也照样通过
```

⇒ 那两段挡的是「越界读」,不是「字段没被写」。**新用例的全部价值在一个手法上:
被测对象必须先填成非零。** 任何字段漏写就会保留那个显眼的值 ⇒ 当场红。

四条,按后果排:

| # | 钉住的性质 |
|---|---|
| ③ | ★★ `FixedVec` 失败 ⇒ `count == 0`(防越界遍历) |
| ② | `FixedStr` 失败 ⇒ `len == 0` **且 `c_str()[0] == '\0'`** —— 两条分开断言,len 归零不代表 data 可用 |
| ① | 纯标量消息(正是 GCC 点名的 `BattleTurnBegin`)⇒ 三个字段全为 0 |
| ④ | oneof 未知 tag ⇒ `fail()` 且 tag 归 `NONE`,不留旧值 |

★★ **反向验证(把早退注回 codegen)⇒ 两道防线同时报红**:

| 防线 | 报的 |
|---|---|
| GCC `-Wmaybe-uninitialized` | `world_tick_test.cpp:372` 原样重现 |
| ★★ **新用例** | `Assertion failed: (b.turn == 0) ... smoke.cpp:254` |

⇒ **第二条才是增量** —— 它不依赖 GCC,在 clang / MSVC 上一样会红。
这就把「一个外部编译器的可选诊断偶然抓到」变成了「三平台都守得住」,
正是 ③ 里 G 型缺的那道防线。
★ 还原后 codegen 与注入前逐字节一致,GCC 复跑 0 告警 · `ctest` 11/11,工作树无残留。

#### ⑦ 诚实标注:一处改动在今天的 schema 下**行为不可区分**

同批把 oneof `default:` 的 `return` 换成了 `break`(让 oneof 之后的字段仍被写)。
⚠️ **当前 schema 下这一改验不到** —— 4 个含 oneof 的消息
(`BattleEvent` / `BattleCommand` / `WindowOpen` / `WindowReply`)里 oneof **都排在最后**,
后面没有字段。⇒ 它防的是**将来往 oneof 之后加字段**的那一天,而那时不会有任何东西报错。
★ 这条标注同时写进了 `cpp.py` 与 `smoke.cpp` ④ —— 不写下来的话,
下一个读到 `break` 的人会以为它被验过。
