### 9.0.2 ★ 0.1 的前置比原先记载的多一项(2026-08-31 实测)

> **§9.0.1 说「0.1 与 IDL 正交,可并行」。做到一半发现:它还差一样东西。**

`05` §1.5 的 L3 契约是 `resolve_turn(BattleSnapshot, Commands, IRandom&) -> BattleEvents`。
落地时三个输入的实际状态是:

| 输入 | 状态 |
|---|---|
| `Commands` | ✅ IDL `domain::BattleCommand` |
| `BattleEvents` | ✅ IDL `domain::BattleEvents` |
| `IRandom` | ✅ 1.0 已落地 |
| **`BattleSnapshot`** | ⚠️★ **一直没有定义** |

⚠️★ **一处必须记住的同名陷阱**:IDL 里那个 `domain::BattleSnapshot` **不是**它。

| | `domain::BattleSnapshot`(IDL) | `rules::BattleField`(L3) |
|---|---|---|
| 用途 | **下行显示**快照(原 `BC` 子命令) | **结算输入** |
| 内容 | 名字 / 等级 / HP / 标志位 / 骑宠显示,13 字段 | 攻防 / 敏捷 / 幸运 / 四属 / 装备修正 |
| 谁消费 | 客户端渲染 | `ResolveTurn` |

⇒ **一个是"给人看的",一个是"拿来算的",故意不复用同一个类型。**
1.0 已按后者定义 `rules::BattleField` / `rules::Combatant`,**0.1 的前置至此齐备**。

### 9.0.3 ★★ 0.1 的产物形态 —— 一遍到位,不做中间态(2026-08-31 裁定)

> **一处此前从未被回答的问题:四步改造改的是哪份代码?**
> 它不是细节 —— 答案不同,最大的一笔工作要做一遍还是两遍。

**问题的来源**:`stoneage-plan/00` §9.2 把 1.1 描述为
「**从 0.1 改造后的代码提取**」⇒ 读起来是两段式:

```
原版 battle/*.c  ──四步机械改造──▶  改造后的 C 代码  ──提取──▶  shared/rules/*.cpp
                     (0.1)                                (1.1)
```

⚠️ **这条路径与 P1/P2 冲突**:

| # | 冲突 |
|---|---|
| ① | **P1 原版不可运行、P2 不编译** ⇒ 中间那份"改造后的 C 代码"**永远无法编译、无法测试、无法回归**。它是一份纯手工产物,正确性完全无人接住 |
| ② | ★ §1.3.1 的 720 处真状态写、429 处串缓冲是**在原版代码上**数的 ⇒ 走两段式,这些点要**编辑两次** |
| ③ | 中间态没有验收口径。§9.0 已定「1.4 验收**改造后代码的实际形状**」,而 1.4 验收的是 `shared/rules` 里的东西,不是那份中间 C |

✅ **裁定:0.1 与 1.1 合并为一件事,一遍到位。**

```
原版 battle/*.c  ──按四步的目标形态直接移植──▶  shared/rules/*.cpp
        (只读的规格说明书)                        (唯一产物,可编译可测试)
```

⇒ **四步不再是"四轮编辑",而是移植时必须同时满足的四条形态要求**:

| 步 | 移植时的形态要求 |
|---|---|
| ① | 原版靠 10 个 `g*` 隐式传参的量,一律进 `ResolveTurn` 的显式参数或局部结构体 |
| ② | 原版 `CHAR_set*` 写世界状态的地方,一律 `out.events` 追加事件 |
| ③ | 原版 `BATTLESTR_ADD` / `sprintf` 拼串 + `lssproto_*_send` 发包的地方,一律追加事件,序列化留给调用方 |
| ④ | 原版 `RAND()` / `rand()` 一律走注入的 `IRandom&` |

★ **§1.3.1 的点数仍然有效,含义变了**:它们不再是"要改多少处",而是
**"移植时会遇到多少处需要按上表转形的地方"** —— 是**工作量刻度与自检清单**,
不是编辑动作的计数。

⚠️ **一处代价必须认下**:两段式的理论好处是「机械改造比重写更不容易改错语义」。
放弃它之后,防线只剩下:
① 四步都不动公式(`05` §1.2,原则不变);
② ★ **L3 黄金用例集** —— `00` §0 已明写它是 ③ 层"不可自证"的**唯一补偿手段**;
③ `tools/check_shared_purity.py` 守住依赖边界。
⇒ **黄金用例集从"建议做"升级为"与移植同步进行的硬要求"**,不可留到移植完再补。

⇒ 阶段表中 **0.1 与 1.1 合并记为 `0.1/1.1`**;`01` §13 欠债 1 同步。

### 9.0.14 ★★ 1.5 收尾 —— TcpTransport 接入入口,并修掉一处会污染构建目录的反向验证(2026-09-05)

> **1.5 至此完整**:`src/{platform,net,world}` + `main.cpp` 四个切面齐备,进程开始监听端口。
> ★ 关键路径上剩下的**只有 1.4**;其客户端侧被一条本轮新登记的待拍板挡着(DR-TS9,见 ④)。

#### ① TcpTransport:与 `01` §12 技术栈表的字面偏离,由用户裁定(DR-TS8)

`01` §12 与本文 §8 写的是「asio + C++20 协程」,落地的是**原生 socket + `poll(2)`,单线程 reactor**
(用户 2026-09-04 裁定)。三条理由按分量:

| # | 理由 |
|---|---|
| ① | ★ `ITransport::Poll()` 的契约(主线程 tick 第 2 步调用、不得阻塞)**本来就是 reactor**。asio 协程的价值在这个接口下发挥不出来:要么改接口让 `io_context` 独占一个线程(推翻 `01` §2 的线程模型),要么退化成 `io_context.poll()`,那只是把下面这段 poll 包了一层 |
| ② | 它会是 `src/` 的**第一个运行时第三方依赖**(doctest 只进 `tests/`)⇒ FetchContent + 三平台 CI 是一笔独立的引入成本 |
| ③ | ★ 与 `platform/api.h` 日志那处偏离(不引 spdlog)**同一条先例**:接口先立死、库延后引 —— `ITransport` 已把替换成本压到局部,换 asio 不动上层一行 |

认下的代价:`poll(2)` 是 O(连接数),上规模时要换 epoll / kqueue / IOCP —— 登记为 `01` §13 欠债 13。
⚠️ 但 `01` §5.1 批的是原版「每连接一次 `select`」(1000 连接 = 1000 次系统调用),poll 一次调用传整个数组已经不同量级。

★ **当初的切分买到了什么**:成帧、会话、编解码接入此前已在 Loopback 上被 18 条用例钉死
⇒ TcpTransport 落地时**上层一行没动**,新代码里出的错只可能是 socket 那一层的,归因面小一个数量级。
13 条真 socket 用例:监听 / accept / 分片到达 / ★ 出站背压与续写 / 优雅关闭 / Stop / ★ 端到端握手成功与版本不符拒绝。

⚠️★ **一条用例本轮修过,值得记**:「大负载往返」首版固定灌 3 MB、对端不读、断言 `pending > 0`,
本机约 **1/6 概率红** —— 内核把 3 MB **全吃下了**(macOS / Linux 的收发缓冲会自动调大,上限因系统与版本而异)。
⇒ 两手:客户端显式设小 `SO_RCVBUF`(显式设置会**关掉**自动调大 ⇒ 对端窗口有已知上界)+ 负载按 256 KB 递增灌到「写不动且 pending > 0」为止(上限 3.75 MB 压在 4 MB 熔断之下)。
**「背压发生了」由用例制造出来,不赌内核的缓冲策略。** 30 次连跑全绿。
★ 偶发红是 §10.4 最难归因的那类红(net_tcp_test.cpp 卷首自己就写了这句),不能带进 CI。

#### ② 入口接线:`01` §11.1 的第 6 步

`main.cpp`:构造 `TcpTransport` → `Listen(bind_addr, port)` **失败即拒绝启动**(退出码 1,`listen_failed` 事件带 errno 文本)
→ 构造 `World` → 挂 SIGINT / SIGTERM → tick 循环(按**绝对期限**睡到下一拍,不把 Tick 耗时累积成漂移)
→ 信号 ⇒ `RequestShutdown` ⇒ 同一 tick 的第 8 步关闭全部连接 ⇒ `Stop` 传输层 → 退出码 0。
新增日志事件 `listen_failed`(7)/ `shutdown_signal`(8);配置面只多了 `bind_addr`(默认 `0.0.0.0`)——
配置与日志此前有意先立对,接线那天果然一处没改。

★ **入口首次有了测试**:`server_self_test` = `--self-test`(绑**系统分配**的端口 → 跑够一个战斗回合间隔 → 关闭 → 退出码 0),`ctest` 11 项。
⚠️ 端口取 0 不取配置值是有意的:自检要能在 CI 上并行跑而不撞端口,它证明的是「入口能启动、能监听、能停」,不是「8300 空着」。

| 路径 | 结果 |

#### ③ ★★ 顺带抓到的:`ci_verify.py` 的反向验证会把改坏的产物留在 build 目录里

**起因**:收尾开工前例行跑 `ctest`,`contract_smoke` 与 `rules_battle` 都报「相克矩阵 [攻0][守1] 得 9.9 应 1.5」。
9.9 正是 §5 反向验证**故意注入**的值,而源码 `constants.h` 与 git 一致。

**根因**:还原用的是 `shutil.copy2` ⇒ 备份的 **mtime 一并被还原** ⇒ 还原后的头文件比注入期间编出的 `.o` **更旧**
⇒ make / ninja 判定产物是新的、不重编 ⇒ `sa_shared` 里改坏的 `battle.cpp.o` 原样留在目录里。
且那句「还原后重建,避免留下改坏的产物」的 `--target` 只指了 `sa_contract_smoke`,对 `rules_battle` 链的那份 `sa_shared` 无能为力。
⇒ 下一个在同一目录做增量构建的人,会看到一条**与自己改动毫无关系的红**。

★★ 它与 §9.0.12 / §9.0.13 同族,是**第三种形态**:

| 形态 | 缺的是 |
|---|---|
| **A**(§9.0.12) | 报告印的是硬编码文本,根本不是观测 |
| **B**(§9.0.13) | 观测是真的,没断言它 == 源码里写的期望值 |
| **C**(本次) | ★ **动作做了(还原),没有任何东西观测它的结果(产物干净了没)** |

修法三步,每步对应一种失效:① `write_bytes` 还原(mtime = 现在,构建系统才看得见文件变了);② 重建**整个**目录,不是单个目标;
③ 复跑 `contract_smoke` + `rules_battle` 并**断言回到绿** —— 「还原了」是动作,「产物干净了」才是结论,中间要有一次观测。

**反向验证**:用驱动脚本把还原换回旧写法(copy2 + 只重建探针),新加的观测**确实报红**并点名残留;
换回新写法后 `ci_verify` 6/6,且**之后再跑 `ctest` 11/11** —— 这一条在修复前是做不到的。
⚠️ 客户端仓的 `ci_verify.py` 没有反向验证步骤,不受影响。
⚠️★ 附一条操作纪律:**反向验证会临时改源码,它在哪个目录跑,那个目录就要在结束后被证明是干净的** —— 今后凡「改源码 → 编 → 还原」形状的检查都按本节三步写。

#### ② ★★ 客户端侧前两层零引擎依赖 —— 这决定了 1.4 的验收口径能不能进 CI

| 层 | 能否进 CI | 为什么 |
|---|:-:|---|
| 协议层(`client_net`,7 用例 / 263 断言) | ✅ | 合成服务端出站字节即可全覆盖 ⇒ 零 socket、零服务端、零窗口 |
| ★ 装配层(端到端) | ❌ | 需要一个**跑着的服务端进程** |

★ 前者与本仓 `tests/world_tick_test.cpp` 的 `ClientMirror` 是**同一手法的镜像**:
那边「用客户端的方式读服务端」,这边「用服务端的方式喂客户端」。
⚠️ 两者**不可互替**:协议层证明解析正确,装配层证明那条链**接对了** ——
而后者恰恰是本批次三个缺口的全部所在(见 ③)。
⇒ 已登记为客户端欠债 16:**装配层每次改动须本地手工复跑一次**。

#### ③ ★★ 三个缺口:全部只有真跑才会暴露,且一个都不报错

| # | 缺口 | 为什么静默 |
|---|---|---|
| 1 | `_info` 在 `initScene()` **之后**赋值,而拨号在其内 | 报 `connect :0 失败` —— **文本看起来像网络问题**,与「配置还没读进来」毫无关系;空 host + 0 端口是一次合法的 `connect` |
| 2 | ★★ **握手在帧循环里抢跑** | 非阻塞 `connect` 期间 `Send()` 按契约拒绝入队,而那一帧**同时置位 `_handshakeSent`** ⇒ 握手包被丢掉且永不重发。服务端侧表现为 `accept` 后立刻 `closed` ⇒ 改由 `OnConnected` 驱动:**连接确立是事件,不是可以轮询猜的状态** |
| 3 | ★★ 引擎的 `scheduleUpdate()` 漏调 | `override` 了虚函数**但没人调它** —— 无编译错、无运行错,900 帧后仍停在 `dialing`,而网络代码 / 握手时机 / 配置全都是对的 |

★ 另修一个**既有**缺陷,由本批次构建暴露:客户端 `BootScene.cpp` 的
`SG_LOG_ERROR` / `SG_LOG_INFO` 被 §9.0.11 的 DR-TS7 改名**一并改成了 `SA_LOG_*`**,
⚠️★ **而那两个宏是引擎提供的** —— `SG::` 是 `SG::Engine` 的前缀,不属于本项目,
改名的作用域本不该覆盖它。`SA_LOG_*` 从未在任何地方定义。

⚠️⚠️ **它自改名(2026-09-04)起就编不过,两天无人发现** —— 因为 `BootScene.cpp`
只在 `SA_CLIENT_WITH_ENGINE=ON` 时编译,而 CI 跑 `d2-only`(**不建 core 与入口**)。
⇒ 这是 §9.0.11 那批改名**第二次**兑现「按名字匹配的地方要同批改」那条纪律的代价
(第一次是 §9.0.12 的 `-DSG_WERROR`),而这一次的新形态是:
**改名放宽到了不属于本项目的符号上 + 唯一能发现它的构建路径不在 CI 上。**
★ 后半句才是要记的那一半 —— 客户端欠债 10「引擎前缀是机器本地状态,未纳入自动化」
原写的代价是"干净机器上跑不起来",实测代价比那句重:**那一半代码没有任何守卫。**

#### ④ ★ 一处判据修正:「跑完」不能定义成「服务端断连」

初版等断连。⚠️ 实测**服务端 1.4 打完一场后既不下发 `BattleLeave` 也不关连接**,
会话停在 `online`(结束通知属阶段 2)⇒ 客户端会一直等到帧数耗尽。
⇒ 判据改为客户端侧可观察的事实:已进场 + 至少两条 `BattleEvents` 被逐条消费。
★ 这与 1.4 的验收口径本来就一致(**事件流端到端一致**),不需要"战斗结束"这个概念。

⚠️ 顺带修了客户端 `Poll()` 的一个真缺陷:读条件只看 `POLLIN`,而
**macOS 上对端关闭时 `revents` 只有 `POLLHUP`** ⇒ `recv` 永不被调用、客户端静默挂住。
★ 改成 `(POLLIN | POLLHUP)` 且**仍走 `recv`** 而不是直接判死 ——
`POLLHUP` 时缓冲里可能还有未读完的事件流,先读干净再收尾,否则会丢掉结局。
