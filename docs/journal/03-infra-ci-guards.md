### 9.0.9 ★★ CI 挂载(2026-09-03)—— 从「今天成不成立」到「明天改了还成不成立」

> **§9.0.7.1 的一次性验证与本节回答的不是同一个问题,两者不可互替。**
> `01` §13 欠债 7 把这一条一直留着没关,理由就是这个。

**平台 = GitHub Actions**(用户 2026-09-03 裁定)。两仓的主 remote 仍是 gitee,
GitHub 是**为 CI 而设的镜像** —— 欠债 7 要的 `windows-latest × MSVC` 只有它有,
而 B 类编译器方言恰恰只有 MSVC 能验。

| 仓 | job | 矩阵 |
|---|---|---|
| 服务端 | `verify` | ubuntu(GCC)· macos(Apple clang)· windows(MSVC) |
| 客户端 | `d2-gate` | 同上三平台,跑的是**客户端工具链下的黄金用例集** |

⇒ 正好覆盖 §9.0.7.1 结案时的桌面三套工具链。

**★★ 判定逻辑不在 YAML 里,在 `tools/ci_verify.py`(两仓各一份)。**

| # | 理由 |
|---|---|
| ① | CI 平台会换,**验收内容不该跟着换**。YAML 一旦成为唯一真源,本地就无法复现 CI 的判定,「在我机器上是绿的」会变成常态 |
| ② | ★ 其中两项**不是跑命令、是做判断**(下表 ①②),在 YAML 里写不下 |

**★★ 本次真正新增的三道守卫 —— 都不是"把已有命令搬上 CI"**:

| # | 守卫 | 它挡的是什么 |
|---|---|---|
| ① | ★★ **测试注册清单断言**(`EXPECTED_TESTS`,5 条) | `tests/CMakeLists.txt` 里 `shared_purity`(需 Python3)与 `idl_verify`(需 protoc)是**条件注册**的,缺依赖时不注册而非常红。⇒ CI 镜像哪天不带 protoc,那道关**静默消失**,而 ctest 照样打印 `100% tests passed`。欠债 9 的原话「那比常红更坏」——★ 现在它是一条会失败的断言。⚠️ 装了 protoc ≠ 它生效,**真正接住这件事的是这条断言,不是 workflow 里的安装步骤** |
| ② | ★ **断言防线反向验证**(跨平台移植自 `tools/win_validate.ps1` §6) | 故意改错相克矩阵一格,期望 `contract_smoke` **失败**;不失败才是问题。它守的是 `sg_enable_assertions()` —— 而**那个函数自己此前没有任何东西守着**。四态判别(assert 触发 / 被编译掉 / 注入没进产物 / 注入方式有问题)原样保留 |
| ③ | ★ **`SG_WERROR`**(新增 option,本地 OFF / CI ON) | 「0 告警」在 §9.0.5–§9.0.7.1 被当凭据用了四次,但**至今没有任何机制保证它继续为真** —— 告警只是滚过屏幕的文字。⇒ CI 上让告警中断构建,那句话才是可持续的。⚠️ 认下代价:runner 的编译器随镜像升级(GCC 13→14→15),新版本常带来新告警 ⇒ CI 可能因**编译器升级**而非代码改动变红。接受 —— 那种红值得看一眼;不可接受的是反过来 |

**★★ 一处当场兑现:发布态首次被真正执行(客户端 `01` §13 欠债 12 当场关闭)。**

`SgShared.cmake` 的模式选择是「同级目录有 `stone-age-server` ⇒ 联调态」
⇒ **两仓并排放置的开发机上,发布态分支永远走不到**,而 DR-TS3 的裁定形态
**正是发布态**。⇒ 那条路径此前从未被任何一次配置执行过,而客户端 CI 完全押在它上面。
本次在一个无同级服务端仓的临时目录里真跑了一遍:

| 项 | 结果 |
|---|---|
| `FetchContent` 从 GitHub 镜像取 `shared-v0.1.0` | ✅ **发布态,锁定 ref 解析成功** |
| 清洁构建(`SG_CLIENT_WERROR=ON`) | ✅ 0 告警 |
| 黄金用例集 | ✅ 33 用例 / 2,276 断言 |

⇒ ★ **DR-TS3「FetchContent + 锁定 tag」从纸面裁定变成实证。**
★ 不为它加"强制发布态"开关 —— CI 是干净克隆,天然走发布态;
本地走联调态。两条路径各有其执行场所,零额外机关。

⚠️★ **一条由 CI 平台带来的新持续耦合,别踩**:

```
gitee(主 remote)  ←─ 日常推送
GitHub(CI 镜像)   ←─ ★ CI 从这里拉代码,且客户端 CI 从这里 FetchContent 服务端的 tag
```

⇒ **锁定的 tag 必须同时存在于两个远端**,否则会出现一种很难诊断的红:
服务端「明明已经发布了」,而客户端 CI 报 ref 找不到。
⇒ 「服务端提交 → 客户端复验 → 前推 ref → **两仓 × 两远端**一起推」是一个整体动作。

✅ **2026-09-03 已自动化,不再依赖人记住**:两仓 `origin` 配置了**双 push URL**
(gitee + GitHub)⇒ `git push origin master` 与 `git push origin <tag>` 一次推两端,
`fetch` 仍只走 gitee。★ 口径由此明确为 **「只维护 gitee 仓库」**(用户 2026-09-03):
GitHub 侧不开 issue / 不开 PR / 不建分支,它只是 CI 的取件口。
⚠️ 但**不能因此认为 GitHub 侧无需关心** —— 见 §9.0.10 的第二面。

### 9.0.10 ★★ CI 首跑归因(2026-09-03)—— 服务端全绿,客户端红在一条 17 份文档都没记过的耦合上

> **§9.0.9 交付的是「脚本 + YAML」,本节是它们**第一次真被执行**的结果。**
> 欠债 10 的原话「『脚本写好了』和『脚本真跑过一次』之间隔着五个缺口」——
> 结果是:预判的三种红**一个都没发生**,而真正的红是**预判之外**的。

**✅ 服务端 `verify`:三平台全绿,五项全过**

| 平台 | protoc | 结果 |
|---|---|:-:|
| Linux · GCC | 3.21.12 | ✅ |
| macOS · Apple clang | 35.1 | ✅ |
| Windows · MSVC | 36.1 | ✅ |

五项:配置(`SG_WERROR=ON`)· ★★ 测试注册清单 5 条全注册 · 清洁构建 0 告警 ·
`ctest` 5/5 · ★ 断言防线反向验证。
⇒ **欠债 7 的 ② 与欠债 10 的服务端侧关闭。**

★ **一笔意外的凭据,值得单独记**:`protoc` 从 **3.21 到 36.1 跨了一个大版本时代**,
`idl_verify` 仍然过 ⇒ **生成物不依赖特定 protoc 版本**。这一条此前是未知的
(欠债 9 只处置了「本机没有 protoc」,从未回答「版本差异要紧吗」),
而它恰好由三个 runner 镜像自带的三个版本免费验了出来。

**❌ 客户端 `d2-gate` 首跑:三平台同时红 —— 而这个形状本身就是诊断**

```
fatal: could not read Username for 'https://github.com'
Failed to clone repository: 'https://github.com/naka1205/stone-age-server'
  at cmake/SgShared.cmake:80 (FetchContent_MakeAvailable)
```

三平台**同一步、同一原因**(措辞只差在系统层:`No such device or address` /
`Device not configured` / `No such file or directory`)⇒ 与编译器差异无关。

★★ **根因:两个镜像仓当时都是 private,而 runner 的 `GITHUB_TOKEN` 只授权它自己那一个仓。**

⚠️★ **这是 §9.0.9 那条耦合的第二面,而 17 份文档里没有一处记过它**:
上面只写了「锁定的 tag 必须同时存在于两个远端」—— 而 tag 一致性当时**是满足的**
(`f615ccd → 5c8f69d`,gitee 与 GitHub 都有)。真正缺的是**跨仓可见性**。

⇒ **处置(用户 2026-09-03 裁定):两个 GitHub 镜像仓改为 public。**
备选是给客户端仓加一个只读 PAT secret + `url.insteadOf` 注入(3–5 行 YAML,不动 CMake),
未采纳的理由是 PAT 会过期、且多一处机器本地状态之外的凭据要管;
而镜像仓本就只承载 CI,主 remote 仍是 gitee。

**✅ 重跑结果(run `33749020925`):三平台全绿。**
★ 按 §12.6「`ctest` 只看退出码,一个完美的绿色而 D2 什么都没验」的同一条纪律,
**取日志逐项核验它到底验到了什么**,而不是相信绿灯:

| 守卫 | 日志实证 |
|---|---|
| ★ 接入模式 | `shared/(D2)= 发布态(FetchContent + 锁定 ref)` · `锁定 ref: shared-v0.1.0` · `--expect-mode fetch` 通过 |
| 只建闸门 | `SG::Engine 未找到 ⇒ 只建 sg_shared + 黄金用例集`,跳过 core 与入口 |
| ★★ 用例集规模 | `test cases: 33 \| 33 passed` · `assertions: 2276 \| 2276 passed` |
| `ctest` | `100% tests passed, 0 tests failed out of 1` |

⇒ ★★ **欠债 10 关闭(客户端侧同步关闭其欠债 13)。CI 从"写好了"变成"在验着"。**

⚠️★ **一条随裁定而来的新约束,别忘**:~~镜像仓~~ public 是客户端 CI 成立的**前提**,
不是无关的仓库设置 ⇒ **哪天把它改回 private,`d2-gate` 会立刻回到上面那个红**,
且报错措辞(`could not read Username`)与"权限设置"看不出任何关系。
⇒ 要改回 private,必须**同时**落地 PAT secret 方案。

#### ★ 该约束的作用面比上一段写的窄 —— 只落在**服务端仓**(2026-09-04 复核)

上一段说的是「**两个**镜像仓 public」,而 §9.0.10 卷首那句裁定也是这么记的。
**实测两仓当前的可见性并不相同,而 CI 三平台仍全绿**:

| 仓 | GitHub 可见性 | 在这条耦合里的角色 | public 是否必需 |
|---|---|---|---|
| `stone-age-server` | **public** | ★ **被拉方** —— 客户端 runner 用 `FetchContent` 跨仓取 `shared/` | ✅ **必需** |
| `stone-age-client` | **private** | **拉方** —— runner 拉的是它自己,走 `GITHUB_TOKEN` | ❌ **无关** |

⇒ 根因本来就是**跨仓**那一步:`GITHUB_TOKEN` 只授权 runner 自己那一个仓,
所以**只有被拉的那一方需要匿名可读**。拉方拉自己,从来不缺权限。

⚠️ **为什么这处偏差值得改而不是放着**:约束记宽了不会让 CI 变红,
它的代价在另一个方向 —— 它要求客户端仓做一次**它并不需要的对外暴露**,
而"文档说必须 public"会让这个多余的暴露显得是有理由的。
★ 与 §10.4 三类静默错误反向同族:**过宽的约束不会失败,只会安静地多付一笔代价**。

⇒ 口径改为:**`stone-age-server` 改回 private 必须同时落地 PAT secret 方案;
`stone-age-client` 的可见性可自由选择。**

★ **另有一处曾被考虑并否决的做法,记下来免得重来**:
「把 `shared/` 复制一份进客户端仓,临时把 CI 跑通」。
⇒ **它跑出来的绿不含信息**:`--expect-mode fetch` 会直接失败 ⇒ 要绿就得关掉那条断言,
而关掉之后客户端 CI 只剩「客户端工具链能编 L3」—— 本地 `d2-only` 已验过四次的东西。
**副本等于换掉了被测对象本身**(引入既非联调态也非发布态的第三种接入模式),
还连带破坏「`shared/` 只有一份真源」这个漂移告警的前提。
⇒ 与 §12.6 那条 doctest 陷阱同族:**先问"绿了能证明什么",再问"怎么让它绿"。**

### 9.0.12 ★★ 改名后首跑归因(2026-09-04)—— 一个真开关变成了假开关

`shared-v0.2.0` 推出后 CI 首跑:**Linux · GCC 绿 / macOS · clang 绿 / Windows · MSVC 红**。
两条,性质完全不同。

**① Windows 红 —— `check_module_boundaries.py` 漏了输出编码那一段**

windows runner 上 Python 的 stdout 是 cp1252,`print("✅ …")` 抛 `UnicodeEncodeError`
⇒ 退出码 1 ⇒ CI 报「§3.1 的守卫失败」,**而边界检查本身是通过的**。

★ 值得记的不是这个错,是**它为什么会发生**:`ci_verify.py` / `check_shared_purity.py` /
`saidl_gen.py` 三处**早就都有** `reconfigure(encoding="utf-8")`,且 `check_shared_purity.py`
卷首还专门写了半屏理由(2026-09-02 实测)。**惯例存在、理由写清楚了,新加的第四个脚本
照样漏掉** —— 因为它是「每个文件各自记得」的纪律,而非结构性保证。
⇒ 凡新增会被 `ctest` 注册的 Python 检查,必须带上那一段;这条已补进本节。

**② ★★ 真正要紧的一条:`-Werror` 有一批提交根本没开过**

`ci_verify.py` 传的是 `-DSG_WERROR=ON`,而 option 在改名时已成 `SA_WERROR`。
CMake 对不认识的 `-D` **只印一句 `Manually-specified variables were not used`,
配置照样成功**,第 1 项照样报告「`SA_WERROR=ON`」——**那行文本是硬编码的,
它从来不是对现实的观测**。

⇒ 后果:自 `d7a5754` 起「清洁构建(告警即失败)」这道关是空的,
三平台的绿**绿得没有意义**。⚠️ 这正是 §9.0.11 自己预警的「漏改是静默失效,
比失败更坏」,而当时点名的是 `EXPECTED_TESTS` 与 `check_shared_purity.py`,
**恰恰漏了同一文件里的这一行**。

★ 抽象出来的类型,与 §10.4 三类静默错误同族,建议按第四类记:

| 类 | 表现 | 防线 |
|---|---|---|
| **开关名传错** | 不报错、不崩溃,开关静默失效,而报告照旧宣称它开着 | 见下 |

⇒ 已加防线:`ci_verify.py` 在配置期把 `Manually-specified variables were not used`
**判为硬失败并列出变量名**,理由是——**凡「我们靠某个 `-D` 才成立的结论」,
都要先证明那个 `-D` 真的被项目收下了**。
(同族先例:`RelWithDebInfo` 定义 `NDEBUG` ⇒ `assert` 被编译掉,测试照常打印 OK。)

⚠️★ 该防线本身也做了**反向验证**(故意传回 `SG_WERROR` ⇒ 判失败并点名变量),
理由同断言防线:一道没被验证会失败的检查,和它防的那个假开关是同一种东西。

**复验**:修完后 Apple clang 21 与 GCC 15.2 在 **`-Werror` 首次真正生效**下
各 0 告警 · `ctest` 9/9 · `ci_verify` 5 项全过;
`PYTHONIOENCODING=cp1252` 复现 windows 环境,①已不再触发。

### 9.0.13 ★★ 两条守卫补齐(2026-09-04)—— §9.0.12 那条原则有**两种**失效形态

> **起因是一次例行动作**:1.5 收尾(`TcpTransport`)开工前先跑一遍两仓基线。
> 服务端全绿,**客户端红了一条** —— 而红的原因和它报出来的原因不是同一件事。

#### ① 入口脚本输出编码 —— 把「各自记得」变成会失败的断言

§9.0.12 ① 已经把 `check_module_boundaries.py` 那个漏掉的
`reconfigure(encoding="utf-8")` 修了,并写下「凡新增会被 `ctest` 注册的 Python 检查
必须带上那一段」。⚠️ **但那仍然是一条纪律,不是保证** —— 而 §9.0.12 自己已经论证过
「惯例存在、理由写了半屏,第四个脚本照样漏」。

⇒ 已加 `ci_verify.py` **§0**(两仓各一份),判据只有两条,**故意做到不需要维护任何清单**:

| 判据 | 为什么是它 |
|---|---|
| ① 有 `if __name__ == …` 守卫 | 它会被当作入口执行 ⇒ **退出码有人读** |
| ② 源码含非 ASCII | 它可能 `print` 出 cp936 / cp1252 编不出的字符 |

被 `import` 的模块(`idl/codegen/saidl/*.py`)**不在其列** —— 它们共用入口设好的 `sys.stdout`。
⚠️ 判据**故意不**写成「在 CI 上跑的脚本」:那需要一份清单,而**清单本身就是下一个
「各自记得」**。⇒ 宁可对一次性分析工具也过严(实测揪出 `tools/rescope_battle_port.py`,
已补)。

★ §0 排在**配置之前**:它判的是「后面那些检查脚本的退出码本身可不可信」——
一个会在 cp1252 下把"通过"印成退出码 1 的脚本,它给出的红与绿都不含信息。

⚠️ 客户端仓此刻只有一个 py 文件,这条检查**立刻通过** —— 那不是它多余,恰恰是加它的时机:
§9.0.11 ② 已裁定客户端要新增一条**依赖方向检查**,而「新加的第四个脚本」正是
上面那个错发生的位置。**守卫要先于它守的东西存在**,否则又是一次事后补救。

#### ② ★★ 锁定 ref 与源码一致 —— 观测值是真的,却没人断言它是**对**的

客户端本地复验报「`shared/` 与锁定 ref 一致」**失败**。但同一份报告的上一行写着
**`锁定 ref = shared-v0.1.0`**,而 `cmake/SaShared.cmake` 里明明是 `v0.2.0`。

★ 根因:**`SA_SHARED_GIT_TAG` 是 `CACHE` 变量** ⇒ 改了 `SaShared.cmake` 的默认值,
**已存在的 `build/` 目录不会跟着更新**(实测 `CMakeCache.txt:273` 停在 `v0.1.0`)。
⇒ 本地复验编的是**改名前那一份 `shared/`**。

⚠️★ **这次它被抓住是运气**:`shared/` 的内容恰好因改名而变了 ⇒ 漂移检查报了红。
而那条红说的是「`shared/` 与 `v0.1.0` 不一致」—— **真实,却在回答一个错的问题**。
⇒ 若两个 tag 之间 `shared/` 恰好没有改动,漂移检查会**安安静静地绿**,
本地验的仍是旧 ref,且没有任何东西说得出这件事。

★★ **它与 §9.0.12 的差别,正是这一族问题的第二种形态**:

`clang-format --dry-run --Werror` 每处违规打一行诊断并非 0 退出。

⇒ CI 侧用 pip 往 PATH 上装的**钉死版本**会被 `HINTS` 命中的 Xcode 工具链**整个绕过**,

⇒ 改用 `PATHS`(在 PATH 之后才搜),语义才是「先用 PATH 上的,本机没有再退回已知位置」。
