# 现有问题修复实施计划（2026-09-12）

本计划承接[两仓 8.0 玩法忠实性审计](2026-09-11-8.0-fidelity.md)，回答“有哪些处理不了、接下来如何实施”。范围仍是 stone-age-server 与 stone-age-client 的**已有行为修复**，目标是按可核实的原版 8.0 语义收敛，避免隐藏的自创规则。

**当前状态：R0–R8 工程工作及本地共享版本同步准备已完成。** 18 项已修复，F03 的确定部分已修、U01 仍待用户裁定；家族经验表在最后补证中查明。实际修改、测试和边界见[修复结果](2026-09-12-remediation-results.md)。本计划保留实施前约定的范围与验收口径；审计基线及原始失败输出保留在原报告中。

## 1. 可处理性结论

**19 项发现中，没有发现工程上无法修复的问题。** 其中 18 项已有明确的修复方向；F03 的两处共识错误也能修，但它包含的版本系数和下限冲突无法由现有资料确证。复杂度最高的是 F04/F07/F08/F18 共同涉及的回合内提交时序，需要调整规则层与世界层之间的调用方式，属于工程工作。

必须另行承认：**有些原版事实目前无法确定，不能承诺把它们“修成已证实的 8.0 真值”。** 原版不能运行、完整旧代码编译与反汇编不在当前取证路径内。现有测试只能证明新实现符合明确的源码期望及自身契约，不能证明原版运行时逐位一致。

| 类型 | 本次处理方式 | 是否阻塞明确缺陷的修复 |
|---|---|---|
| 已有源码反例或自身契约错误 | 修代码、建立有区分力的回归、复验实际调用链 | 不阻塞；按下文批次执行 |
| 两代源码冲突、B80 函数体无法确认 | 保留未决标识、列出候选语义和影响，不选择一个值冒充事实 | 只限制该子项的忠实性结案 |
| 原版未定义行为 | 保留有依据的兼容选择和可见差异，不能宣称复现原库结果 | 不阻塞其余修复 |
| 既有主动改规则 | 逐项量化并给出恢复方案，随实施修订裁定，保留历史 | 不阻塞无关批次 |
| GUI 或跨平台环境尚未验证 | 分开记录逻辑验证与实际运行验证；环境未验证不能记通过 | 影响对应验收，不是已证实的不可实现 |

## 3. 原版未决项与既有差异

### 3.1 无法从当前证据确证的事实

| 登记 | 事实边界 | 实施处置 |
|---|---|---|
| U01：F03 速度系数及下限 | SSRC80 的默认/用药扰动为 0.3 且有下限；SSRC85 为 0.1 且下限被注释；B80 符号不能证明采用哪一个函数体 | R2 先修双源一致部分。补证期间保留当前 0.1/不夹下限作为**待核实的现行选择**，撤掉“已照抄 8.0”的表述；两个候选的结果分别列示。若仍无证据，保持未决，不由测试替它裁定 |
| U02：同速排序 | EsCmp 不满足严格弱序，无法还原旧标准库在原环境的具体结果 | 继续将 DR-BT8 的按槽位稳定排序标成兼容选择，不改称原版事实 |
| U03：其余原版事实边界 | 装备损坏槽位算法、Load_PetSkillCodes 的文件、战斗金币公式、sizeof(Char)/视野 20 或 23 | 最后补证已查明 B80 家族经验初始化值，移出未决项；其余见更新后的[证据清单](../backlog/04-undecidable.md)。新模型无需复制原内存布局，但视野等可观察选择必须披露 |
| U04：原版整体运行与手感 | 当前无可运行的原版客户端/服务端作为行为基准 | 验收写明源码一致性、数据覆盖和新实现联调范围；不承诺原版运行时等价 |

U03 与 U02 原对应旧清单六项，其中家族经验在本轮末补证解决；它们不与 19 项新增问题重复计数。找不到证据只限制相关结论，其他确定修复继续推进。

### 3.2 已主动改变的规则如何处理

当前用户要求以原版行为为目标，不能继续用“按意图修正”自动豁免可见差异。下表保留实施前约定的方向；代码与当前 DR 已按这些方向同步，原决定的论证保留为历史并追加勘误指针。具体结果见修复记录 §3。

| 差异 | 计划方向 | 批次与验收 |
|---|---|---|
| DR-DT1 成长 4.50 对 atoi→4 | 拟恢复源码截断口径；将实际 World 配置入口与默认值一并核实，消除“测试可开、运行时不可开”的错觉。无需为此新增多套玩法模式 | R2 独立子批；真实小数模板在多个等级的数值、玩家获得宠物的实际路径都按选定原式验证 |
| DR-BT2 骑宠分摊分子及 +1 | 拟恢复原式；它在有效输入上改变人宠承伤，不能归入内存安全修复 | R2 独立子批；不同防御比及取整余量的原式期望；世界尚未接线的范围继续标明 |
| DR-DT10 负成长打包 | 拟恢复原式可观察的跨字节效果，以定义良好的算术实现结果。记录这是对既有用户裁定的迁回建议，保留原决定及变更原因，不混入普通格式修正 | R2 独立子批；原始负值模板、解包四维和后续属性链验证。尚未落实的选择保持差异状态 |
| DR-BT8 同速顺序 | 按 U02 保留兼容策略标签 | R0 登记、R8 核查 |
| DR-DT23 用药目标已死 | 有活目标时拟恢复原目标改选及 RNG；全死造成未定义行为的分支独立处置，不能借此删除正常分支 | R4 用药子批；活目标改选、无活目标、耗药与随机位置分别验证 |
| DR-DT15/DT22 收益时序 | 撤回“放到战斗结束仍等价”的论证；掉落抽签与最终发包/入包分别追溯原时点，关联经验资格也需核实 | R4；先杀怪后继续行动、宠物及主人离场的归属变化 |

这些是已知的差异，不能悄悄改写成“以前没有发生”，也不能仅靠补一条注释宣布忠实性问题已经关闭。若实施中仍保留某项主动差异，须保留具体范围及依据，并在最终结案中单列。

### R0 — 明确验收口径与证据输入

交付：本计划的实施台账、U01–U04 登记、主动差异对照，以及每个子批的源码片段和输入/期望。

- 沿用审计记录的两仓 SHA、原始源码位置与[源码/数据指纹](evidence/2026-09-11/source-evidence.json)。开始修改时记录新的工作树基线，保留已有文档改动。
- 核对函数体、宏、枚举值、表达式中间类型、RAND 调用和状态写入时点。SSRC80/SSRC85 不一致就登记，不能只引用功能文档转述。
- 优先复用已有探针，将反例逐项纳入合适的正式测试；测试输入与期望注明证据来源。旧报告及 results.txt 保留，不覆盖成新运行结果。
- 当前规格中“玩法自洽重制”“照抄与修正都合法”的宽泛表述应随实施补充本轮约束：已知的有效输入行为按原式收敛，差异和未知显式登记。

验收：F01–F19 都能追到修复批次、源码或契约依据和可观察期望；本轮没有被悄悄纳入的新技能、内容系统或自行平衡项。

### R1 — 先让客户端验收可信（F11/F13/F17）

主要落点：[ClientSession.cpp](../../../stone-age-client/src/net/ClientSession.cpp)、[ClientApi.h](../../../stone-age-client/src/net/include/net/ClientApi.h)、[BattleScene.cpp](../../../stone-age-client/src/scenes/BattleScene.cpp)、[main.cpp](../../../stone-age-client/src/app/main.cpp)、[BattlePresenter.cpp](../../../stone-age-client/src/battle/BattlePresenter.cpp)、[ClientNetTest.cpp](../../../stone-age-client/tests/ClientNetTest.cpp)。

顺序：先拆分测试终态与失败原因，再接 BattleResult 的解码/回调/场景状态，最后单独修事件边界检查。删除“收两条事件就完成”的条件；正常交互与定帧自动验收分别处理结束条件。

成功必须包含正确战斗 ID 的结算和预期状态断言；胜负是游戏结果，输掉战斗不等于协议失败。握手拒绝、提前断线、协议违规、定帧耗尽须有清楚的失败结果，后到的关闭回调不得覆盖已完成结果或先前错误。

验收：

- 实际编码帧经 FrameReader → ClientSession → 宿主消费，0x0206 不被拒收；未知/方向错误消息仍按协议处理。
- 两条正常 BattleEvents 而没有 BattleResult，不能通过完整战斗验收。
- 分别注入拒绝、断线、畸形消息及超时，观察非零退出码；仅逻辑用例通过时不得写“GUI 已验收”。
- Damage/SetHp 等字段在访问前校验，覆盖合法端点和 20、最大可表示槽号；按各消息契约判断，不能把 SelfInfo 的观战槽 20 与 Damage.target=20 混为一谈。ASan 无越界。

### R2 — 修正数值和随机表达式（F01/F02/F03 确定部分/F16）

主要落点：[Status.cpp](../../shared/rules/Status.cpp)、[Battle.cpp](../../shared/rules/Battle.cpp)、[Constants.h](../../shared/rules/Constants.h)、[RandomSource.h](../../shared/rules/RandomSource.h)、[RulesBattleTest.cpp](../../tests/RulesBattleTest.cpp)。主动数值差异另涉及 [Progression.cpp](../../shared/rules/Progression.cpp)、[Config.h](../../shared/rules/Config.h) 及 World 的实际配置写入者。

按“状态公式 → 随机表达式 → 行动速度 → 既有数值差异”拆小批。每笔先给原式期望，验证旧实现确实不能满足，再改实现与错误的既有期望。

验收：

- F01 覆盖小数体力比例、负值/封顶边界及最终命中；F02 同时核实实际枚举和无效分支。
- F03 覆盖 quick+20、用药 +15%、先后手变化与 U01 两套候选的区别；不新增尚未实现指令的速度档。
- F16 覆盖不能被 8/16 整除的攻击、变异后小数攻击与接近随机上端的样本。核查当前已启用 RAND 调用的输入类型、输出支持集、区间概率和调用次数，不能用“改成更宽的均匀整数区间”代替原浮点表达式。
- 原 PRNG 与新 PRNG 的种子序列不承诺相同；测试用受控随机输入核实表达式及消耗位置。区间退化仍是否消耗、深度倒置区间等按源式单列，不能扩用原有错误概括。
- DR-DT1/BT2/DT10 各有独立对照和变更记录；若运行入口尚不支持某行为，只能验到相应层，不能写全链已完成。

### R3 — 统一回合工作态与状态读写（F05/F06）

主要落点：[Combatant.h](../../shared/rules/Combatant.h)、[Battle.h](../../shared/rules/Battle.h)、Battle.cpp、Status.cpp 及 World 的投影/回写。

建立包含占位、HP/死亡、状态计数与本回合有效属性的局部工作态，使每次计算都读取上一步结果。保持规则层不依赖世界实体池、网络或存储；不是在 World 再写一套规则。

酒醉/混乱与原 StatusTbl 对应的 work 计数确定为同一权威来源，消除无人同步的重复字段或将其严格派生。按当前已实现状态范围处理，不顺带增加职业状态施加能力，也不以互斥假设抹掉原版允许共存的例外。

验收：

- 正伤害唤醒先于后续行动/回避读取；零伤害及当前支持的吸收/消失分支按原适用条件验证。
- 状态施加、递减、解除及行为判定读取一致；酒醉加成的随机调用位置正确。
- 复核原回合准备步骤：临时 quick 等修正不能未经重算永久积累。玩家/宠物原始四维投影与实际模型一致，脚手架不可用零值掩盖已存在的属性来源。
- 新动作接口仍使用回合开始时确定的一份行动顺序；中途状态变化改变可否行动，不擅自重排剩余行动者。

### R4 — 修复回合内提交与收益时序（F04/F07/F08/F18）

主要落点：Battle.h/Battle.cpp、[World.cpp](../../src/world/World.cpp)、[WorldTickTest.cpp](../../tests/WorldTickTest.cpp)，以及已有收益计算和宠物/物品模型。

采用**可逐步骤推进的规则计算接口**：规则计算到世界提交点 → 宿主同步处理资源与实体 → 将提交结果交回规则工作态 → 完成该步骤及事件 → 继续下一步。共享规则只接收明确输入/结果，不调用 socket、数据库或持有实体池。原一次性 resolveTurn 如保留，只作为同一实现的适配入口，不再另写第二套乐观成功逻辑。

接口首先覆盖原版的逐行动提交点；若原调用位于多段动作中间，就在该子步骤暂停，不能一律挪到动作末尾。排序仅生成一次，暂停/恢复不重摇行动速度。

| 子批 | 修改边界 | 必需验收 |
|---|---|---|
| R4a：提交接口与离场 | 逃跑、捕获、叫宠/收宠成功后，工作态与世界态在后续行动前一致 | 三种 F04 反例；目标已离场、宠物槽满、模板缺失、实体池满；失败不发布成功结果、不错误移除目标 |
| R4b：用药 | 依据实际执行/提交结果扣对应物品，投影阶段不扣；已死目标改选按正常原分支处理 | 麻痹、睡眠、先手被杀、目标失效、满血合法使用、堆叠耗尽；恢复与扣药各一次；原版的无条件副作用按原时点保留 |
| R4c：宠物权威态 | 建立战斗槽到持有宠物的稳定身份对应，在收回/换宠/结束/逃跑/断线前正确回写 HP | 真实受伤后 16→15→收回→再叫出仍为 15；不同宠物复用同槽不串写；退出时清除/保留字段逐项有来源 |
| R4d：死亡收益 | 新死亡敌人只结算一次，按原调用点抽掉落归属、更新暂存；最终发放按实际退出/结束边界处理 | 先杀掉落怪再行动及跨回合、互换死亡顺序、单归属仍摇 RNG、宠物折回主人、暂存满时覆盖/丢弃；关联经验资格不凭结束时集合重构 |

捕获的资源可用性检查必须回到原控制流中的位置；不能为了“先检查更安全”提前跳过原本要消耗的随机数。提交失败保留原本必做的清零等副作用，不能对整个动作一概回滚。

**事件容量同时处理。** 当前 256 是 BattleEvents 单帧容量，不能成为截断规则执行的理由。规则结果应可续写到有序批块，World 按同一战斗/回合顺序消费并发送；客户端不能把一个批块误当一整个回合。按当前已支持的最大合法动作组合验证超过一帧时无丢事件、无重复 RNG、无多扣资源，禁止“应用前缀后直接推进回合”。输出空间应在相应步骤提交前得到保证；若编码/投递发生不可恢复错误，记录明确失败并结束对应连接，不能宣布客户端已完成。

R4a–R4d 各自保留回归，不等最后整批才测试。客户端快照的具体排布在 R5 完成，但成功/失败事件的真实性在本批就须通过世界测试。

### R5 — 权威快照与客户端状态闭环（F12）

主要落点：World 入场/回合发送点、[battle_events.proto](../../idl/schema/domain/battle_events.proto)、ClientSession/ClientApi、BattlePresenter/BattleScene。

**优先接通已定义的 BattleSnapshot（0x0201），复用 CombatantState 的 hp/max_hp/flags。** BattleSelfInfo 没有初始 HP，Enter/PetSwitch 也不提供完整新单位数值，不能靠这些消息猜初始状态。

本轮采用同一连接上的有序消息流，明确下面的提交及消费边界：

1. 初次入场：SelfInfo → 初始 Snapshot → 对应 TurnBegin/Events。快照到达前，单位血量保持未知，不能用 0 或默认满血推断存活。
2. 中途入退场：先交付截至该提交点的事件，再给该点的权威快照，随后才给后续增量。快照替换该点状态，之前的伤害不能再应用一次；表现队列也须保持这一顺序。
3. 结束：最终事件/必要快照 → BattleResult。换战斗时清除上一场状态，同一战斗重复 SelfInfo 不得无条件丢掉已知血量。

现有 Snapshot **没有 turn/revision**，上述方案只承诺当前有序单连接、不含重连补帧的边界；实现中必须证明客户端能唯一识别快照覆盖点。若无法做到，需要单独评审最小的序号/快照字段改动，同时更新 schema、生成物、消息版本与双端消费者，不能只在客户端自拟规则。

验收：100−10=90、恢复后 HP 正确、死亡与离场分开、同槽换宠重建状态、换场不串血、跨批块连续消费、快照前后无双重扣血。用 World 实际输出喂客户端消费，与权威场景逐阶段比对；原 F12 探针的“SelfInfo 后直接伤害”应改验未知/缺快照错误，不能要求客户端凭空算出 90。

### R6 — 修复已存在的世界接线（F10/F14/F15）

主要落点：World::onWalk、角色移动循环、triggerEncounter、enterEnemyToField，以及 [WorldMapTest.cpp](../../tests/WorldMapTest.cpp)/WorldTickTest.cpp。

- F10：入口和已排队走路串都检查战斗状态，暗雷触发检查归属；入战时走路串如何清理按原入口核实。
- F14：玩家最多 5 个玩家位与敌方可用 10 格分别处理；已选敌人到实际入场不能再静默取前 5 个，大怪占位/组合限制仍按原规则。
- F15：按原查物品函数的槽范围收集真实物品 ID，装备是否计入也由该函数决定；捕获删物品、使用耗尽等现有变更须反映到下一次遇敌。

验收：合法行走中入战后坐标停住；带排队指令与连续请求均不产生第二场归属；普通敌人 1/5/6/10 与混排；持有门、排除门、删除后再遇敌；真实表扫描量化覆盖范围，不把 509/1051 配置行误写成实际遭遇频率。

### R7 — 生命周期收口（F09/F19）

主要落点：World::onDisconnected、战斗结束/离场路径、实体池与既有 stats 观察接口。

断线清理按所有权处理背包及装备位中的道具引用，和宠物、玩家释放保持正确顺序。当前尚未实现存档，不能为本项引入整个存储系统；已有内存对象应完整回收。

战斗结束须先完成收益、宠物回写和最终消息复制到连接输出队列，再从活跃容器删除。stats(id) 如需保留，只保存最小统计并明确历史容量，不能为旧测试无限保留整个 BattleInstance。

验收：自然胜负、逃跑、捕获后结束、主动断线和异常断线；持续创建/结束的次数超过历史保留容量后，活跃战斗、敌人和断线会话的持有资源归零；最后结算仍能被客户端读取，无陈旧句柄、重复释放和遍历失效。内存/容器规模按上限衡量，不只看一次运行的进程 RSS。

## 6. 结案规则与第一批入口

实施台账状态只使用“未开始 / 进行中 / 已修复 / 证据未决 / 保留的明确差异”。**证据未决和明确差异均不计入已修复。** F03 拆记确定部分与 U01；最终报告保留整项的剩余边界。

每个修复子批的最小结案材料：

1. 改动所依据的原式或现有契约、实际文件和影响路径。
2. 能区分旧错误与正确结果的回归；接口改变时保留等价场景的前后证据，不仅改到编译通过。
3. 当前批次适用的测试通过，新增故障没有被忽略；生产路径与测试注入的差别明确。
4. 代码、规格、裁定、未决/差异登记一致；不以改日志、扩大默认值或放宽期望来关闭问题。

首个编码批次确定为 **R1：F13 → F11 → F17**，在开始时补齐 R0 对这三项的契约和反例即可动手。R1 交付“错误必失败、真实结算能消费、异常槽不越界”，然后推进 R2 的确定公式修复。U01 与历史不可判定项不要求整条修复线停工。

完成本计划的工程工作后，再评估后续功能安排；仍未解决的原版事实和保留差异必须随结果一起展示。不能把“当前构建和测试全绿”写成“原版 8.0 已全部还原”。
