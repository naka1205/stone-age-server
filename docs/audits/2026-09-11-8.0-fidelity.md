# 现有实现的 8.0 玩法忠实性审计（2026-09-11）

本轮范围为 stone-age-server 和 stone-age-client 的已有实现。目标是找出现有缺陷、隐含自创和证据链缺口，形成修复依据。**本轮未增加业务功能，未修改运行时代码、IDL、既有测试期望值或既有 DR 裁定，也未推送版本。** 随文 C++ 文件仅为独立审计探针，不进入产品构建。

用户本轮要求的验收方向是：**真实还原原版 8.0 玩法，防止未被发现的自行改规则。** 下文中“已证实”指当前实现与所列源码语义或自身契约不一致；原版不可运行，因此没有把静态对照写成原版运行时差分测试。

后续：[实施计划](2026-09-12-remediation-plan.md)已进入实施与验收，当前状态见[修复结果（2026-09-12）](2026-09-12-remediation-results.md)。**下文冻结在审计时点**，保留原问题、源码证据及失败输出。

## 1. 结论与范围

本次登记 **19 项问题**：17 项有新实现的执行探针或运行观测，2 项依据静态控制流核实。另列既有主动差异、尚未接线的风险和修复建议。**审计时这些问题尚未修复；当前结果由后续修复记录单独追踪。**

现有工程能通过测试，但测试未充分覆盖“当前实现是否保留了原版规则”。在同一审计基线上：

| 验证 | 结果 | 能证明的范围 |
|---|---|---|

| 服务端 CTest | 17/17 | 包括规则、世界、网络、IDL、模块边界、文档索引和格式 |
| 客户端无引擎构建及 CTest | 5/5 | 共享规则、客户端协议层、引擎隔离和格式 |

| 客户端边界探针 | AddressSanitizer 报 heap-buffer-overflow | Damage.target=20 导致越界读取 |
| 图形客户端完整联调、MSVC/GCC、原版运行环境 | 本轮未运行 | 不把历史 CI 结果算作本次验证 |

## 3. 逐项证据与处置建议

### F01 — 状态命中率的整数转换位置错误

现实现：[Status.cpp](../../shared/rules/Status.cpp#L152)，rollStatusAttack。SSRC80 battle/battle_event.c:5088–5136 与 SSRC85 同文件:5211–5262 一致：先计算包含 fVitalP 的浮点表达式，赋给 int per 时才截断。

当前实现先 static_cast<int>(vital_p)，再做整数减法。例如体力占比 1/3，其他整数项合计 30，原式 int(30−13.333…) 得 **16**，当前 30−int(13.333…) 得 **17**。随机值 16 时，原式不命中，当前命中。探针同时验证了阈值和最终布尔结果。

建议：保留原式的类型提升、运算顺序和最终转换位置。新增包含小数体力占比、正负边界及 80 上限的源码期望用例；不要按现实现重算期望。

### F02 — 把不同枚举中的同名含义当成相同数值

现实现：[Status.cpp](../../shared/rules/Status.cpp#L44)，equipResistOf。SSRC80 battle/battle_event.c:5142–5151、SSRC85:5268–5277 比较的是 status == CHAR_WORKWEAKEN 等，而 status 参数属于 BATTLE_ST_* 枚举。

使用现有静态枚举解析器，读取 SSRC80 的 version.h、correct_bug.h、version_pk.h、char_base.h、battle_event.h，得到：

| 项 | 值 |
|---|---:|
| CHAR_WORKWEAKEN / CHAR_WORKBARRIER / CHAR_WORKNOCAST | 51 / 53 / 54 |
| BATTLE_ST_WEAKEN / BATTLE_ST_BARRIER / BATTLE_ST_NOCAST | 7 / 9 / 10 |
| BATTLE_ST_END | 44 |

函数入口已拒绝 status>=44，所以原来的三个比较不会命中。当前改用 BATTLE_ST_* 后让它们生效：相同输入原式 per=20，装备抗性 7 使当前 per=13。

这是**可观测规则改动**，不能用“字段名字在骗人，所以按语义翻译”解释为等价移植。建议保留原版的无效效果；若确实要修原版缺陷，应单独登记影响及裁定，不能混入忠实复刻。已有相关测试、journal/15-status、05-battle 和 DR-DT24 的转述须一起复核。

### F03 — 行动顺序有两处确定遗漏和一处版本冲突

现实现：[Battle.cpp](../../shared/rules/Battle.cpp#L705)，computeActionDex；[Constants.h](../../shared/rules/Constants.h#L170)。

确定遗漏：

1. 两代源码均先 work=quick+20，再按 work 摇扰动；当前扰动只乘 quick。quick=100，即使继续采用当前 0.1 系数，范围也应基于 120 得到上界 12，当前是 10。
2. USE_ITEM 已实现，但 command 仍被忽略。两源的道具分支都有 +work*0.15；quick=100、扰动取 0 时原式为 **138**，当前为 **120**。先用药还是先受伤因此可能改变。

版本冲突须保持未决：SSRC80 battle/battle.c:4297–4312 默认及道具扰动系数为 0.3，并有 dex<=0 夹取；SSRC85:5409–5423 为 0.1，下限夹取被注释。当前注释引用了 8.5 形态，却称“照源码”，没有呈现这处冲突。**不能未经核实就把 0.3 或 0.1 写成 B80 已证实值。**

建议先修双源一致的两处遗漏，将系数与下限的版本差异单独登记。用边界随机值验证先后顺序，而非只检查生成了几个事件。

### F04 — 分层之后，原版的“当场离场”变成“回合后离场”

现实现：[Battle.cpp](../../shared/rules/Battle.cpp#L1093)，resolveTurn；[World.cpp](../../src/world/World.cpp#L635)，applyEvents。

原版捕获成功在 SSRC80 battle/battle_event.c:4124 调 BATTLE_Exit；逃跑成功在 :4303 离场并在 :4304 改战斗模式；收宠在 :4417 调 BATTLE_PetDefaultExit。后续行动读取已经变化的世界态。

当前 HP、死亡和状态有局部镜像，但捕获、逃跑、收宠只发事件，原 field 的 occupied 与行动队列继续被读取。三个受控场景分别得到：

- 逃跑成功后，仍生成针对逃跑者的攻击；
- 捕获成功后，被捕敌人仍出手；
- 主人收宠后，该宠物仍出手。

世界最终写回时跳过部分伤害也不能恢复等价：多余行动、随机消耗和已广播事件都已产生。已知欠债 22 的“捕获/叫宠意图成功，但世界提交失败”属于相邻问题，尚不能由本项自动关闭。

建议维护完整的**回合工作态**，让后续动作看到已提交的入退场结果。纯函数可以修改自己的局部工作副本；“L3 不写宿主世界”不要求在回合内继续读旧状态。涉及宠物槽、实体池的失败也须在生成对外成功结果前处理。

### F05 — 睡眠目标受伤不醒

现实现：[Battle.cpp](../../shared/rules/Battle.cpp#L1530)，普攻结算段。SSRC80 battle/battle_event.c:2764–2765 在 damage>0 且非吸收/消失反应时调用 BATTLE_DamageWakeUp；:1599–1614 清 CHAR_WORKSLEEP 并发解除状态消息。

当前缺少这个动作。探针先确认睡眠目标收到一条正伤害，再确认没有睡眠解除事件。状态仍按原计时推进。

建议补齐当前普攻与睡眠系统之间的既有交互；回合内唤醒也必须反馈给后续回避、行动判定，不能只在末尾改图标。

### F06 — “酒醉和状态槽是两个来源”缺少源码依据

现实现：[Combatant.h](../../shared/rules/Combatant.h#L290) 同时持有 status/status_turns、drunk 和 confusion，注释称它们是两个来源。[Battle.cpp](../../shared/rules/Battle.cpp#L470) 的回避只读 drunk，防御门另读 confusion。

SSRC80 battle/battle_event.c:90–94 的 StatusTbl 已直接把酒醉、混乱映射到 CHAR_WORKDRUNK、CHAR_WORKCONFUSION；:858–859 的酒醉回避也读同一个 CHAR_WORKDRUNK。不是两个可任意分离的原版状态。

探针设置 status=DRUNK、turns=3，当前只消耗一次回避随机数，漏掉原版酒醉加成 RAND(20,30) 那一次。混乱也存在类似的计时状态与行为字段分离；其目标改选链路还未完整核验。

边界：当前正式施加者主要是装备毒，酒醉/混乱的完整来源尚未接通；探针证明的是现有状态模型与公式接口的断开，未声称现有 UI 已能施放酒醉。

建议建立可追溯的状态存储与行为派生关系，清除无依据的“双来源”说明；职业技能允许共存的例外应另核，不能用互斥假设抹掉，也不能据此制造两份无人同步的状态。

### F07 — 准备好道具基数，不等于已经用过道具

现实现：[World.cpp](../../src/world/World.cpp#L540)，projectItemUsePower / consumeUsedItems；结算调用顺序见 :1856–1889。

投影只证明“背包有有效恢复药”。L3 仍可能因行动前死亡、麻痹、睡眠、目标失效或事件溢出而不执行。但 consumeUsedItems 只检查 command=USE_ITEM 和 item_heal_power>0，无执行结果依据。

探针中玩家麻痹、状态正确从 3 减为 2，未执行用药，背包物品却从 1 变 0。原版由行动分发进入 ITEM_useRecovery_Battle，扣除在该路径内；未执行动作不会仅因之前选了药而扣药。

建议由真实执行/提交结果驱动物品扣除。分别验证“选药后被先手击倒”“仍被状态禁止行动”“合法执行但满血”等不同场景，不能把它们统一为“不回血就不扣”。

### F08 — 宠物战场血量没有回到持有实体

现实现：[World.cpp](../../src/world/World.cpp#L635) 的伤害写 Combatant；:3188 enterPetToField 从 Model::Pet.hp 拷入；:3267 exitPetFromField 只清占位。收宠与战斗结束均缺少相应 HP 回写。

集成探针通过现有捕获链获得 HP=16 的宠物并叫出，将战场置为合法受伤状态 HP=15 后收回，再叫出得到 **16**；Model::Pet.hp 全程仍为 16。受伤状态注入仅隔离伤害随机性，实际伤害路径也只写同一 Combatant。

原版 CHAR_HP 属于同一宠物实体，收回不会从另一份旧 HP 重新生成。建议明确战场态与持有态的权威及提交时机，覆盖换宠、结束、逃跑和断线。退出时哪些状态需清除，要逐字段照源码核对，不能自行规定全部保留。

### F09 — 断线回收漏掉道具池

现实现：[World.cpp](../../src/world/World.cpp#L2775)，onDisconnected。清理玩家和宠物后释放 Player，没有释放 Player.items 引用的 Item 实例。

探针：放入一件物品后断线，playerCount=0、itemCount=1。重复会耗尽 10000 个道具槽，使后续掉落/入包失败。这是当前生命周期缺陷，存档未实现不构成保留孤儿对象的理由。

建议在正确的保存/登出边界回收道具，验证背包、装备位和异常断线；记录“会话全部清空后各族活跃计数”而非只验证宠物池。

### F10 — 战斗状态没有阻止移动

现实现：[World.cpp](../../src/world/World.cpp#L2943)，onWalk；:2169 起的玩家移动循环。它们未检查玩家正在战斗。

SSRC80 char/char_walk.c:921–923 在 CHAR_walk_init 明确要求 WORKBATTLEMODE==BATTLE_CHARMODE_NONE。探针在已 joinBattle 后发合法方向串，同一玩家坐标仍向东移动 1 格。

此外，移动后的暗雷判定也缺少当前战斗归属检查，存在重复开战的关联风险，本轮没有把“多场并存”计作独立已复现结论。

建议在原版对应边界阻止移动，并核查入战前已排队走路串的处置。不要只禁客户端按钮；服务端应验证真实状态。

### F11 — 已合法下发的结算消息被客户端拒收

服务端：[World.cpp](../../src/world/World.cpp#L2108) 战斗结束发送 BattleResult（0x0206）。客户端：[ClientSession.cpp](../../../stone-age-client/src/net/ClientSession.cpp#L116) 只接握手和三个旧战斗消息，BattleResult 落入默认拒绝分支。

使用实际共享编码器、FrameReader 和 ClientSession：握手成功、BattleEvents 成功、BattleResult 被拒，last_reject_msg_id=0x0206。不是 TCP 或序列化错误，而是两端消费契约没有同步。

建议列出每条现有下行消息的“服务端发送点→客户端分发→状态提交→表现”路径，逐条验证。锁定 tag 更新本身不会补上客户端的分发逻辑。

### F12 — 缺少初始 HP，客户端凭伤害推算出假死亡

现实现：[BattlePresenter.cpp](../../../stone-age-client/src/battle/BattlePresenter.cpp#L68)。第一次 Damage 到达时，未知初始 HP 被直接设成 hp_delta，随后用 hp>0 判断 alive。

探针的服务端情境是 HP=100、普通非致死伤害 −10，客户端得到 **HP=−10、alive=false**。当前 BattleSelfInfo 不含初始 HP，服务端也没有在这一链路推送已定义的完整战场快照，所以单改一条加法不能补足信息。

建议以权威初始状态初始化表现，再应用增量；信息未知时保持“未知”，不能猜 0 或用默认满血。覆盖入场、换宠、恢复药、逃跑和死亡的连续表现。

### F13 — 自动验收会把失败退出也计为成功

现实现：[BattleScene.cpp](../../../stone-age-client/src/scenes/BattleScene.cpp#L132) 在协议错误、断线、握手拒绝时都置 _finished=true；[main.cpp](../../../stone-age-client/src/app/main.cpp#L157) 用 const bool ok=scene->finished() 决定 PASSED 和退出码 0。

此外，BattleScene 收到两条回合事件就置 finished，不等待真正的胜负结算；正常交互模式也共用这一条件。

静态结论：**失败结束和成功完成使用同一个判据**，因此历史 autotest PASSED 不能单独证明完成了一场战斗。未运行图形端失败场景，避免把控制流检查写成 GUI 实测。

建议先使验收能正确失败，再用它验修复；成功应包含明确的完成结果和必要状态断言，拒绝、断线、协议错误须保留不同结果。补“握手拒绝仍 PASSED”这类反例。

### F14 — 把玩家的 5 格限制套到了敌人身上

现实现：[World.cpp](../../src/world/World.cpp#L3981)，enterEnemyToField 拒绝每侧后 5 格；:2603 起 triggerEncounter 也将已选敌人裁到 kBattlePlayerMax=5。

原版 SSRC80 battle/battle.c:1022–1037 **按类型分支**：玩家 iEntryMax=BATTLE_PLAYER_MAX，敌人 iEntryMax=BATTLE_ENTRY_MAX。敌方可以用 10 个位置，后 5 格并非永远只能放宠物。

探针向 10..19 十个空位置放普通敌人，仅成功 **5** 次。真实 csa8.0/gmsv/data/encount.txt 1051 行中有 **509 行的数量上限大于 5**；这是可能受影响的配置范围，不表示每次都实际抽出 6 只以上，大怪与编组上限仍会约束数量。

建议恢复类型对应的槽位规则，验证 1/5/6/10 只普通怪及大小怪混排，并检查“已抽中的列表→真正入场列表”一致性。不能保留“取前 5 只”的静默裁剪。

### F15 — 背包接上了，遇敌仍假装玩家没有物品

现实现：[World.cpp](../../src/world/World.cpp#L2566)，triggerEncounter 无条件构造 empty_bag 传给 pickEnemyGroup。后者的两道道具门本身已实现，输入却永远为空。

探针：玩家真实背包持有物品 999，区域只引用一个需要 999 的编组；沿 onWalk→tick→暗雷触发运行，敌人仍为 0，预期应生成 1 只。SSRC80 char/enemy.c:1307–1332 的筛选直接检查玩家实际持有物品。

旧注释“道具系统未移植，接上后自动恢复”已失效；I.1–I.4 不会自动修改这个调用点。建议传真实背包快照，并同时验证“持有才出现”“持有反而不出现”以及捕获扣除后下一次遇敌的变化。

### F16 — 普攻随机端点的浮点截断丢掉合法结果

现实现：[Battle.cpp](../../shared/rules/Battle.cpp#L337)，computeDamage 将 attack*D_16、attack*D_8 转为 int 后传 RNG。

两代原始 battle_event.c 的对应表达式一致：RAND(0, attack*D_8)；SSRC80 include/util.h:77–78 的宏为 x+int((y−x+1)*u)，端点参与浮点运算。attack=100 时 y=12.5，原式可取 **0..13**，当前只取 **0..12**。

探针隔离相克、装备与全局倍率，使用高端随机值：当前伤害 **205**，原表达式 **206**。这是合法值集合变化，超过“换了 PRNG 所以种子序列不同”的范围。I.4 已为回血药处理过同类端点问题，却没有回查既有普攻调用。

建议逐一审计所有 RAND 调用的实参类型、截断时机、分布与消耗位置。测试须包含不能被 8/16 整除的攻击值，以及敌人随机加成后出现小数的攻击值。

### F17 — 客户端先越界读，再检查槽号

现实现：[BattlePresenter.cpp](../../../stone-age-client/src/battle/BattlePresenter.cpp#L77)。Damage 分支先读 _slots[slot].seen / hp，后面才检查 slot<20。

独立 ASan 探针构造 target=20，报 heap-buffer-overflow，读取地址恰好在 BattlePresenter 分配对象之后。当前合法服务端通常不会发这个槽号；这是异常消息的稳健性缺陷，不是原版玩法差异。

建议在任何读写前验证槽号和事件必要字段。不能以“最终赋值前有检查”认定已覆盖边界。

### F18 — 延后掉落随机数并不与原版时序等价

现实现：[World.cpp](../../src/world/World.cpp#L1980) 在战斗结束后统一分配掉落，并解释“该 RNG 用完即弃，不平移任何后续序列”。

原版 SSRC80 battle/battle.c:8900 在行动结算中调 BATTLE_AddProfit；:5178 转到 BATTLE_AddExpItem；:4994–5015 在确认新死亡敌人后即为物品抽签。**原版在这个抽签之后仍可能有其他角色行动或下一回合。**

因此，将抽签挪至整个战斗之后改变同一战斗内随机调用的相对顺序。原版 allnum=1 的抽签也消耗随机数；不能只凭“单玩家归属唯一”证明时序等价。原版按 pBidList 归属，当前按结束时的在场集合，还需进一步核对组队、收宠、逃跑等情况。

本项的结算延后已有 DR-DT15/DT22 记载，**发现的是其“等价性论证”不足**，不称为完全未登记的新改动。本轮做了静态调用链核对，没有运行完整原版战斗。

建议重新建立逐行动的收益与随机时序证据，至少覆盖“先杀掉落怪、再继续战斗”和死亡顺序互换；未经证明不得继续标为“只换计算位置，玩法等价”。

### F19 — 已结束战斗对象无限累计

现实现：[World.cpp](../../src/world/World.cpp#L1231) 用 map 保存 BattleInstance；结束路径 :2142–2162 释放敌人，但不移除 BattleInstance 或转换为有界历史记录。

探针完成 10 场战斗后仍保留 **10 个完整战斗对象**。后续 tick 继续遍历整个 map 再跳过 finished；会话归属等容器也留在旧对象中。因此增长同时影响内存和每 tick 遍历成本。

这是无界保留，不是“敌人池已经归零”能覆盖的生命周期。建议分离活跃战斗与有限历史统计，明确保留上限；验证长时间创建/结束循环。不要为保持旧测试可随时 stats(id) 而无限保留整个运行态。

## 6. 文档与验证方式的改进建议

### 6.1 收紧“已完成”和“等价”的用语

当前 00-architecture §0 的“玩法自洽重制”、11-decision-register §0 的“照抄与修正都合法”，与 deviations 中“可观察后果一律照抄”的口径存在张力。**用户当前要求应约束后续实现**：接受原版无法运行的限制，同时继续用源码、数据和明确例外约束规则。

后续每个批次分别记录：

1. 规则函数已实现；
2. 世界调用点及权威状态已接通；
3. 双端协议及表现已接通；
4. 原版语义已核到的范围、主动差异和未决项。

“默认 0、测试里可注入”只对应某一层，不等于整条玩法完成。I.1–I.4 完成后 F15 仍在，说明前置完成不会自动清掉调用点中的旧占位。

### 6.2 引用函数还不够，要核对表达式与控制流

每条规则至少记录以下证据：

| 要素 | 本轮对应教训 |
|---|---|
| 原文件、函数、分支及宏依据 | F03 的 8.0/8.5 常量冲突 |
| 字段/枚举的实际数值与命名空间 | F02 把 51 当成 7 |
| 中间类型、赋值和取整点 | F01、F16 |
| 随机取值集合、概率、次数和位置 | F03、F16、F18 |
| 写状态的时点及下一位行动者读到什么 | F04、F05、F07 |
| 数据进入点、有效值域、默认值的退出条件 | F06、F08、F14、F15 |

原版资料不能验证的地方，保留“不知道”。推测设计意图不能自动升级为源码事实，也不能作为改动可观察结果的依据。

### 6.3 验证应有独立来源

保留现有构建和回归守卫，但增加源码驱动的反例：

- 以源表达式确定期望，再调用新实现；不从新实现复制一份计算得到期望。
- 浮点与 RNG 使用边界样本，验证结果集合和分布，而非只数调用次数。
- 多动作场景检查执行顺序、中途离场、失败回滚及跨回合状态。
- 世界/客户端集成检查权威值，不以“有事件”“计数增加”替代语义。
- 真实数据扫描与人工构造反例各有用途：前者量化影响，后者暴露边界。前置条件的控制断言不通过时，不能引用该场景作证。
- 代码改变后重新定位旧“前置未实现”注释，尤其是宣称未来会自动生效的字段。

### 6.4 文档自身需要勘误，但不能改写历史

新增审计结论后，建议在相应 journal 条目旁追加勘误指针，保留当时记录；当前规格、DR 及测试期望再随具体修复同步更新。

需要优先回写的范围：状态命中率及抗性（F01/F02/F06）、行动调度（F03）、瞬时世界写（F04/F07/F08）、敌方容量与遇敌道具门（F14/F15）、随机端点与时序（F16/F18）、客户端验收（F11–F13）。
