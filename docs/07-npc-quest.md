## 1. NPC 的注册面

### 1.1 旧形状

```
data/npc/*.template 的 functionset=<id>
        ↓ NPC_searchFunctionSet(id)                    ← 找不到返回 −1
functionSet[66] 的 16 个回调名(★ 字符串)
        ↓ getFunctionPointerFromName(name)
名→指针表(331 条:NPC 201 / ITEM 117 / CHAR 7 / PET 5 / PETMAIL 1)
        ↓ hashpjw 先比 hash 再 strcmp
        ↓ ★ 查不到 → 返回 NULL,不报错、不日志
CHAR_FUNCTABLE 的 26 个槽
```

| 指标 | 值 | 含义 |
|---|---:|---|
| functionset 条目 | 66 | = NPC 子系统总数 |
| 回调槽 | 16 | 每个 NPC 最多 16 个行为钩子 |
| 有 `loopfunc`(tick 驱动) | **16** | ★ 只有这 16 个是真状态机 |
| 有 `windowtalkedfunc` | **46(69.7%)** | ★ 主流交互形态是「请求-响应对」 |

### 1.2 新形状

★ **不复刻字符串绑定** —— 它是 C 缺少一等函数值的产物。
新实现用接口/函数值直接注册,**断链在编译期发现**。

```
NpcBehavior {
    on_init(ctx)                         // 生成
    on_talked(ctx, actor) -> WindowOpen  // ★ 46/66 只需要这一个
    on_window_reply(ctx, actor, reply) -> WindowOpen | Done
    on_tick(ctx, dt)                     // ★ 只有 16 个需要
    on_looked / on_item_put / ...        // 其余槽按需
}
```

★ **绝大多数 NPC 是无状态的 `(actor, window_id, choice) → WindowOpen` 纯函数**,
状态存在实体的少量工作字段里(见 `03-domain-model.md` §2.2)。

### 1.3 ⚠️ 迁移前必须跑的三重检查

`16` §3.2:链路有**三处可断且全部静默**:

| 断点 | 实例数 | 说明 |
|---|---:|---|
| `functionset=` 找不到 id | **18** | ★ 头名 `ExChageMan`(**是 `ExChangeMan` 的拼写错误**,少一个 `n`)引用 6 次 ⇒ 这 6 个 NPC 是**哑的** |
| 回调名不在名表 | **16** | ★ **恰好是 5 个 functionset 的完整集合**(见 §2.3) |
| 实现文件不参与编译 | **6** | `npc_door.c` `npc_fmchallenge.c` `npc_roomadminnew.c` `npc_sample.c` `npc_ship.c` `npc_simpleshop.c` |

★ **断链是「整体断」不是「零散断」** —— 这提高了判定的可信度:
名表漏登记应当零散出现,整体断说明**这 5 个模块被整体废弃**,只是没人从表里删掉名字。

⚠️ **不跑这三重检查,就会把已经死掉的子系统当活的去实现。**

### 1.4 ★ 大小写口径:相邻两处不同

`09` §6.3:

| 查找 | 实现 | 大小写 |
|---|---|---|
| `functionset=` → `functionSet[]` | 纯 `strcasecmp` | **不敏感** |
| `.create` 的 `enemy=` → `templatename` | ★ 先比 `hashpjw` 哈希(**区分大小写**),再 `strcasecmp` | **实际敏感** |

⇒ 数据里同时存在 `ExchangeMan`(10 次,小写 c)、`ExChangeMan`(4 次,正确)、
`ExChageMan`(6 次,**错拼**)。因为查找不敏感,**前两者能绑上,只有第三个是哑的**。

⚠️ `templatename` 那一路是**潜在坑**:哈希预筛让后面的 `strcasecmp` 形同虚设。
**实测投产数据 0 例**(未知模板 0 / 仅大小写不同 0),故是潜在而非现存缺陷。

## 3. 内容 DSL 的语言规格

### 3.1 ★★ argstr 的真实构造:三条必须照抄的行为

`09` §2.2 / §2.3。**整个文件被逐行拼成一个 `|` 分隔的长串**,key 查找是
**`strstr` 子串匹配 + 取冒号第 2 段**:

| # | 行为 | 后果 |
|---|---|---|
| ① | **返回第一个命中的段** | 同名 key 出现多次时只有第一次生效 |
| ② | ★★ **`strstr` 子串匹配,不是等值** | `"EVENT"` 命中 `"NEWEVENT1"`;`"Item"` 命中 `"DelItem"`;`"PET"` 命中 `"PETTEMPNO"` |
| ③ | ★ **值 = 冒号第 2 段** | 值里再出现 `:` 会被**截断** |
| ④ | ★ **不做任何注释剥离** | `#` 开头的行照样是一个段,**只要它包含某个 key 的子串就会被命中** |
| ⑤ | 行尾已有 `|` 时不再补;空行被吞掉 | 作者可把多个 key 写在一行手动分隔 |

⇒ ★★ **任何"按行 split 冒号"的提取器都与投产行为不符。**
迁移脚本必须复用 `09` 的 `npc_dsl_parse.py`,不要自己实现。

★ **一条 GBK 安全性**:`:` 与 `|` 的切分走 `ScanOneByte`,**跳过双字节序列的尾字节**
⇒ 汉字里的 `0x3A`/`0x7C` 不会被当分隔符。
⚠️ **但多字节分隔符(`"EventEnd"` / `"OVER"` / `"!="`)走裸 `strstr`,没有这层保护。**

### 3.2 四种方言(块分隔符是每个消费者自选的)

| 方言 | 块分隔符 | 条件键 | 消费者 | 实测 |
|---|---|---|---|---|
| **EventNo 事件块** | `EventEnd` | `EVENT` | ★ **唯一一个解释器** | 863 文件 / 3,514 块 |
| 菜单/动作块 | `}` | `FREE` | 事件动作 | 489 文件 |
| OVER 块 | `OVER` | `FREE` | 传送 NPC / 战斗 NPC / 传送点 | 287 文件 |
| 宠物对话 | `OVER` | `FREE` + `PET` 子条件 | 宠物事件 | `data/npc/pettalk` |

★ **宠物对话方言的专属机制**:代码只认前缀 `TALKRUN` / `EVENTRUN` / `BOTH`,
数据里的 `TALKRUN1`…`TALKRUN19` **尾部数字只是内容作者的编号** ——
这就是这批 key 在 C 里搜不到字面量的原因。

⚠️ **只按 `}` 切会漏掉 1/4 的条件式**(实测 623 → 1,552)。

### 3.3 条件语言 EBNF

```ebnf
expr        = branch , { "," , branch } ;      (* ★ 不只是 OR,见 §3.5 *)
branch      = atom , { "&" , atom } ;          (* AND,短路 *)

atom_event  = pet_atom | cmp_atom | reduce_atom ;
pet_atom    = ? 任何含子串 "PET" 的原子 ? ;    (* 先于一切被截走 *)
reduce_atom = var , "=" , int , "*" , int ;
cmp_atom    = var , ( "<" | ">" | "!=" | "=" ) , int ;

atom_free   = [ head , "-" , temp ] ;          (* ★ FREE 方言多一个前置 "-" 切分 *)
head        = var , op , int
            | var , "=" , int , "*" , int      (* 数量 ≥ *)
            | var , "=" , int , "^" , int ;    (* ★ 数量 == ,仅 FREE 有 *)

var         = ? 两套变量表之一,或任意存档字段名 ? ;
int         = ? atoi 语义:跳过前导空白,取首个整数,取不到为 0 ? ;
```

**求值顺序不可改**(它决定含多个运算符的原子怎么解释):

```
EVENT 方言:  PET → "<" → ">" → "!=" → "="(含 "*" 走数量判定)→ 都不中则 FALSE
FREE  方言:  ★ 先按 "-" 切 → "<" → ">" → "!"(★ 探测用 "!",切分用 "!=",且整体取反)
              → "="(含 "*" / "^")→ 都不中则 FALSE
```

⚠️ **`<` 在投产数据里只用了 16 次**(vs `=` 9,968 / `>` 3,866)
⇒ 绝大多数"等级下限"是用 `LV>N` 写的,**语义是「> N」不是「≥ N」**。

### 3.4 ★★ 两套变量表,内容作者混用过

| | EVENT 方言 | FREE 方言 |
|---|---:|---:|
| 变量数 | 32 | 52 |
| 交集 | 29 | 29 |
| 各自独有 | `SP` `IMAGE` `PROSK` | `MT` `FAME` `GOLD` `EQUIT` `PARTY` `DR` `DP` `Skill` `BOX` `MANOR` … 共 23 个 |

★ **实测混用一例**:某 NPC 写 `EVENT:LV<11,DR<11,DR=77,DR=777` ——
`DR`(斗技排名)**只存在于 FREE 表** ⇒ **后 3 条分支在该路径下恒假**,只有 `LV<11` 有效。

⚠️ ★ **新实现若把两张表合并成一张(很自然的"简化"),这个 NPC 的行为会变** ——
从"只看等级"变成"也看斗技排名"。⇒ **须显式决策**(§10 决策 1)。

### 3.5 ★★ `,` 是分支选择器,不只是 OR

```c
while (取第 i 个逗号分段) {
    i++;
    if (该分支成立) { i--; return i; }   /* ★ 返回 1-based 序号 */
}
return -1;
```

返回值驱动文案 key 的后缀:`AcceptMsg%d` / `ThanksMsg%d` / `RequestMsg%d` / `NomalWindowMsg%d`。

⇒ ★ **第 N 个条件分支命中 ⇒ 用第 N 号文案。** 这解释了三件事:

1. `AcceptMsg1..10` 这些 key **在 C 里搜不到字面量**;
2. ★★ **条件分支与文案是位置耦合的** —— 重排、插入、删除分支都会让文案错位;
3. **空分支(连续逗号)也占一个序号**(实测 9 处)。

⇒ **新实现必须给每个分支显式 ID**,不能沿用位置耦合(见 `02-protocol.md` §5.3 改变 1)。

### 3.6 ★ 第三条变量通路:任意存档字段名

两个求值器的**末尾**都有一段"遍历存档键表比对名字"的兜底
⇒ ★ **任意存档字段名都是合法的条件变量**(8.5 有 270 个,8.0 血统 173 个)。

⇒ **变量空间实际上是开放的** —— 新实现若只实现两张表会漏掉这条通路。

⚠️⚠️ **这条通路用 `strcmp`,区分大小写。** 实测踩中一次:
4 个宠物对话文件写 `FREE:LV>0&HP<51&HP>20`,而键表里的键是**小写 `"hp"`**
⇒ **这 12 个原子恒假**,那 4 条宠物台词永远走兜底分支。

★ **变量名的大小写是有意义的,新实现不能做大小写规范化。**

## 4. 事件类型与块的前置门

### 4.1 五种 `TYPE:`

`09` §4。分派用 **`strstr` 匹配** ⇒ `TYPE:MESSAGE `(带尾空格)照样命中(实测 11 处)。

| TYPE | 实测 | 行为 |
|---|---:|---|
| `MESSAGE` | **2,123** | 就地处理:气泡或窗口;**立即执行副作用**(置旗标 / 传送 / 任务上报) |
| `ACCEPT` | **1,150** | 先出确认窗,玩家点 YES 才结算 |
| `REQUEST` | **194** | 按"是否已在进行中"分流到进度文案或接取文案 |
| `CLEAN` | **23** | 放弃 / 清旗标 |
| `LV` | 1 | ⚠️ **不是一种类型** —— 四类全不中 ⇒ 该块**静默无分派** |
| 异常值 | **19** | `-1 TYPE` 10 / 乱码 1 / 带尾空格 11(其中 7 已计入上表) |

### 4.2 ★ 块的前置门(顺序不可改)

```
1. 按 "EventEnd" 取第 i 块
2. EventNo 取不到          → ★ 整块跳过
3. 该事件已完成            → 跳过    (★ EventNo = -1 时恒 FALSE ⇒ 永不跳过)
4. KeyWord 存在且不匹配    → 跳过
5. Pet_Name 存在 → 置标记
6. 条件求值返回 -1         → 跳过
7. 按 TYPE 分派;四类都不中 → ★ 继续下一块(不是返回)
8. 全部块都不中 → ★ 从 NomalMainMsg 的逗号列表里随机选一句说出来
```

★ **`EventNo:-1` 是「不占旗标位」的惯用写法** ⇒ **该块可无限次触发**。
实测 `EventNo` 为 `-1` 的块占绝大多数。

## 6. 旗标系统

### 6.1 存储与编号空间

```
array = flag / 32;  shift = flag % 32;
两个独立位图:已完成(ENDEV)与进行中(NOWEV),各占一段连续的持久化槽
```

| 血统 | 槽位数 | 编号空间 | 证据 |
|---|---:|---:|---|
| **8.0** | **8** | **0..255** | ★ **三源交叉**:B80 存档键 `evt`..`evt8` 可检索、`evt9` 不存在;`SSRC80` 枚举同型;8.5 枚举门控 |
| 8.5 | 32 | 0..1,023 | |

★ **实测投产数据用到的最大旗标号 = 226** ⇒ **8.0 下只剩 29 个空位。**

### 6.2 ⚠️ 两个必须修的缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | ★★ **没有上界检查** —— 只在 `flag == -1` 时提前返回 | 旗标号 ≥ 256 会写进相邻的 `NOWEVENT` 段;更大的号写到转生字段 |
| 2 | ★ **清除路径用 XOR** 而不是 `&= ~(1<<shift)` | **若该位本来就是 0,这次"清除"会把它置 1** |

★ 缺陷 2 在投产路径下通常不触发(调用点前面刚置过位),
**但另一条清除路径(`CleanFlg`)走的是不同函数**。
⇒ **重构时不要照抄 XOR,除非确认要保留这个行为。**

### 6.3 旗标也可由代码硬编码置位

`09` §8.2 扫到 **14 处**在 C 里带字面量旗标号的置位/检查:

| 出处 | 旗标 |

## 8. ★ 遇敌触发

> **为什么它值得做到最深**:**它决定整个游戏的节奏,而只有 600 行,成本极低。**
> 遇敌率错了,数值表再准也没用。
> ⚠️ 本节公式的置信度恒为【8.5 源码推定】。

### 8.1 数据侧:`encount.txt` 的 33 列

**1,050 数据行,列数恒为 33,覆盖 581 个 floor。**

| 列 | 语义 |
|---|---|
| 0–1 | `index` / `floor` |
| 2–5 | 生效矩形 |
| **6–7** | ★ `encountprob_min` / `max` —— 遇敌计数器上下界 |
| 8 | `enemymaxnum` —— 一次最多生成几只 |
| **9** | ★ `zorder` —— **区域叠加时的优先级,大者胜** |
| 10–19 | `groupid[0..9]` |
| **20–29** | ★ `createprob[0..9]` —— **权重(不是百分比)** |
| 30–32 | `event_now` / `event_end` / `enemy_group` |

**分布**:`min` 90.3% 为 1;`max` 41.6% 为 3、30.0% 为 5。

### 8.2 ★★ 公式与"一个键决定整个节奏"

```
每步:  p_hit(cep) = temp / (120 × ENEMYACTION)     temp ≈ cep(无职业修正时)
       命中   → cep 复位到 minep
       未命中 → cep = min(cep + 1, maxep)
```

⇒ ★ **玩家走得越久,遇敌概率越高;命中后立刻回到最低。**
**这是一个刻意设计的反连续遇敌机制。**

⚠️ **8.5 与 8.0 的骰子分母写法不同**:
视图是 `rand()%(120*getEnemyAction())`,`SSRC80` 是**裸的 `rand()%120`**
⇒ **`_ENEMY_ACTION` 宏在 8.0 血统源码里根本不存在**。
但 `csa8.0/setup.cf:43` **确实写着 `ENEMYACTION 1`** ⇒ **1 是等效值(乘 1 等于没乘),两版行为一致**。

**★ 期望步数表**(逐步展开求期望,不是几何分布近似):

| `min` | `max` | 行数 | 占比 | **csa8.0**(EA=1) | stoneage85(EA=3) | StoneAge(EA=10) |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 3 | **437** | 41.6% | **41.0 步** | 121.0 | 401.0 |
| 1 | 5 | **315** | 30.0% | **26.0 步** | 74.0 | 242.0 |
| 1 | 7 | 116 | 11.0% | 20.1 步 | 54.4 | 174.4 |
| **0** | **0** | **90** | 8.6% | ★ **∞(永不遇敌)** | ∞ | ∞ |
| 1 | 2 | 36 | 3.4% | 60.5 步 | 180.5 | 600.5 |
| **100** | **100** | **2** | 0.2% | ★ **1.2 步** | 3.6 | 12.0 |

⇒ ★★ **`ENEMYACTION` 这一个键把节奏拉慢 3 倍 / 10 倍。这解释了不同私服"打怪频率"体感差别巨大。**
⇒ **新实现必须把它做成一等的运营旋钮,并在文档里标明它的量级效应。**

★ 两条运营含义:`(100,100)` 的 2 行是**必遇敌区**(剧情强制战斗点);
90 行 `(0,0)` 是**安全区**(城镇/剧情区)。
⚠️ **安全区总数须与 §8.4 的"无 groupid"取并集,不能只看一条判据。**

### 8.3 区域选取

`zorder` **最大者胜**,不是先命中先赢 ⇒ 同一坐标可落在多个遇敌区里。
581 floor / 1,050 行 ⇒ 平均每图 1.8 个遇敌区,**存在刻意的区域叠加设计**
(整图一个低频区 + 局部一个高频区)。

### 8.4 ★ 编组选择的四类数据缺陷

```
1. 逐 groupid 过滤(持有道具才出现 / 持有道具则不出现)
2. r_max = Σ createprob[found];  r_max--
3. r = RAND(0, r_max)
4. 累加 aaa += wr[i];  if (wr[i] != 0 && r < aaa) break;
```

在真实数据上跑出的**四类可复算缺陷**:

| 缺陷 | 行数 | 含义 |
|---|---:|---|
| ★ **无任何 groupid** | **82** | 该坐标区**永不生成敌人** |
| ★ `groupid` 个数 ≠ `createprob` 个数 | **22** | 多出的那侧被忽略或权重取 −1 |
| ★ 有 groupid 但 createprob 留空 | **6** | 权重 = −1,**会拉低 Σw** |
| ★★ **存在永不被选中的编组** | **5** | 权重分布使某组不可达(如配了 6 组只给 3 个权重,后 3 组恒选不到) |

★★ **这四类是"原版就有的 bug",不是提取错误。**
⇒ **如果目标是行为一致,必须复刻;如果修 bug,遇敌构成就与原版不同。**
★ **建议:照抄语义,但在数据加载时打 warning,把决策权交给运营。**

⚠️ 另有一处 `atoi` 语义缺陷:某行 `encountprob_max` **字段为空** ⇒ `atoi("") = 0`
⇒ 等效于 `(0,0)`,**永不遇敌**。这不是解析错误,是原始数据留空。
