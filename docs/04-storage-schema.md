## 0. 一个反常识的起点

> ★★ **按 8.0 基线,关系库只需要「账号 + 密码 + 在线态 + 封禁 + 一种点数」。
> 其余全部是文本文件和进程内存。**

`17` §10.2 实测 `csa8.0/saac/csadb.mdb`(**74 KB**,Standard Jet 格式),
去掉系统表与 VBA 残留后,**可辨识的业务表只有一张**:

```
表:  CSAlogin
列:  Name / PassWord / RegTime / LoginTime / Online / OnlineName / Path / lock / VipPoint / Info
```

与 `acserv.cf` 三方吻合(`SQL_INFOTABLE CSAlogin` / `SQL_LOCK lock` / `SQL_VIPPOINT vippoint`)。

对照 8.5 的 **27 张表**(`capturepet` `CashDraw` `consignment` `loan` `OnlineBuy` `OnlineCard`
`OnlineCost` `PauctionInfo` `petbilling` `SaleVipPoint` `weekpay` `yuxiaxie` …):
**26 张是私服运营层加的**(计费、拍卖、赌博、抽奖、贷款、周薪)。

⇒ ★ **这是存储选型最重要的一条输入**:新库的规模由"要把哪些文本文件与进程内存搬进库"决定,
**不由 8.5 那 27 张表决定**。

⚠️ 但反过来也有加法:8.0 的**文本文件与进程内存**里装着大量必须持久化的东西
(角色档、公共仓库、家族、庄园、邮件、排行),它们在原版就没有事务保护(§5)。
**新库要接的正是这一块。**

## 1. 存储选型

| 项 | 定 | 备注 |
|---|---|---|
| 关系库 | **MySQL 8.4.8 / InnoDB / `REPEATABLE READ`** | 用户环境 |
| 字符集 | ★ **`utf8mb4` / `utf8mb4_0900_ai_ci`,库级强制** | §7.2 说明为什么这不是例行公事 |
| 客户端库 | **Connector/C++ 8.4**,JDBC 风格,3306 经典协议 | 不用 X DevAPI |
| 认证 | ★ **`caching_sha2_password` + TLS** | §1.1 |
| 角色档 | ★ **JSON 列 + 生成列索引**,不引入文档库 | §4.2 |
| 缓存 / 锁 / 排行 | **Redis 8.6.2**,生产与测试都用 | §6 |

### 1.1 ⚠️ 8.4 的一处硬差异

**MySQL 8.4 默认不再启用 `mysql_native_password`**(降为需显式加载的组件)
⇒ 旧版 C/C++ 客户端库连不上。

- **Connector/C++ 必须取 8.4 线**;
- 需配 TLS 或 RSA 公钥交换才能完成 `caching_sha2_password` 的首次认证。

★ **这一点极易在联调第一天被误诊成网络问题**,先写在这里。

**两项待在服务器上核实**(本文不替代实测):① X Plugin(33060)是否启用;② MySQL 是否已配 TLS。

## 2. 库划分

按 `00` §3 的服务边界(方案 B,按延迟敏感性切),库跟着服务走:

| 库 | 属主服务 | 一致性 | 内容 |
|---|---|---|---|
| **`sa_session`** | session-storage | ★ **强一致 · 原子** | 账号、角色档、道具、宠物、公共仓库、登录态 |
| **`sa_social`** | social | 最终一致 | 家族、庄园、邮件、留言、名片簿、排行落盘 |

★ **判据是 `17` §3.2 的实测**:7 条"会挂起玩家"的协议**全部落在会话与存档一侧**;
社交侧 39 条**一条都不挂起玩家**。

⚠️ **一处已知的归属难点**(`17` §9.1):**KV/排行域两难** ——
`DBDeleteEntry*` 参与删角(延迟敏感),其余 11 条是排行(不敏感)。
**裁定:`DBDeleteEntry*` 对应的派生数据表划归 `sa_session`**(`00` §3)。

### 2.1 测试形态

单容器形态下**两个库仍然是两个库**(同一个 MySQL 实例的两个 schema),
不合并成一个。理由同 `00` §3.1:**进程内形态不是"可以直接读对方"的许可**,
库也一样 —— 合并了就会有人写跨库 JOIN,生产拆开时挂。

## 3. `sa_session` 的表

### 3.1 账号面

| 表 | 说明 |
|---|---|
| `account` | 账号本体:登录名、密码哈希、注册时间、状态 |
| `account_ban` | 封禁:原因、生效区间、操作者 ⇒ ★ 从 `CSAlogin.lock/LockTime/LockInfo` 三列独立出来 |
| `account_session` | 当前登录态:实例 ID、世代号、角色、心跳时间 |

⚠️ **不做 `CSAlogin` 那种"一张表装完账号 + 在线态 + 点数 + 封禁"**。
原表把在线态(高频写)与账号资料(几乎不写)混在一行,是**行锁热点**。

### 3.2 角色面

| 表 | 主键 | 说明 |
|---|---|---|
| `character` | `char_id` | 角色标识、账号、名字(唯一)、创建/删除时间 |
| `character_data` | `char_id` | ★ **持久化字段的 JSON 列 + 生成列索引**(§4.2) |
| `character_item` | `item_uid` | 道具实例;`owner_kind`(角色/仓库/地面)+ `owner_id` + `slot` |
| `character_pet` | `pet_uid` | 宠物实例;含融合码、技能槽、主人字段 |
| `character_skill` | `(char_id, skill_id)` | ★ 变长集合,不做 `haveSkill[26]` 定长数组 |
| `character_title` | `(char_id, title_id)` | 同上,替代 `indexOfHaveTitle[30]` |
| `depot_item` / `depot_pet` | `uid` | ★ **公共仓库**,与 `character_item` 同族但归属不同(§5.3 是它出事的地方) |
| `address_book` | `(char_id, seq)` | ★ **独立聚合** —— `addressBook[80]` 占 `sizeof(Char)` 的 39%,不该在实体里 |

### 3.3 字段口径

★ **持久化边界直接沿用原版的字段级划分**(`11` §7 C5):

```
有存档键的  285 个   → 入库
纯运行时的  384 个   → 不入库
死字段       41 个占持久化空间 → ★ 直接删,不建列
```

⚠️ **把运行时字段一起持久化会让存档膨胀 135%。**

## 4. `character_data` 的形状

### 4.1 为什么不做 285 列宽表

三条理由,都来自 `03-domain-model.md`:

1. 47 种实体共享同一套 slot,**宽表会让 90% 的列恒为默认值**;
2. 65 条别名要求字段按实体族拆开 ⇒ 宽表反而回到了合并;
3. 字段集会随玩法演进变化,**宽表的每次加列都是一次 DDL**。

### 4.2 JSON 列 + 生成列索引

```sql
CREATE TABLE `character_data` (
  `char_id`   BIGINT UNSIGNED NOT NULL PRIMARY KEY,
  `schema_ver` INT UNSIGNED  NOT NULL,        -- ★ 显式版本,原版没有
  `payload`   JSON           NOT NULL,
  -- 需要被查询/排序的字段提升为生成列 + 索引:
  `level`     INT  AS (payload->>'$.level')     STORED,
  `floor`     INT  AS (payload->>'$.floor')     STORED,
  `fame`      INT  AS (payload->>'$.fame')      STORED,
  KEY `idx_level` (`level`),
  KEY `idx_floor` (`floor`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

**三条使用边界**:

| # | 边界 | 理由 |
|---|---|---|
| 1 | ★ **只有真被查询/排序的字段做生成列** | 生成列是有成本的;285 个全做等于回到宽表 |
| 2 | ★ **`schema_ver` 必须显式写** | 原版存档**无版本号 ⇒ 字段增删即破坏兼容**(`01` §6.3) |
| 3 | **`payload` 的 schema 由 IDL / 领域模型生成,不手写** | 与 `02-protocol.md` §8 同源:单一真源 |

⚠️ **不用 JSON 列做"什么都往里塞"的口袋**。
持久化字段集是**已知且有限**的(285 个),JSON 只是免去 285 次 DDL,不是免去建模。

## 5. ★★ 事务面:12 个"必须原子",原版有保护的是 0 个

`17` §4.5 / §5 的清单。这是新库最贵的一部分,逐条给对策:

| # | 操作 | 原版失败后果 | 新做法 |
|---|---|---|---|
| **T1** | **角色存档保存** | ★ `charSave` **先解锁后写盘**;三个失败分支任一触发 ⇒ 锁已放、档没写 ⇒ **另一线路登录读到旧档,本次进度永久丢失且玩家无提示** | ★ **写盘成功后才释放锁** |
| **T2** | 存档写盘 | `fopen(fn,"w")` 截断重写,**无 `fflush`/`fsync`/`rename`**;崩溃留半截档,原档已覆盖,8.0 又无备份 ⇒ **角色永久损坏** | InnoDB 事务;**并留 `schema_ver` + 结构级校验** |
| **T3** | 存档读取 | `loadCharOne` 的形参 **`outlen` 一次都没被使用** ⇒ 超长档直接溢出 | 显式长度约束 |
| **T4** | **公共仓库存盘** | ★★ **fire-and-forget 后立刻销毁本地道具对象**;失败时唯一处置是发一句聊天提示,**不回滚不重试** ⇒ **道具永久蒸发** | ★★ **「预留 → 提交」两阶段,禁走 Notify**(§5.3) |
| **T5** | **角色删除** | ★★ **4 条协议 × 3 个职责域,且不等第 1 条的结果**;密码错 ⇒ **角色还在,但决斗点与名片簿已删**,而且全服已广播"此角色已删除" | ★ **Saga + 补偿**:删存档成功后才删派生数据(§5.4) |
| T6 | 点数扣减 | 读-改-写两条独立 SQL,全用绝对值写 ⇒ 并发丢失更新 | ❌ **整条不做**(点数系统 8.0 不存在,见 `08-economy.md` §7) |
| T7 | 充值销卡 | 三条独立 SQL,两种坏结局 | ❌ 同上 |
| **T8** | **家族仓库 / 资金** | 只改进程内存 + 脏标记,**600 秒后才落盘** ⇒ saac 崩溃回滚 10 分钟 | InnoDB 事务,写即持久 |
| **T9** | 建族 / 入族 / 退族 / 解散 | 两侧不同步 ⇒ **孤儿成员 / 幽灵家族** | 跨库 ⇒ Saga(§5.4) |
| T10 | 庄园占领结算 | 部分成功 ⇒ 庄园归属与点数不匹配 | 单库事务(同在 `sa_social`) |
| T11 | 家族 PK 结算 | 部分成功 ⇒ 战绩单边 | 同上 |
| T12 | 邮件投递 | 收件箱写失败 ⇒ 发件人以为发出、收件人没收到 | 同上 |
| T13 | 跨星球迁移 | 部分成功 ⇒ 角色两边都在或两边都没有 | ⏸ 暂不做(多星球是后续拓扑) |

★ **12 条里 9 条在单库内 ⇒ InnoDB 事务直接解决**(`17` §9.2 方案 C 的量化)。
剩下的是 T4(资产两阶段)、T5 / T9(跨库 Saga)。

### 5.1 ⚠️ 加数据库事务解决不了的另一半

`12` §5.3:`trade.c:975 TRADE_HandleTrade` 是 **10 步顺序结算 + 零回滚**,
任一步失败就把已扣的道具/宠物/石币留在半途;调用者只 `return -1`,同样不补偿。

★ **这与 saac 侧的 SQL 事务缺失是两个独立问题。**

⇒ **`world` 进程内也需要工作单元边界**:

```
world 进程内 UoW:  收集变更 → 全部校验通过 → 一次性提交到领域对象
                   任一校验失败 ⇒ 整体丢弃,不留半途状态
storage 侧   UoW:  InnoDB 事务
跨服务       UoW:  Saga + 补偿
```

**两侧都要做。**

### 5.2 周期落盘的丢失窗口(不复刻)

`17` §4.3 的 `csa8.0` 投产值:

| 任务 | 间隔 | 崩溃丢失窗口 |
|---|---:|---|
| KV 与排行 `dbFlush` | **3,600 s** | ★ **1 小时**的排行/决斗点/名片簿变更 |
| 家族 `writeFamily` + `writeFMPoint` + `writeFMSMemo` | **600 s** | ★ **10 分钟**的全部家族变更 |

★ **玩家在 10 分钟内做的所有家族操作只存在于 saac 的进程内存;saac 崩溃 = 全部回滚。**
⇒ 新实现**写即持久**,不做"周期 flush 内存表"。
⚠️ 若为性能引入写缓冲,**必须是 WAL 语义而不是"整表定期重写"**。

### 5.3 ★★ 资产移动一律两阶段

**这是 12 条里后果最严重的一条**(`17` §5.4):

```c
①  saacproto_ACCharSavePoolItem_send(...);   // 只写进发送缓冲
②  CHAR_removeDepotItem(charaindex);          // ★ 立刻销毁本地道具对象
③  return TRUE;                               // 无条件报成功
```

⇒ 发送后到落盘之间的任何失败(缓冲溢出 / 崩溃 / 磁盘满),
道具**既不在 gmsv 也不在 saac** ⇒ **永久蒸发**。
★ 源码注释里那句「◆特别注意:请勿将贵重宠物存入公共仓库」**说明作者知道这个问题**。

**新做法**:

```
Reserve:  存储侧写入 pending 记录(带 idempotency key),世界侧道具置为 LOCKED
Commit:   存储侧确认 → 世界侧才销毁本地对象
Abort:    超时或失败 → 世界侧解锁道具,存储侧清 pending
```

⚠️ **`Ack{accepted}` 只代表入队,不代表持久化** ⇒ **资产类操作禁走 Notify**(`00` §3.1)。

### 5.4 角色删除的 Saga

`17` §5.5 的原始序列(**② ③ ④ 在 ① 的结果回来之前就发出去了**):

```
① ACCharDelete        删存档     (D2)
② DBDeleteEntryInt    删决斗点   (D4)
③ DBDeleteEntryString 删名片簿   (D4)
④ Broadcast           全服广播   (D7)
⑤ CONNECT_setState(WHILECHARDELETE)
```

而 ① 在 saac 侧有三个失败分支(密码错 / 找不到角色 / 删文件失败)。

**新顺序**:

```
1. 校验(密码、角色归属、是否在战斗/交易中)      ← 全部前置
2. sa_session 事务:标记 character 为 pending_delete
3. 等待确认成功
4. 才发起派生数据删除(决斗点、名片簿、家族退出)  ← 可重试,失败不影响 2
5. 全部完成后才广播
6. 补偿:4 失败 ⇒ 重试队列;超过阈值 ⇒ 告警 + 留待人工
```

★ **`17` §5.5 原文的一句话值得抄下来**:这条操作**横跨三个候选服务,
无论怎么切都会变成分布式事务 —— 任何切分方案都必须回答它。**

⚠️ 另一处:`ACDelFM` 失败时**存档文件已经删了**,家族里留下一个指向不存在角色的成员槽,
**无补偿**(整个函数体内 `rollback` / `restore` / `undo` 零命中)。
⇒ 新顺序把"家族退出"放在第 4 步的可重试集合里,正是为此。

## 6. Redis 的职责

**Redis 是生产必需,不是可选项**(`00` §5)。理由是实测而非惯例:

| 事实 | 出处 |
|---|---|
| 账号锁是**纯进程内存 256 桶哈希链**,零持久化 ⇒ saac 崩溃 = 全部锁丢失 | `17` §6.1 |
| `lockdir` 是**死代码** —— 8.0 算了路径从不使用,8.5 已删光;`csa8.0/saac/lock/` 有 256 个空目录、**零文件** | `17` §6.2 |
| ★ **锁只有账号级粒度 ⇒ 42 条家族协议完全无锁**,靠"saac 单线程"隐式串行 | `17` §6.3 |
| 多个 saac 实例互不可见(8.0 用 LS 上锁服务器补这个洞,8.5 删了) | `17` §6.4 |

| 用途 | 结构 | 说明 |
|---|---|---|
| **分布式锁** | 带 TTL 的 SET NX | ★ **须有超时** —— 原版无超时,gmsv 崩溃且 saac 没察觉时账号被永久锁死到 saac 重启 |
| **家族级并发控制** | 按 `family_id` 的锁 | ★ 原版这一级**根本没有锁**,拆分后必须补 |
| **跨分片路由** | `char_id → shard` | |
| **排行** | ZSET | 替代 `db.c` 的自研 KV + 定期 flush |
| **在线态** | Hash + TTL | 替代 `CSAlogin.Online` 的行写热点 |

⚠️ **测试环境不得省掉 Redis** —— 省掉会造成最坏的一种情况:
**测试跑通、生产挂**,而本项目没有任何行为验证手段接住它。

⚠️ **不复刻的一个 bug**:`17` §8.3 —— 星系移民锁的守卫字面量 4 处里错 1 处
(`DeleteMemLock` 写成 `"移民"`,实际写入的是 `"星系移民"`)⇒ **移民锁会被当普通锁删掉**。
新实现把锁语义显式建模(锁类型是枚举),**不用字符串比对做守卫**。

## 7. 内容资产导入(L4)

### 7.1 什么进库、什么不进库

| 内容 | 处置 |
|---|---|
| 9 张主数值表(道具 13,885 行 / 敌人 2,154 / 宠物模板 1,053 / 遇敌 1,050 / …) | ★ **进内容管线,不进业务库** —— 它们是随版本发布的只读资产 |
| 1,235 个 `LS2MAP` + 客户端地图 | 同上 |
| 3,536 个 NPC 数据文件 / 3,514 个事件块 | 同上 |
| 源码内**硬编码**数值表(108 个玩法表 / 29,456 元素) | ★ 同样外置为内容资产,不留在代码里 |
| 角色档、家族、邮件、排行 | 进业务库 |

★ **区分玩法配置与部署配置**(`01` §9):前者进内容管线,后者进部署。
原版把两者混在一个 `setup.cf` 里,导致改一个数值要重启整条线路。

### 7.2 ⚠️ 入库前必须完成编码归一

**这不是例行公事。** `09` §2.4 / `05` §7.4 的实测:

```
data/ 下 3,604 个文本文件:GBK 3,341 · EUC-JP 45 · cp950(Big5) 10 · GB18030 1 · ASCII 207
★ 72 个文件的注释行与数据行编码不同
★ 64 个文件的数据行内部就混了 ≥2 种编码
```

且乱码链是**双重的**:EUC-JP 日文 → 被当 Big5 解码 → 繁转简写成 GBK。

⇒ **管线必须逐文件查 `encoding_map.json`;对 `per_line_required=true` 的文件逐行试解**,
整文件一把解码会**静默丢字**。

★ **决策 ② 保证新库从第一天就干净,但任何一条乱码串进库,
之后就再也分不清是数据本身还是转换错误。**

### 7.3 导入期必须显式处理的三处数据缺陷

### 7.4 ★ 一个必须裁定的数据精度问题

## 9. 审计表

`12` §8.3 的三个结构性缺口,直接决定审计表的形状:

```
① 无 correlation id —— 一次交易在 tradelog / itemlog / stonelog 里是三条互不关联的行
② LogTrade 是 sprintf 拼串,不是结构化字段
③ ★ 5 个「直接清零」石币写点与 18 个绕过 CHAR_AddGold 的增发口,一条日志都不写
```

⇒ **新审计表**:

```sql
CREATE TABLE `audit_event` (
  `event_id`   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `corr_id`    BINARY(16)   NOT NULL,     -- ★ 一次业务操作 = 一个 corr_id
  `kind`       SMALLINT UNSIGNED NOT NULL,-- 事件类型枚举(不是字符串)
  `actor_id`   BIGINT UNSIGNED NULL,
  `occurred_at` DATETIME(3)  NOT NULL,
  `payload`    JSON          NOT NULL,    -- 结构化字段,不是拼串
  KEY `idx_corr` (`corr_id`),
  KEY `idx_actor_time` (`actor_id`, `occurred_at`)
) ENGINE=InnoDB;
```

★ **资产变更事件必须携带变更前后余额** —— 8.0 的 `LogBankStone` 已经这么做了,
其字段设计可直接沿用(`12` §8.3)。

事件类型清单见 `08-economy.md` §6。
